# e2e 评测流程重设计计划（0831）

> 目标：在既有 0818–0827 评测链基础上，重设计一套**可复现、同批、中文公平、面向真实使用**的端到端（e2e）评测流程。重点解决四件事：
> 1. **Mem0 中文适配**——给 OSS Mem0 打补丁（jieba 分词替换英文 lemmatize + 中文 spaCy 模型），使其 BM25/实体信号在中文下真实参与，而非静默退化为纯向量。
> 2. **Zep 上游对照**——Zep Community Edition 已弃用，采用 **Graphiti 自托管（Graphiti+Neo4j）作为 Zep 核心的对齐基线**，并如实披露其与完整 Zep（含 MMR rerank / context assembly）的差距。
> 3. **评测对象与方法重构（本次核心变更）**——场景明确为**情感陪伴**；评测对象收敛为"**系统喂给模型的结构化记忆上下文块**"（不生成回复做判分，避免比较回复模型能力）；判断方式为**同题并排一次判定**（把三系统的上下文块同题一起交给 judge 相对比对），不再"3 次回复取平均"。
> 4. **方法论修正**——修复 0828 报告审计发现的硬伤：跨批次混排、同族 judge、PAR 自定 purpose 标尺；并回填复现缺口（v3 查询集、数据版本、边数不一致）。

## 一、背景与动机

### 1.1 为什么重设计（承接 0828 报告审计结论）

0828 报告《对比评测数据》在方法学上透明、自我批判充分，但经审计存在以下**影响数字可信度**的问题，需在重设计流程中系统性修正：

| # | 问题 | 审计依据 | 对数字的影响 |
|---|------|---------|------------|
| 1 | **跨批次混排**：PAR/RAG 用 0819 批次，Graphiti 用 0821 批次，却在同一张表比较 | `0828报告 §3.5/§9` | T6 排位（4.74/4.67/4.51）需同批重跑 |
| 2 | **同族 judge**：抽取/StoryRank/judge/PAR 目的推断均基于 deepseek 系 | `§6.3 局限·7` | 存在自偏好，无独立模型交叉验证 |
| 3 | **PAR 自定 purpose 作 judge 标尺** | `eval/run_pipeline.py:109` | 带查询五维实为"PAR 自定标尺下各家表现" |
| 4 | **复现缺口**：报告用 v3 查询集（30 陈述+5 弃权、9 情境），仓库仅 v1 问答式 | `data/LiFEMem_queries.yaml` vs 报告 §1.2 | headline 数字无法从仓库复现 |
| 5 | **数据规模不一致**：报告 410 边，实际 392 边 | `data/LiFEMem.yaml` 实测 322 节点/392 边 | 图结构/联想论证的基准数对不上 |
| 6 | **小样本 + 单次判定**：35 条查询、单次 R@all 波动 std ±11.4pp | `§4.6` | 幅度性结论缺乏置信区间 |

### 1.2 Mem0 中文适配的根因（已确证）

Mem0 OSS 检索侧三路信号（语义 / BM25 / 实体 boost）中，后两路对中文**静默失效**，根因已定位到源码硬编码英文：

- `mem0/utils/spacy_models.py:60` — 实体抽取强制 `spacy.load("en_core_web_sm")`
- `mem0/utils/spacy_models.py:85` — BM25 词形还原强制 `en_core_web_sm`（`disable=["ner","parser"]`）
- `mem0/utils/lemmatization.py` — 对每条查询与每条入库记忆跑英文 lemmatizer

后果（[mem0 issue #4884](https://github.com/mem0ai/mem0/issues/4884) 已复现）：中文整句 lemmatize 后与库内 lemmas 零重合 → `bm25_scores` 恒空 → `has_bm25=False`、实体 boost 消失 → **非英文部署一律退化为纯语义**。这解释了 0819 报告"35/35 逐条同序 = 纯向量"的实测。

> 存储侧并非问题：Mem0 已内置 `ADDITIVE_EXTRACTION_PROMPT_ZH` 中文抽取提示词，抽取阶段中文正常；仅检索侧 BM25 词形还原 + 实体 NER 是英文硬编码。**补丁只动检索侧，不动抽取侧。**

### 1.3 Zep 上游对照的现状（已确证）

- **Zep Community Edition 已弃用且不再受支持**（2025-04 弃用，2026-02 进一步删功能）；官方替代仅：Zep Cloud（SaaS）/ Graphiti（开源）/ BYOC。
- Zep Cloud 的多语言支持"在路线图上、尚未显式"——中文全文检索无保证，且免费额度（1000 credits/月）不足以支撑 322 节点全量建图 + 多次检索。
- **决定**：采用 **Graphiti 自托管（Graphiti+Neo4j）作为 Zep 核心对齐基线**（复用 0821 已接入的 `frameworks/graphiti_runner.py`），并如实披露其与完整 Zep 的差距：缺 MMR rerank、缺 context assembly（`thread.get_user_context` 的 4-episode BFS + MMR 重排）。

## 二、目标与成功标准

### 2.1 目标

1. 建立**同一场景（情感陪伴）、同一批次、同一 judge、同一口径**的四系统对照：Ariadne PAR / Naive RAG / Mem0(中文补丁) / Graphiti(Zep 核心)。
2. 评测对象改为**系统喂给模型的结构化记忆上下文块**（非检索候选、非 StoryRank 故事、更非"回复"），把回复 LLM 与记忆系统**解耦**，judge 只评记忆上下文块作为陪伴素材的质量。
3. Mem0 在中文下 BM25 + 实体信号**真实参与排序**（不再与 Naive RAG 逐条同序），并量化其对检索与**上下文块质量**的净增益。
4. 明确并量化 Graphiti 作为 Zep 核心基线的定位与差距。
5. 全部 headline 数字可从仓库一键复现（输入锁定、脚本参数固化、产物版本化）。

### 2.2 成功标准（可验收）

**评测方法变更（本次核心）**
- [ ] 场景明确为**情感陪伴**，查询集/判分 rubric 与场景对齐（见 §4.5）。
- [ ] 评测对象 = **系统喂给模型的结构化记忆上下文块**（Ariadne=`{story}`、Mem0=`{memories}`、Graphiti=`{entities,relations}`），**不生成回复做判分**（§4.5.2）。
- [ ] 判断方式 = **同题并排一次判定**：每条查询把三系统的上下文块同题一起交给 judge 相对比对，每题判分一次（§4.5.3，不再"3 次回复取平均"）。
- [ ] judge 用 `temperature=0`（稳定）；若日后评估 judge 稳定性，作为**独立一致性子实验**（多次判分取均值），不混入主判分。

**Mem0 中文补丁**
- [ ] Mem0 中文补丁后：qdrant(BM25) 与 faiss(纯向量) 的候选排序**不再逐条同序**（对照中文实验须为"至少 N/35 不同序"，以英文实验 0/10 同序为参照）。
- [ ] BM25 稀疏向量对中文文本产生**词级多维度**（对齐英文 1→6 token 的程度，中文句须≥3 token）。不再出现整句哈希单维。

**方法论修正**
- [ ] 四系统**同一 judge 会话**内完成同题并排判分，无跨批次混排。
- [ ] judge 结果由**至少两套模型**（deepseek + 一个非 deepseek 系）做交叉一致性（kappa / 排位相关性）验证。
- [ ] `data/LiFEMem_queries_v3.yaml`（或等价重建物）与数据版本号回填仓库，`0828报告` 的 headline 数字可重跑。
- [ ] 报告明确披露：purpose 来源（PAR 自推断）、Graphiti 与完整 Zep 的差距、expected 口径说明。

## 四、总体架构（新 e2e 管道）

```
输入锁定 ─► 检索层 ─► 组装(结构化记忆上下文块) ─► 同题并排判分 ─► 汇总 ─► 交叉验证 ─► 报告
   │          │           │                    │              │        │
 情感陪伴      PAR        Ariadne={story}      三系统上下文块    每题判分   独立模型
 查询集+数据   RAG         Mem0={memories}      同题一起交给    均分→总均分 judge一致性
 版本化       Mem0(zh)    Graphiti={entities,  judge 相对比对   +分情境
             Graphiti     relations}          (temperature=0)
```

**公平性协议（五同 + 三项新增）**：

- 同数据、同查询、同指标、同判定、同 embedding（沿用 0818 五同）。
- **＋同批次**：四系统候选 → 组装上下文块 → 判分全部在**同一 judge 会话**内完成（修复跨批次混排）。
- **＋同 purpose 来源**：明确 judge 使用的 `查询目的` 由 PAR 自推断产生，并在报告中披露（该偏置方向偏向 PAR，需要单独声明或改为三方独立推断）。
- **＋同候选配额**：候选数按 PAR 输出量 N 动态对齐（沿用 D2 决策）。
- **＋同组装形态对齐**：四系统产物统一映射为 `{story}`/`{memories}`/`{entities,relations}` 三形态上下文块，用同一 prompt（`JUDGE_JOINT_PROMPT`）交给 judge，确保判断侧无差异（差异只来自检索/组装输入）。

### 4.5 评测方法：情感陪伴场景 + 结构化记忆上下文块判分 + 同题并排一次判定（本次核心变更）

#### 4.5.1 场景设定：情感陪伴（系统的建立基石）

- **基石定位**：**情感陪伴是本系统最初建立的基石**，也是整个记忆体系（DBA 建图 → 联想检索 → StoryRank 表达）的原点。系统不是为"知识检索"而生，而是为"用记忆去陪伴用户"而生——这与报告 §5.2 的定论一致：**记忆系统（情景记忆）与知识库（语义记忆）应分离合作**，本系统行走在"情景记忆/陪伴"一侧，而非"知识库/事实问答"一侧。
- **对联想性质的证明作用**：情感陪伴恰好需要联想型检索具备的核心能力——唤起相关人生经历、情感纽带、情绪应对史、跨场景关联。因此**各种评测与联想性质（跳转轴/目的回归/发散区记忆价值）都可在该基石场景下得到印证**；若联想检索在此场景不占优，恰恰说明系统基石未立，需回头审视。
- **定位**：用户表达情绪/状态/倾诉（如"最近项目排得太满，天天加班到十一二点……"），系统需调用记忆**共情、理解并提供陪伴性回应**，而非做事实问答。
- **对检索的影响**：陪伴场景**天然放大联想/发散型系统（PAR）的优势**。因此本场景下"纯向量最优"的既有结论**可能反转**——报告须如实呈现、不得预设结论（若反转，恰恰是"联想价值在陪伴场景成立"的直接证据，而非对既有结论的否定）。
- **查询集处理**：从既有 v3 集（含工作压力/情绪/怀旧/关系/健康等 9 类情境）中**筛选或重标注**为情感陪伴子集；每条查询标注"用户在表达何种情绪/需要何种陪伴"。

#### 4.5.2 评测对象：系统喂给模型的结构化记忆上下文块（不生成回复做判分）

```
查询 ─► 检索(候选) ─► 组装(结构化记忆上下文块) ─► judge 直评该块
```

- **不对**检索候选、不对 StoryRank 故事、更不对"回复"打分；judge 直接对"系统组装、将喂给模型的结构化记忆上下文"打分：Ariadne=`{story}`、Mem0=`{memories}`、Graphiti=`{entities,relations}`。
- 这避免"变成在比较回复模型的回复能力"：把回复 LLM 与记忆系统**解耦**，judge 只评记忆上下文块作为陪伴素材的质量。
- **模型可替换（解耦接入）**：judge 通过 API 配置接入（`.env`/runner 参数），**不绑定某一家**；作为报告的模型敏感性变量披露（如 deepseek / GPT-4o / Qwen-Max / 豆包等）。

#### 4.5.3 判断方式：同题并排一次判定（不再"3 次回复取平均"）

- 每条查询把**三个系统的上下文块同题一起**交给 judge（在一起比对更易分辨好坏，避免绝对打分全 5 天花板，见 §4.5.4）。
- 每题判分**一次**：本方法不对回复打分，故不再"生成 3 次回复取平均"。若日后要评估 judge 稳定性，可多次判分取均值，作为**独立一致性子实验**，不混入主判分。

#### 4.5.4 判分维度（陪伴场景 rubric，三系统同题齐评）

**同一次对话里同时给出三个系统的记忆上下文块，让 judge 在一起比对后各打 1–5 分**（相对分辨，避免绝对打分全 5 天花板）。维度（各 1–5 分）：

| 维度 | 含义 |
|------|------|
| 记忆丰富度 | 记忆信息是否足够丰富、能支撑充分的陪伴（5=非常丰富，1=单薄贫乏） |
| 易理解性 | 这段上下文是否条理清晰、便于直接用（5=一目了然，1=晦涩零乱） |
| 用户建模度 | 能否据此准确理解用户、形成用户画像（5=很强，1=很弱） |

> 各系统块：Ariadne=`{story}`（模型实际看到的检索故事，非内部 nodes）、Mem0=`{memories}`、Graphiti=`{entities,relations}`。judge 材料是"喂给模型的结构化记忆上下文"，即 `JUDGE_JOINT_PROMPT`（`eval/smoke_system_compare.py`）。
> ⚠️ judge 同源偏置仍存在（陪伴场景主观性强）→ 交叉模型验证为**必要条件**（§8）。

#### 4.5.5 总分汇总

- 每题标准分 = judge 对该题上下文块的一次判分（同题三系统各一档，见 §4.5.3）。
- **总评 = 所有题目标准分的均值**（同时给出总和与按情境分解，报告主看总均分）。
- 四系统用同一套判分、同一 judge、同一场景，排位可直接对比。

#### 4.6 外部指标：系统内部 LLM token 成本（非回复侧）

**定义**：统计记忆系统「自身」在每轮对话中因检索/写入而调用的 LLM 的 **input+output token 累加**。它不同于回复侧（模型上下文注入 token），衡量的是**记忆框架自己做主推理/抽取的算力开销**，与调用架构强相关。

**架构差异（决定性）**：

| 系统 | 内部 LLM 调用 | 触发频率 | 定性 |
|---|---|---|---|
| Ariadne | search=目的推断+StoryRank；**write=MemoryDBA.maintain（triage+节点+边）** | search 仅换话题/冷启动；write 每轮 | 每调用 prompt 小；search 低频 |
| Mem0 | 抽取/去重 | 每轮（每个消息抽取） | 侵入式，每轮固定开销（巨型提示词） |
| Graphiti | 节点+边合并抽取 | 每轮（每次 ingest） | 每轮，且随图规模膨胀 |

**实测（冒烟，会话 = 6 轮 + 1 次换话题，Ariadne search 2 次 + 每轮 write(maintain) 6 次；嵌入模型 token 不计）**：

| 系统 | 单轮内部 LLM | 会话总计 |
|---|---|---|
| Ariadne | search=1050，write(maintain)=2220 | **15418** |
| Graphiti | 6858 | 41151 |
| Mem0 | 8250 | **49500** |

- **检索非 LLM 已确认**：Mem0 用真实 `mem.search()` 实测 = 0 LLM（默认 `rerank=False`、未配 reranker → 向量+BM25）；Graphiti 混合检索同样非 LLM。
- **Mem0 添加**：用真实 `add(infer=True)` 包裹 `mem.llm.client.chat.completions.create` 实测 = **1 次 LLM 调用/轮**（抽取 + 增/删/改决策在同一调用合并），input 7932 / total 8250。
- **Graphiti 抽取**：`add_episode_bulk`（合并抽取，含重试）实测 4 episode → 16 调用 / 27434 token。
- 比值：Mem0 ≈ **3.2×** Ariadne，Graphiti ≈ **2.7×** Ariadne。**Ariadne 的"添加节点"也花 token**——`MemoryDBA.maintain`（triage+节点抽取+边连接，单轮 2220）。真正优势不在"add=0"，而在**每调用 prompt 更小**（maintain input≈2073 vs Mem0 7932）且 **search 低频**。
- **口径透明**：Ariadne search 用 `retrieve_with_story` + langchain `.invoke` 的 `token_usage`；Ariadne write 用 `MemoryDBA.maintain` 实测；Graphiti 用 AsyncOpenAI `.usage`；Mem0 用真实 `add(infer=True)` 包 openai `create` 的 `.usage`。均为 API 真实 token。

#### 4.6.2 检索侧增长趋势（三系统"检索到多少内容/注入量"）

> complement §4.6.1：上节测的是**写入/抽取侧**（Ariadne maintain、Mem0 add、Graphiti ingest）。本节补**检索侧**——"图/库规模 ↑，检索返回多少内容、注入多少 token"。检索侧分两层：① 内部 LLM 成本（只有 Ariadne search 是真 LLM；Mem0/Graphiti 检索是向量+混合，**非 LLM=0**）② **检索注入量**（检索结果喂给下游模型/回复的上下文 token，用 cl100k_base 统一标尺）。

| 检索侧 | N=50 | N=100 | N=200 | 趋势 |
|---|---|---|---|---|
| Ariadne 候选数 | 26 | 26 | 26 | **自然收敛**（PAR 寻峰终止+目的回归拦截，图内相关节点已搜完） |
| Ariadne story注入token | 415 | 331 | 367 | **平**（~330-420） |

**关键结论（检索侧）**：
1. **⚠️ "恒定"≠优势：Ariadne 的 26 与 Mem0 的 8 性质完全不同**——这是本测量最需要区分的事实：
   - **Ariadne 候选恒 26 = 检索机制的自然收敛**（PAR 寻峰终止 + 目的回归拦截）：PAR 会把图中与该查询**相关的因果路径节点**全部找到，26 已是该类查询在该图内的**完整相关集合**（再大图里若无额外相关节点，就是 26；若相关节点更多，理论上会更多，此处图内相关节点即 26）。这是"检索完整/不遗漏"的体现，不是人为设限。
   - **Mem0 返回恒 8 = `top_k=8` 硬截断**：库/图内可能存在更多相关记忆，但只取 top-8。**代价是检索深度与丰富度大幅下降**——对比 Ariadne 一次检索到 26 条，Mem0 仅有 8 条（且注入 token 267 vs Ariadne story 367，显著更少）。**图越堆越大时，Mem0 被 `top_k` 砍掉的潜在相关记忆越多，丰富度损失被放大**，而这个损失不会出现在 token 数字里（因为被截断的没进入上下文）。
   - 因此**不能把"Ariadne 与 Mem0 都不随规模增长"等同视之**：Ariadne 的"恒定"可能反映检索收敛到完整集合；Mem0 的"恒定"是**截断损失**。若把 Mem0 的 `top_k` 调到 26，其注入量与深度会上升（也会更接近 Ariadne 的覆盖），届时成本会相应增加——本测量用默认 `top_k=8`，需在报告里把这一点**与 Ariadne 的检索完整性对照披露**。
2. **Graphiti 是唯一检索侧随规模线性放大的系统**：facts 50→102→210，fact 注入 token 888→1785→3635（≈2×）。其混合检索把**图谱遍历出的更大子图**作为上下文注入，图越大返回越多——这正是用户担心的"图遍历在多节点/关系下爆表"在**检索侧**的体现。
3. **单条 fact 长度恒定（~17.5 字符）**——Graphiti 注入增长**完全来自"返回的 fact 数量增多"，而非单条变长**，属"数量型"膨胀（子图遍历范围随规模扩大）。
4. **量级对比（检索注入量，非写入成本）**：N=200 时 Graphiti 检索注入 3635 token，明显高于 Ariadne story(367)/Mem0(267)——检索注入随规模增长的只有 Graphiti。此 3635 是**检索侧注入量**（会进模型上下文），需与写入成本分开呈现；若主 LLM 上下文窗口紧张，Graphiti 在大规模下的检索注入会先成为瓶颈。<!--（注意：此 3635 是检索返回的 fact 注入量，与写入侧无关，勿与一次性建图初始化成本混为同一量纲）-->
5. **对评测的意义**：检索侧的"封顶"要分两类看——**Ariadne 是检索机制的自然完整收敛**（26 是完整相关集合）、**Mem0 是 `top_k` 硬截断**（8 是截断结果，损失深度/丰富度，且图越大截断损失越明显）。只有 **Graphiti 真正随规模增长**（子图遍历放大）。因此报告应同时给出：①各系统检索**注入量**（谁喂给模型的内容更多）；②各系统检索的**完整性/覆盖**（Ariadne 26 vs Mem0 8 vs Graphiti 210 facts 的差异）——避免只看到 Mem0"省 token"而忽略其丰富度裂口。

#### 4.6.3 架构性归因：为何三系统单次/会话成本都恒定，而 Graphiti 检索注入随规模涨

> 背景：Graphiti 与 Ariadne 同属**图结构记忆系统**。§4.6.1/4.6.2 实测：三系统**单次写入/会话成本都恒定**（不随规模 N 增长）；但 Graphiti 的**检索侧注入量**随规模增长。本节点明**根本差异在架构**，并披露 Mem0 的同源图谱模块这张"隐藏牌"。

**根本差异：是否"整图遍历/消歧"作为每次调用的上下文**

| 维度 | Graphiti | Ariadne | Mem0（默认向量+BM25） |
|---|---|---|---|
| **抽取/写入** | 每条消息 ingest 都要做**实体抽取 + 与图中既有实体/边的消歧、去重、合并** | `maintain` 只处理**本条新内容**的节点抽取，仅在**局部邻近**连边，不把整图塞进抽取 | `add(infer)` 抽取 + 增/删/改决策，只对照**相关记忆**，不遍历整库 |
| **检索** | 内置**混合检索 + 图遍历**，返回子图随规模扩大、注入量随规模线性涨 | 按需检索，PAR 寻峰终止 + 目的回归拦截 → 候选收敛到**完整相关集合**（恒定 26），不随规模扩大 | search = 向量+BM25，`top_k` 封顶（恒定 8） |
| **单次成本随规模** | **不随规模增长**（写入/检索单次均恒，~10.45k） | **不随规模增长**（恒定 2.4k） | **不随规模增长**（恒定 ~9.2k） |
| **每个会话成本** | **恒 ~63k**（6×~10.45k，随轮数累积） | **恒 ~18k**（6×2.4k + 2×search） | **恒 ~58k**（6×9.2k） |
| **架构** | **时态图谱 + 三路混合检索**，核心就是"建图 + 遍历" | **tool-calling 按需检索**，只在需要时局部建图/检索 | **侵入式记忆**，检索是向量/BM25，非图 |

**结论：三系统"单次写入/检索"成本都**不随图规模放大**——Ariadne 2.4k、Mem0 9.2k、Graphiti 10.45k，三者单次都恒定；Ariadne 单次最低。差异在于调用频率（Ariadne 按需/search 低频，Mem0/Graphiti 每轮都抽）与单次成本大小。Graphiti 的"随规模增长"体现在**检索侧注入量**（返回子图随图规模扩大，见 §4.6.2），而**单次/会话写入成本恒定**。同为图结构系统，是否把"全图上下文"塞进每次调用，决定单次成本与检索注入量。**图结构之于 Ariadne 是"精确召回相关路径"的手段（按需、检索收敛），之于 Graphiti 是"建图 + 遍历"的引擎（检索注入随规模扩大）。**

**第二个结构差异：侵入式 = 每一轮都有固定抽取开销（与"本轮值不值得抽"无关）**

Mem0/Graphiti 是**侵入式（in-stream）**：每来一条消息都强制走一次 LLM 抽取（Mem0 `add(infer=True)`、Graphiti `ingest`）。因此**对话一旦进行到数轮，之后的每一轮都背着这个固定的抽取 token**——即使本轮没有新内容、没有换话题、没有需要检索的信息，也要付这一笔；且它与对话历史长度无关，只与"每轮都抽"这一机制相关，是**随轮数线性累加但不消失的固定开销**。

对比 Ariadne 的 **tool-calling（按需）**：LLM 只在**真正需要记忆时**才被调用——search tool 只在冷启动/换话题时触发，write 才走 `maintain`；其余轮次主 LLM 完全不调记忆系统（`add` 只是把内容交接给抽取，不即时消耗对话 token）。所以 Ariadne 的消耗**由"用户是否需要记忆"驱动，而非"每轮都付"**。

> ⚠️ 这解释了为什么会话级成本差距在**长对话**下会被进一步拉大：Mem0/Graphiti 每轮固定抽取 `~9.2k / ~10.45k`，**轮数越多，这部分累积越大**（且都不随图规模 N 增长）；Ariadne 若不换话题，search 几乎不再发生，只有 write 的 `maintain`。上面的 §4.6.1 会话级（6 轮 + 1 次换话题）已含此差距，但报告应注明**真实语境下对话更长时差距只会更明显**——侵入式框架是"每轮都烧"，按需式是"只在用到时烧"。

#### 4.6.4 Mem0 的同源图谱模块（隐藏牌，若启用则检索注入随图同步增长）

- **Mem0 本身也内置"图谱/实体"模块**（与 Graphiti 同源的图记忆范式：`graph_store: neo4j`、实体/关系抽取、图遍历检索）。本项目当前评测**未启用**（用默认向量+BM25 混合检索），因此测得"Mem0 成本恒定"。
- **若启用 Mem0 图谱模块，其检索侧将随图规模增长**（走"图遍历返回子图"，注入量随规模扩大，同 Graphiti）；写入侧"实体抽取 + 图消歧/去重"的单次成本仍恒定（类 Graphiti 逐条 ingest）。届时 Mem0 就不只是"恒定 8 条/58k"的省成本系统，其**检索注入量会随规模放大**（单次写入/会话成本本身仍恒定）。
- **对评测的界定**：本报告的"Mem0 检索恒定/成本恒定"结论**仅适用于默认向量+BM25 模式**；必须声明 Mem0 存在与 Graphiti 同源的图谱选项，且启用后在**检索注入**上同样随规模增长。因此若对比要做"同范式公平"，应在**同一范式**下比：向量范式（Mem0 默认 vs Ariadne 故事检索）/ 图范式（Graphiti vs Mem0 图谱模式 vs Ariadne 若启图谱），而非混用 Mem0 向量模式来代表"Mem0 的整体成本"。
- 若启用，Mem0 相比 Ariadne 就不再是"检索封顶"的优势，而是像 Graphiti 那样**检索注入随规模膨胀**（单次写入/会话成本则仍恒定）。

#### 4.6.5 三系统「抽取 → 输出」全链路 LLM 调用点覆盖核对（确认统计完毕）

## 六、Mem0 中文适配：补丁实现方案

### 6.1 补丁范围（只动检索侧，不动抽取侧）

> **核对结论（已对照 mem0ai 2.0.18 实际源码）**：Mem0 检索侧中文失效的真正入口是 **`lemmatize_for_bm25`（BM25 词形还原）** 与 **`extract_entities`（实体抽取）** 两个函数；`spacy_models.py` 只提供英文模型加载器（`get_nlp_full`/`get_nlp_lemma`），并**不**包含这两个函数。BM25 词形还原/实体抽取的实际定义在 `lemmatization.py` / `entity_extraction.py`，且被 `main.py` 以 `from ... import` 直接导入到自身命名空间——**因此补丁必须同时覆盖源模块与 `mem0.memory.main` 命名空间**，否则 `main.search()` 仍走旧函数。

| 层（真实入口） | Mem0 现状（英文硬编码） | 补丁后 |
|----|-------------------|--------|
| BM25 词形还原 `mem0.utils.lemmatization.lemmatize_for_bm25` | 内部调 `get_nlp_lemma()` 加载 `en_core_web_sm`；spaCy 不可用时整句原样返回 → 中文整句发给 fastembed = 单 token | 改为 jieba `lcut` 后空格连接（"用户 喜欢 喝 咖啡 提神"）→ fastembed 按空白切分出词级 token |
| 实体抽取 `mem0.utils.entity_extraction.extract_entities` | 内部调 `get_nlp_full()` 加载 `en_core_web_sm`，且启发式面向英文（`tok.text[0].isupper()` / PROPN / noun_chunks / `-ing`） | 换为 `zh_core_web_sm` NER（仅换模型不够——中文无大写，`isupper()` 恒假，需整体替换函数体） |
| spaCy 模型加载 `mem0.utils.spacy_models.get_nlp_full/get_nlp_lemma` | 硬编码 `en_core_web_sm`（第 60/85 行） | 中文时加载 `zh_core_web_sm`（作为备选，非主补丁） |
| BM25 稀疏向量（qdrant） | 由 payload 的 `text_lemmatized` 字段（`vector_stores/qdrant.py:206`）经 fastembed 空白分词 → 整句单维 | 词级多 token（随 `lemmatize_for_bm25` 修正自动生效） |

### 6.2 实现方式（monkeypatch / 子类，不打散 meme0 本体）

在 `frameworks/mem0_runner_zh_patch.py` 中做**运行期注入**，避免 fork 整个 Mem0。**关键**：`main.py` 用 `from mem0.utils.lemmatization import lemmatize_for_bm25`、`from mem0.utils.entity_extraction import extract_entities`（对应 `main.py` 第 61/68 行），即主检索用的是 **`mem0.memory.main` 命名空间里绑定好的函数**——所以必须同时覆盖源模块与 `mem0.memory.main` 命名空间：

```python
import jieba
import mem0.memory.main as _mm              # sync Memory 实际引用处
import mem0.utils.lemmatization as _lem     # BM25 词形还原源模块
import mem0.utils.entity_extraction as _ee  # 实体抽取源模块

_ZH_NLP = None
def _get_zh_nlp():
    global _ZH_NLP
    if _ZH_NLP is None:
        import spacy
        _ZH_NLP = spacy.load("zh_core_web_sm")   # 中文 NER
    return _ZH_NLP

def lemmatize_zh(text: str) -> str:
    # jieba 精确分词 + 空格连接 → fastembed(Qdrant/bm25) 按空白切分出词级 token
    return " ".join(jieba.lcut(text))

def extract_entities_zh(text: str) -> list:
    # 中文 NER：仅换 spaCy 模型不够（英文启发式 isupper() 对中文恒假），需整体替换
    try:
        nlp = _get_zh_nlp()
        ACC = {"PERSON","ORG","GPE","LOC","FAC","PRODUCT","EVENT","NORP","LAW","LANGUAGE"}
        return [(ent.label_, ent.text) for ent in nlp(text).ents if ent.label_ in ACC]
    except Exception:
        return []

# 同时覆盖源模块 + main 命名空间（后者才是主检索真正调用的）
_lem.lemmatize_for_bm25 = lemmatize_zh
_mm.lemmatize_for_bm25 = lemmatize_zh
_ee.extract_entities = extract_entities_zh
_mm.extract_entities = extract_entities_zh
# infer=True 时会走批量抽取，一并覆盖（infer=False 可忽略）
_mm.extract_entities_batch = _ee.extract_entities_batch = extract_entities_zh
```

> ⚠️ 以上钩子点已对照 **mem0ai 2.0.18** 实测源码确认（本计划基线），并核实：BM25 索引由 payload 的 `text_lemmatized` 字段（[qdrant.py:206](file:///c:/Users/makot/AppData/Local/Programs/Python/Python311/Lib/site-packages/mem0/vector_stores/qdrant.py#L206)）经 fastembed 空白分词构建，查询侧 BM25 走 `_search_vector_store`（[main.py:1634-1648](file:///c:/Users/makot/AppData/Local/Programs/Python/Python311/Lib/site-packages/mem0/memory/main.py#L1634-L1648)）也经 `lemmatize_for_bm25`——故 jieba 修正可同时作用于入库与查询两侧。**实施前仍以 `pip show mem0ai` 锁定版本为准**，升级到含 v3 混合检索的版本时需复核这三处钩子（2.0.18 已含 v3 管线）。

## 七、Zep 上游对照：Graphiti 自托管基线

### 7.1 定位声明（披露）

**结论（§8.2 交叉一致性）**：
1. **Ariadne 占优在 4 个有效模型下均稳健**：qwen（4.74）/ gemini（4.56）/ gpt-5.6-luna（4.43）/ **deepseek（4.17）** 都把 **Ariadne 排首位**，排位方向一致（Mem0/Graphiti 仅在第 2/3 名间有交换）。→ **"Ariadne 全面占优"不是单模型自偏好产物**；连**同族的 deepseek 也认可**，是对审计点 2 的最严苛检验。
2. **两两 top-1 一致率 0.74~0.87、kappa +0.39~+0.58（次强~中等）、Spearman 0.65~0.69**——四模型对"谁是最好"的判断一致性为中等偏上，符合主观判分（陪伴场景）的预期水平；同族 judge 偏置（§1.1 问题 2）已获**实质缓解**。
3. **qwen / deepseek vs gpt-5.6-luna 的 kappa 最低（+0.389）**——qwen、deepseek 与 gpt 对"哪系统第 2"分歧更大（qwen 排 Graphiti>Mem0，gpt 的排位方向与 qwen 相同但分数差更小）。属预期（模型家族差异）。

5. **⚠️ 关键观察：同族的 deepseek 反而给 Ariadne 最低分（4.17，四模型最低）**——若存在"同族 model 自偏好/越近越捧"，同族的 deepseek 应对 Ariadne（同为可召回故事的叙事型产物）给**更高**分；但它反而在四个有效模型里**给最低**。这从反方向证明：
   - **无同族自偏好**：同族的 deepseek 并没有"因同族/同范式而偏袒 Ariadne"，反而更客观甚至更挑剔。
   - **Ariadne 占优是跨模型稳健的**：连最"可能偏袒"的同族模型都给出较低但**仍排 Ariadne 第一**的分数（4.17 vs Graphiti 3.56 / Mem0 3.30）。
   - **解释**：DeepSeek 作为高度"元认知/批判型"模型，对 `{story}`（Ariadne 的故事块）可能在"这是否讲故事讲得太满/是否主观渲染"维度上更苛刻，故整体压分，但**排位方向未变**。

> ✅ **审计点 2（同族 judge）已闭环**：主判分用非 deepseek 系（qwen3.8-flash），并额外用 gemini + gpt-5.6-luna + deepseek 做独立交叉，**四模型排位方向一致（Ariadne 均第一）**，自偏好风险已缓解。

**结论（语言/文化偏差）**：
1. **Ariadne 占优在 4 个有效模型下全部成立**（qwen / deepseek / gemini / gpt 均列 Ariadne 第一，4.17~4.74）。**连同族的 deepseek 也认可 Ariadne 占优**——说明这不是"同族模型集体偏好"（§1.1 审计点 2 的最严苛检验），而是跨模型稳健的结论。
2. **中文组（qwen+deepseek）vs 国外组（gemini+gpt）的 Ariadne 均分差仅 −0.04**——**未观察到国外模型对中国语境的系统性偏差**（Ariadne 上几乎无差；Mem0 −0.32、Graphiti +0.17 属中等幅度，且方向不一致，无单调语言偏差信号）。
3. **glm-4-flash 不能作为 judge 对照组**——其评分病态（形态偏好/评分通胀）掩盖真实信号，应作为"judge 质量退化"问题披露，而非"语言偏差"结论；已在脚本中显式排除出有效区域对照。
4. **Ariadne 占优结论不受 glm 影响**：主判分 qwen 未受污染；glm 异常是单模型质量问题，不是重跑主判分的理由。
5. **披露**：judge 模型质量差异是主观判分的固有风险（§10 风险表），本批次已用"4 有效模型交叉 + 披露单模型病态"双保险。

> ⚠️ **glm-4-flash 判分结论作废（保留记录）**：因其对 Graphiti `{entities,relations}` 形态的极端偏好（60/70 满分），该模型不纳入交叉一致性的有效对照，仅作为"judge 形态偏好"案例披露。
