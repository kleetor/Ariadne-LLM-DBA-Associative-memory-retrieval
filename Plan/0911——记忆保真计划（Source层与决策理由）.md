## 二、系统现状分析

### 2.1 核实结论

| 结论 | 证据 |
|---|---|
| 图里**没有任何来源信息** | [`MemoryGraph.add_memory`](../dba_pipeline/graph/memory_graph.py) 有 `metadata` 字段，但全仓库**无任何写入点**（恒为 `{}`，见 `mcp_server.py` / `viz/api_server.py` 均传 `metadata={}`） |
| 节点与原文**无法关联** | `add_conversation` 只返回 `nodes_created` 计数，不返回节点 id 列表；`to_dict()` 只落 5 个基础字段 + `PERSISTED_NODE_FIELDS`，无 `source_ref` |
| oplog **是"半个答案"** | [`oplog.py`](../dba_pipeline/oplog.py) 确实记了 `request`（含原文），但 `_summarize(max_str=200)` **截断到 200 字符**，且记不到任何节点 id。当审计日志够用，当纠错依据不够 |
| 错误会**反复回流** | [`_build_node_context`](../dba_pipeline/extraction/dba.py) 把"相关旧节点"喂进抽取 prompt（本意是去重/更新判断）→ 压缩后的"既成事实"反复进场，**没有任何环节回去质疑它** |
| 抽取是**唯一机会窗口** | StoryRank 规则 7 明确"节点里没写的动机、原因、结果一律不补"（防幻觉，正确），意味着**抽取漏了就永久丢** |

### 2.2 损失分类：为什么"决策理由"最先丢

当前 `REASON` 的定义是「**导致状态/行为的原因**」——它管**结果归因**，不管**选择依据**。

| 丢失的内容 | 图上有没有位置 | 说明 |
|---|---|---|
| 结果的原因（"因为客户换主色 → 通宵重做"） | ✅ 有 | `REASON` 节点 + `CAUSAL` 边接得住 |
| **被放弃的选项**（选了 A，B/C 呢） | ❌ 没有 | 图里只留"选了 A"，B/C 从未存在 |
| **权衡依据**（A 好在成本、B 好在工期） | ⚠️ 勉强 | 只有被单独抽成 `REASON` 才留得下；但「只抽事实」+「每条独立可读」天然把它当过程噪音滤掉 |
| **当时的信息约束**（"那会儿我还不知道 X"） | ❌ 没有 | 既不是 `STATUS` 也不是 `REASON` |

### 2.3 两个放大器

1. **不可逆**：抽取漏了 → StoryRank 不允许补 → 检索也拿不回来。
2. **会累积**：错误节点作为上下文回流抽取，压缩损失被当成既成事实反复引用。

### 2.4 现有可复用的基础

| 已有能力 | 用途 |
|---|---|
| `PERSISTED_NODE_FIELDS` 登记通道 | 新增 `evidence` / `source_ref` 字段的落盘出口（已在本轮验证可用） |
| `GraphBuilder._find_duplicate`（余弦 0.85 语义去重） | 巡检合并的操作执行器；也是补齐 `intervene` 去重的现成实现 |
| `oplog`（JSONL，含 ts / op / actor / request / result） | 巡检变更的审计与回滚依据 |
| `MemoryDBA.save_checkpoint` | 巡检前的快照点 |
| StoryRank 的 `adopted_ids` / `discarded_nodes` | 巡检结果的旁证 |

## 三、目标与非目标

### 目标

1. 让"为什么做这个选择"在记忆图上**有位置放**，且能被稳定抽出来。
2. 让每条节点具备**可核查的存在依据**（它凭什么存在）。
3. 让图具备**自我整理**能力（清理重复、纠正推测、补漏），而不是只靠后续对话偶然触及。

### 非目标

- 不改 ALM 侧行为（本计划全部改动对 ALM 保持 opt-in / 无副作用）。
- 不新增 `node_type`（`jump_axis.py` 中每种类型对应一张跳转权重表，加类型会牵动 PAR 扩展权重，属动核心检索）。
- 不做句子级 span 溯源（LLM 产出的是"消解指代 + 补省略"后的陈述，本就不是原文子串，span 天然对不上）。

## 四、任务划分

### 任务 A｜抽取侧：给"选择/决策"开口子（小）

**改动**

| # | 内容 |
|---|---|
| A1 | `REASON` 定义扩展为：`导致状态/行为的原因，或做出某个选择/取舍的依据` |
| A2 | 新增抽取原则：遇到"选择 / 取舍 / 权衡"表述时，**必须抽出被放弃的选项及其原因**，写成独立 `REASON` 节点（不新增 node_type，避免动跳转轴） |
| A3 | 对这类节点**放宽"每条独立可读"**：允许带最小限度的上下文指代（如「当时考虑到成本，放弃了 B 方案」） |
| A4 | 边界：不得编造未说出口的动机（与 StoryRank 规则 7 对齐） |

**验收**

- 构造含选择/取舍的对话（"比较了三种排期，最后选 A，因为…"），检查产出节点是否覆盖"备选 + 依据"。
- 回归：既有群聊专项的节点数、归属统计、时序锚点不得劣化。

**风险**：`REASON` 节点变多 → 图规模与叙事长度上升，需观察是否稀释检索精度。

**实测（0911，`eval/test_choice_extraction.py`，N=3 取中位数）**

实现方式：新增 `NODE_CHOICE_EXTRA` 补充规则（插入到 `## 输出` 之前），通过 `MemoryDBA(enable_choice_extraction=)` **opt-in** 控制；MCP 侧开启、ALM 侧关闭（关闭时 node chain 的 system prompt 与基线**逐字一致**，已断言）。

| 指标（中位数） | OFF（基线） | ON（开启） |
|---|---|---|
| 节点数 | 10 | 10 |
| **REASON 节点数** | **0** | **6** ↑ |
| 含"成本"依据的节点 | 3 | 4 ↑ |
| 含"时间"依据的节点 | 3 | 3 |
| 孤立节点数 | 0 | 0 |

OFF 的节点明细（关键）：
```
n2 [STATUS] 用户一开始打算把装修全包给装修公司
n3 [STATUS] 全包装修虽然省心，但报价比半包贵了快一倍
n4 [STATUS] 用户装修预算不够
n5 [ACTION] 用户因预算不够放弃了全包装修方案
```

ON 的节点明细：
```
n2 [REASON] 用户一开始考虑把装修全包给装修公司
n3 [REASON] 因为全包报价比半包贵了快一倍，用户放弃了全包方案
n5 [REASON] 用户也考虑过半包装修，但最终放弃了
n6 [REASON] 因为半包需要自己盯工地，用户实在抽不出那个时间，所以放弃了半包
n7 [ACTION] 用户最终折中决定：主材自己买、施工包给师傅
```

**结论**：任务 A 生效。但要注意一个反直觉的细节——**差异主要不在"内容覆盖"，而在"节点类型"**：

- OFF 并非完全没抽到信息（`n5` 内容里就带着"因预算不够"），但它被标成 `ACTION`/`STATUS`；
- ON 把"被放弃的选项 + 放弃原因"变成了 **`REASON` 类型的一等节点**，才能沿 `CAUSAL` 边被检索到；
- 所以关键词指标（"全包/半包"出现次数）几乎不变（5→5），真正的差异是 `REASON: 0 → 6`。

另一个必须确认的点：**孤立节点为 0**——新增的 REASON 节点没有变成孤儿（否则连续 3 轮孤立后会被 `forgotten` 清掉），说明连边步骤能把它们接上。

**波动**：ON 三次分别为 6/7/4 个 REASON，OFF 稳定为 0。中位数 6 有代表性，但单次对比不可归因（印证 §8.3）。

### 任务 B｜`evidence` 字段：给每条节点一个可核查依据（中）

**设计**

| # | 内容 |
|---|---|
| B1 | `PERSISTED_NODE_FIELDS` 增加 `evidence`（落盘通道） |
| B2 | 抽取 schema 增加 `evidence`：**原文中支撑该节点的最短连续片段**（必须是原文子串） |
| B3 | **程序化校验兜底**：`evidence` 去标点/空白后必须是该批原文的子串，不满足则丢弃该字段（不阻塞主流程） |
| B4 | 暴露范围：`dba_inspect_graph` 展示；**检索与 StoryRank 默认不注入**（避免污染叙事） |
| B5 | 开关：`ENABLE_EVIDENCE`（默认关），因 `evidence` 属原文片段，有隐私与体积属性 |

**为什么选 `evidence` 而不是全量原文**

- 体积远小于整段原文，且天然最小化（只留支撑部分，不是整段隐私）。
- 巡检可直接做**自洽核对**：`content` 是否被 `evidence` 支撑——单这一条就能抓 txt 的 `n22`（推测没有 evidence 支撑）。
- 代价：依赖 LLM 产出该字段 → 用 B3 的子串校验兜底。

**验收**

- 抽样检查 `evidence` 产出率与子串校验通过率（目标是能稳定产出，且非法 evidence 被程序化拦掉）。
- 人为构造一条推测型对话，确认该节点**没有**合法的 evidence 支撑 → 可作为巡检的判定信号。

**实测（0911）**

实现方式：`NODE_EVIDENCE_EXTRA` 补充规则 + **替换输出示例**（而不是追加规则，避免两套 schema 打架）；`MemoryDBA(enable_evidence=)` opt-in，MCP 侧开启、ALM 侧关闭；`sanitize_evidence()` 做去标点后的子串校验；字段登记进 `PERSISTED_NODE_FIELDS`。

离线断言（确定性）：
- 基础 prompt 的 sha1 未变（`82b99d91…`，1090 字符）→ **ALM 不受影响**
- 关闭 evidence 时 node chain 与基线**逐字一致**；开启时才替换输出示例
- `sanitize_evidence` 正确拦截"改写/概括"与"过短"两类非法片段，无 evidence 的 op 不受影响
- `to_dict` → YAML → `load_graph` 往返后 `evidence` 保留

真实 LLM（群聊语料，17 个节点）：

```
evidence 覆盖: 17/17 节点；非法（非原文子串）: 无
```

抽样：
```
n2  需求评审决定先做 A 方案，B 方案放到后面   ← evidence: '先做 A 方案，B 方案放后面'
n6  小林前天改 bug 改到凌晨两点               ← evidence: '前天改 bug 改到凌晨两点'
n8  客户最近又加了两版需求                    ← evidence: '客户最近又加了两版需求'
```

产出率与合法性都达标。**但要注意**：本语料是"每句话都能自证"的直白对话，LLM 摘原文片段的难度最低；对**归纳型节点**（如"用户最近压力大"）能否留空而非硬凑，还需要含推测成分的语料才能验证——那正是 C3 的判定依据，留待 C 阶段一并测。

**复测（同语料又一次抽取，18 节点）——发现了上面那个问题的答案**

```
handler 返回: evidence_stats = {'kept': 11, 'dropped': 7}
evidence 覆盖: 11/18 节点；非法（非原文子串）: 无
```

结论有三条，都会影响 C3 的设计：

1. **程序化校验确实在起作用**：7 条 evidence 不是原文子串（LLM 做了改写/概括/拼接），被 `sanitize_evidence` 拦掉。没有这道闸，这些"伪证据"会进图并**直接误导 C3 巡检**——这正是 B3 存在的意义。
2. **LLM 不倾向"留空"，而倾向"勉强凑一个改写版"**：18 条 op 全部带了 evidence 字段，其中 7 条不合法。规则里"原文找不到支撑就留空"没有被遵守；但经过校验后效果等价（那 7 条变成"无证据"）。
3. ⚠️ **合规率只有 ~61%（11/18），且波动大**（上一轮 17/17）。**因此 C3 绝不能把"有没有 evidence"当作唯一判定信号**——按 61% 的合规率，大量合法节点也会"无 evidence"，全判成无据会有接近四成假阳性。C3 必须以**节点内容与原文的直接核对**为主判据，evidence 只作提示。

**覆盖率口径也要注意**：`kept + dropped = 节点数` 说明 LLM 基本每条都给了 evidence；所以"覆盖率低"通常是**被校验拦掉**，而不是"LLM 没给"。这个区分靠 `add_conversation` 返回值里新增的 `evidence_stats` 才能看出来。

#### C2｜L1 自洽巡检（**不依赖原文，可先行**）

| # | 内容 |
|---|---|
| C2-1 | 目标：语义重复（`n1`≈`n3`）、重复 person（`n25`/`n27`）、长期孤立、互相矛盾 |
| C2-2 | 机制：向量近邻聚类出候选对 → 交 LLM 判定"是否同一事实" → 产出 `update` / `deprecate` 合并操作 |

**实测（0911）——实现上比原设计更保守：做成纯只读**

落地时把 C2 收敛成"**只发现候选，不下判断**"：不调 LLM、不写图，是否同一事实交给上层结合上下文判断，确认后用 `dba_intervene` 落盘。这样巡检工具本身是只读的，**从根本上不存在与检索的写冲突**（C2-4 的 dry-run 门槛、C2-5 的回滚前置因此都不再必要）。

- 新增纯计算模块 `dba_pipeline/graph/review.py`：`find_duplicate_candidates()`，O(n²·d)，按行分块避免大图一次性分配 n×n 矩阵。
- 新增工具 `dba_review_graph`（第 8 个工具），返回 `duplicate_candidates` / `isolated_nodes` / `scanned`。
- 并发：`_review_running` 非阻塞互斥；**持锁只取一次快照**（节点字段 + 向量缓存浅拷贝），随后放锁做纯计算（相似度是 O(n²)，持锁会阻塞检索）。

实测（群聊图，22 节点）：

```
造对 n21 / n22（第二次创建时 duplicate_warning=True）
scanned=22 候选对=1 孤立=2
  n21(status) ≈ n22(status)  sim=0.9821
体检未改图: True        ← 只读验证
```

**一个必须踩住的坑**：语义去重的第一版把长度门槛设成 8 字，结果候选表为空——中文没有词边界，「用户喜欢喝咖啡」只有 7 字却是正常事实。主防线改为**按类型排除 `thing`**（抽取侧的锚点都是 thing），长度门槛降到 4 只挡退化内容。

#### C3｜L2 溯源巡检（依赖 C1）

|---|---|
| C3-1 | 逐批输入：该批原文 + 该批产出的节点 |
| C3-2 | 问三件事：① 每条节点是否被原文支撑（抓幻觉/推测）；② 原文有无被漏掉的关键事实、**尤其是"为什么"**（抓漏抽）；③ 粒度是否正确（抓「过两天」这类相对表述独立成锚点） |
| C3-3 | 输出：`update`（改写内容）/ `deprecate`（撤销无据节点）/ `create`（补抽） |
| C3-4 | 强约束：只能基于原文事实，不得引入原文之外的信息 |

**实测（0911）**

新增工具 `dba_review_sources`（第 9 个工具）+ `SOURCE_AUDIT_PROMPT` / `InferenceEngine.audit_source()`。

并发同 C2：**持锁只做一次节点快照**（`source_ref == batch_id`），LLM 调用在锁外；只读 `sources/`、不写图谱。核对后由上层用 `dba_intervene` 落盘（无据节点 `deprecate`/`delete_node`，漏抽的 `create_node` 补）。

第一次跑就报了实打实的问题（群聊 18 节点）：

```
[无据] n11: 原文只说"明天发你"，且上一句发言人是小林，无法确定"你"就是老周；
          写成"发给老周"是额外指代推断。          ← 真正的过度推断
[漏抽] '你们看下有没有问题': 老周发排期后要求大家检查…未被抽取。
```

**但第一版判据踩了一个大坑**：`granularity` 报了 **7 条**，全是 `上周五/这周二/下周一/明天` 这类**具体时间词锚点**——而时间锚点正是本系统为时序检索刻意设计的（`TOOL_TIME_ANCHOR_RE` 白名单就是为识别它们）。**巡检把系统的既定设计判成了错误。**

修正后（明确列出"哪些不算粒度问题"）：

| 轮次 | granularity 条数 | 说明 |
|---|---|---|
| 第 1 版 | 7 | 全是时间锚点假阳性 |
| 排除"具体时间词"后 | 1 | 只剩「这两天」 |
| 再排除"已纳入时段映射的近期表述"后 | **0** | 假阳性清零 |

最终一轮：`summary = {'batches_checked': 1, 'unsupported': 0, 'missing': 1, 'granularity': 0}`。

**这条经验值得记住**：巡检 prompt 与抽取 prompt 是**两套价值判断**，必须显式对齐——否则巡检会把抽取侧"刻意为之"的设计（时间锚点、消解指代后的陈述）当成缺陷报出来，噪声会把真问题淹掉。

**与 txt 的对照**：txt L602（推测 `n22` 写成事实）与 L604（「过两天」被独立成节点）这两条原始抱怨，**已在稳定性测试的模拟数据集里成功复现，并被本巡检自动报出**——见 §九。

**召回率问题与修正（本轮最重要的调优）**

上面的判据调对之后，跑 3 轮稳定性测试发现：靶子**每轮都在**（`unlocatable_time_nodes=1`、`speculation_nodes=2~3` 恒定），但巡检只 **1/3 轮**报出来。查原因是 prompt 里那条纪律写反了：

```
- 拿不准时不要报，宁可漏报也不要误报；      ← 原始写法
```

这份报告的定位是**给人工/上层 agent 复核的线索**（只报不改），所以**漏报的代价高于误报**。改成：

```
- 逐条节点都要过一遍，不要跳读；发现可疑就报——
  这份报告是给人工/上层 agent 复核用的线索，漏报的代价高于误报。
  但每条都必须给出判断依据（why），好让复核者能快速否掉；
```

改后同数据集 3 轮：**`unsupported` 3/3 命中、`granularity` 3/3 命中**（之前各 1/3）。报出的理由也很到位，例如：

> 「原文是『反正应该是甲方那边催得紧』，用户自己用了『应该是』表示推测/不确定，
> 节点把这一推测写成了确定事实，丢掉了语气模态，属于把推测写成事实。」

> 「『过两天』是原文中无法定位到具体日期的模糊表述…且其内容与 n20 高度重叠，宜合并或只保留确定性侧的信息。」

**教训**：纪律条款要按工具的**定位**写——"只报不改"的复核工具该偏召回，"自动落盘"的工具才该偏精确。

## 七、风险与约束

| 风险 | 说明 | 应对 |
|---|---|---|
| **隐私** | 原文与 `evidence` 都是原始语料，oplog 已因同样原因被列入"脱敏 + 30 天清理" | 默认关；TTL + 脱敏；不进检索/叙事 |

## 八、决策记录与待确认事项

### 8.1 已定（0911）

| # | 决策 | 结论 |
|---|---|---|
| 1 | **C2 巡检的触发方式** | **两条腿**：① 显式 MCP 工具（`dba_review_graph` / `dba_review_sources`），由上层 agent 决定何时跑；② **空闲时段自动巡检**（0911 追加，见 §8.5）——原先担心的"无人在场周期烧 LLM"与"撞上正在运行的检索"，用**空闲阈值让路 + 工具级互斥 + 默认关闭**解决，而不是干脆不做定时。 |
| 2 | **抽取复现问题** | 接受"依赖 LLM、无法 100% 复现"。不追求可复现，改为**评测侧多次采样取中位数**（见 8.3）。 |

### 8.2 C2 的并发安全要求（由 8.1-1 引出，实现时必须满足）

现有锁结构：[`DBAServer._lock`](../dba_pipeline/mcp_server.py)（RLock，与 `GraphBuilder` 共享）只保护**写**；`dba_query_memory` / `dba_temporal_lookup` 是**读**路径且**不持锁**。因此巡检如果直接改图，会与正在跑的检索并发读写同一张图。要求：

1. **绝不长持锁**：巡检内部的 LLM 判定可能耗时数十秒到数分钟，**不能持锁跑**，否则会阻塞所有检索。
2. **两段式**：持锁取快照（复制节点/边/向量的只读视图）→ 放锁 → 离线判定 → 再对每个操作**单独持锁**执行。
3. **不直接改图，只产出建议**：落盘一律通过现有 `intervene`（已持锁、已写 oplog、可回滚），巡检工具本身不做图写入。
4. **工具级互斥**：巡检自身加 `_review_running` 标志，避免两个巡检并发产生重复建议。

### 8.3 验收方式调整（对应 8.1-2）

抽取不可复现（同一输入节点数 16~18 浮动）意味着**单次对比无法归因**。因此任务 A/B/C 的效果验证统一改为：

- 同一语料跑 **N=3 次**，取指标**中位数**，比较中位数差值而非单次输出；
- 长提示词会进一步放大波动（新增规则容易被既有规则淹没），所以**改动要小步**，一次只加一条规则；
- 不因"无法复现"而放弃验证——**多次采样本身就是为了绕开不可复现**，二者不冲突。

### 8.4 待确认

1. 任务 A 的承载方式：并入 `REASON`（扩展定义）／新增 `node_type`（会牵动 `jump_axis` 跳转权重表）／只加提示词。**默认按"并入 REASON"推进。**
2. C1 原文 TTL 取值，以及与 oplog 脱敏/清理策略是否合并实施。**默认：合并同一套、TTL 30 天、默认关闭原文持久化。**
3. 巡检结果 dry-run 后由谁确认落盘。**默认：上层 agent 看到报告后自行调用 `intervene` 落盘。**
4. `evidence` 是否需要在 MCP 检索结果中返回。**默认：不返回，仅 `inspect_graph` 可见。**

### 8.5 空闲时段自动巡检（0911 追加）

**动机**：`dba_review_graph` / `dba_review_sources` 原先是纯被动工具——只有上层 agent 主动调用才会跑，而 agent 只在"用户说了话"之后才有机会调工具。也就是说巡检永远发生在**刚被使用过**的时刻，既不是空闲时段，也可能与正在跑的检索/维护抢资源。

**落地**：新增 `dba_pipeline/extraction/review_scheduler.py`（`IdleReviewScheduler`），在 `mcp_server.main()` 里启动，默认**关闭**。

五条并发/让路保护：

| # | 保护 | 实现 |
|---|---|---|
| 1 | 不抢占在线请求 | 距最后一次活动超过 `idle_seconds` 才启动（`server.is_idle()`） |
| 2 | **一有人来就让路** | 逐批核对（`review_sources` 会调 LLM）之间复查 `last_activity()`；出现新活动即**中止并丢弃结果、不落盘**（半截报告会误导），等下次空闲重来 |
| 3 | 不重叠 | 复用 `server._review_running` **非阻塞**互斥：手动调用与自动巡检互相排斥，拿不到就直接跳过、不排队。该锁改为 **RLock**——调度器整轮持锁、内部又调 `review_graph()`（它自己也会取同一把锁），同线程重入必须放行；跨线程仍互斥 |
| 4 | 不与 DBA 维护撞车 | `ReviewConfig.from_env()` 强制 `idle_seconds > maintenance_idle_timeout`，过小则提升到 `idle_timeout + 60` 并告警 |
| 5 | 不写图 | 只读 `review_*`，报告原子落盘到 `<图谱目录>/reviews/review-<时间戳>-<触发>.json`，保留最近 20 份；落盘一律仍由上层用 `dba_intervene` |

**活动追踪**：`DBAServer.touch()` / `last_activity()` / `idle_seconds()` / `is_idle()`；`handle_call_tool` 的 dispatch 层对**所有**工具统一 `touch()`，因此巡检自己跑完也会重新计时（天然自我节流，不会连轴转）。

**配置**（默认关闭，属部署决策——自动巡检会消耗 LLM 额度）：

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `ARIADNE_REVIEW_IDLE` | 未设 | 距最后活动多少秒算空闲；**未设 = 不启动**；非法/≤0 也视为关闭 |
| `ARIADNE_REVIEW_INTERVAL` | 1800 | 两次自动巡检的最小间隔（秒），下限 60 |
| `ARIADNE_REVIEW_SOURCES` | 3 | 单次最多核对多少批原文；**0 = 只做确定性体检**，不调 LLM |

**验证**：`eval/test_review_scheduler.py`（确定性、不调 LLM）——配置解析 / 活动追踪 / 正常巡检（只读+落盘）/ 中途让路（核对 1 批后中止、未落盘、锁已释放）/ 工具级互斥 / 触发条件 / 报告轮转 / 后台线程生命周期，**8 段全通过**。

⚠️ 尚未做：接入真实 MCP 进程的端到端验证（起进程 → 等空闲 → 确认自动产出报告 → 期间调工具确认让路）。

## 九、完整管线稳定性测试（0911）

脚本：`eval/test_pipeline_stability.py`（`STAB_ROUNDS` 控制轮数，默认 6）。

分两段：**⓪ 确定性批量用例**（不调 LLM、秒级、可上千例）+ **①  LLM 轮次**（跑完整链路）。

### 9.1 ⓪ 确定性批量用例（161 例）

覆盖本轮所有非 LLM 的修复点：时期词分类（每词两断言）、锚点-事实一致性的时间跨度边界、
显式词硬校验的周X精确化、`evidence` 子串校验、语义去重的阈值与排除规则、标识脱敏。

**第一次跑就抓出 2 个真 bug**（另 3 例是测试自身的期望写错）：

| # | Bug | 根因 | 修法 |
|---|---|---|---|
| 1 | 锚点-事实一致性**误报冲突** | 用**集合交集**比较时期字面：锚点「那天」的可接受集含裸词「上周」，而事实写的是「上周三」——集合不交，被判为冲突 | 改为三层判断：字面交集 → **锚点可接受串出现在事实文本里** → 才是显式冲突 |
| 2 | 人生阶段词**跨学段误配** | 用一张"全部阶段词"平表做可接受集，「大二」能匹配到「高一」 | 按学段**分族**：高中族 / 大学族 / 大专族，只允许族内匹配 |

修后 161 例全过。**这两条都是纯逻辑缺陷，靠端到端跑很难发现——正是确定性大样本的价值。**

### 9.2 ① LLM 轮次（6 轮）

| S2 | 决策取舍（两个被放弃方案 + 自述依据） | 任务 A |

| S4 | 与既有节点近重复 | 任务 D 去重提示 / 任务 C2 体检 |

**6 轮结果**

| `placeholder_user`（绝对代称「用户」） | 0 / 0 / 0 | ✅ 6/6 |
| `speakers_hit`（昵称归属） | 3 / 3 / 3 | ✅ 6/6 |
| `abandoned_hit` / `rationale_hit` | 3/3/3、4/4/4 | ✅ 6/6 |
| `reload_lost`（timestamp/evidence/source_ref） | 0 / 0 / 0（三项全 0） | ✅ 6/6 |
| `tl_types`（时序三档） | exact / rejected / fuzzy 全轮一致 | ✅ 6/6 |
| `rg_found_pair` / `dup_warning` | True 全轮 | ✅ 6/6 |
| **C3 `unsupported` 命中** | ≥1 每轮 | ✅ **6/6** |
| **C3 `granularity` 命中（「过两天」）** | =1 每轮 | ✅ **6/6** |
| `S1_nodes` | 11 / 12 / 12 | ⚠️ 抽取波动 |
| `anchors` | 5 / 5.5 / 6 | ⚠️ 同上 |
| `reason`（任务 A 产出） | 4 / 5 / 6 | ⚠️ 同上 |
| `evidence` 合规率 | **46% / 75% / 100%** | ⚠️ 见下 |

`hard_fail_free = 6/6`。

### 9.3 结论

1. **确定性部分完全可靠**：归属零塌缩、三个扩展字段落盘/重载零丢失、时序三档契约、只读巡检不写图、去重提示与体检命中，**6 轮 6/6 无硬失败**。
2. **C3 召回稳定**：纪律从"宁可漏报"改成"发现可疑就报"后，`unsupported` 与 `granularity` 都是 **6/6**（修正前各 1/3）。txt L602 / L604 两个原始抱怨在每轮都被自动抓出。
3. ⚠️ **`evidence` 合规率区间被放大到 46%~100%**（3 轮时看着是 63%~67%，样本加倍后露出真实宽度）。**再次确认：`evidence` 只能作提示，绝不能当判据**——C3 必须以"内容 vs 原文直接核对"为主。
4. **节点级指标是 LLM 抽取的固有波动**（节点数 11~12、锚点 5~6、REASON 4~6），判断"是否劣化"必须比**中位数**、不看单轮（即 §8.3 的采样口径）。
5. **测试策略的验证**：把"能大批量跑"的部分从 LLM 链路里剥出来做成 161 例确定性用例，用秒级成本抓到了 2 个纯逻辑 bug——**端到端跑 N 轮是发现不了这种问题的**。后续新增规则时，应优先补确定性用例。

### 10.5 关键发现：C3 召回 0 ≠ LLM 没操作

先厘清语义（`InferenceEngine.audit_source` 的契约）：

- **没调用** → `review_sources` 会在最前面返回 `{"error": "未开启原文存储…"}` / "检索链路未初始化"，根本没有 `batches`；
- **正常调用** → 返回 `{"unsupported": [...], "missing": [...], "granularity": [...]}`，**空列表 = LLM 逐条核对后认为没问题**；
- **解析失败** → 返回 `{"error": "JSON 解析失败", "raw": …}`。

所以 `unsupported=0` 的正常含义是"这批节点都能被原文支撑"，**不是"没操作"**——抽取若把推测保留了"可能/估计"这类限定口吻，节点本身与原文一致，本来就没有无据节点可报。

三次独立构建中，`unsupported` 观察值为 **1 / 0 / 1**，`granularity` 为 **1 / 1 / 0**。这与 §9.2 的"6/6"**不矛盾**：§9.2 是 6 轮采样里每轮都命中；单轮采样不足支撑硬断言，故 e2e 把召回列为**软观测**（与 §8.3 采样口径一致）。

⚠️ **但这里暴露过一个真实歧义**：`review_sources` 的汇总用 `len(r.get("unsupported") or [])`，当某批返回 `{"error": …}` 时同样计 0——会把"解析失败"伪装成"没发现问题"。e2e 已补一条**硬不变量**堵住它：逐批检查 `b.get("error")`，有即失败。于是 C3 在 e2e 里的硬不变量是三条：**工具可用 + 只读 + 完成原文↔节点联结（`audited_nodes` > 0）且无逐批解析失败**。

⚠️ 复现这条链路的成本：3 段抽取 + 1 次溯源 + 3 查询 × 3 轮 ×（故事化 + 回复 + 判分）≈ 30+ 次 LLM 调用，属**重量级**测试，不宜进 CI 快跑；日常回归用 `eval/test_review_scheduler.py`（8 段，秒级）与 `STAB_ROUNDS=0 python -m eval.test_pipeline_stability`（161 例，秒级）。

## 十一、C3 准确性基准（0912，扩大样本）

e2e 只能给出"C3 报了几条"，给不出"报得准不准"——因为它没有 ground truth，分不清 0 是"判断干净"还是"漏报"。为此新增 **`eval/test_c3_audit_accuracy.py`**：手工标注用例，逐节点给标签，直接量 precision / recall。

### 11.1 方法

- **14 个用例 / 37 个节点**：28 个 `clean`（不该被报）+ 9 个预置问题（6 个 unsupported、3 个 granularity）；
- 负例里埋了四类**陷阱**：保留限定口吻的推测（「可能请两天假」）、允许的代指消解/补全省略、具体时间锚点（「上周五」「明天」）、已纳入映射的近期表述（「前几天」「这两天」）——考的就是"判断无误"（不误报）；
- 每用例跑 **5 轮**（共 70 次 `audit_source`），按节点 id **精确匹配**；**类别错放也算错**（标 unsupported 却报 granularity → 前者记 FN、后者记 FP）；
- `missing` 只测召回（"原文还有什么该抽没抽"是开放集，算不了精确率）。脚本 `C3_ROUNDS` 控制轮数。

### 11.2 结果（70 次核对）

| 类别 | TP | FP | FN | Precision | Recall | F1 |
|---|---|---|---|---|---|---|
| unsupported | 30 | 1 | 0 | **0.968** | **1.000** | **0.984** |
| granularity | 14 | 5 | 1 | 0.737 | 0.933 | 0.824 |

- **干净节点误报率 5/140 = 0.036**（且 5 次全集中在同一个陷阱，见下）
- **`missing` 召回 10/10 = 1.000**（"为什么"类：`预算/成本`、`品牌/升级` 每轮都被抓出）
- 解析失败 0/70；**跨轮结果稳定 13/14** 个用例

### 11.3 结论

1. **"判断有误"（抓真问题）几乎满分**：unsupported 召回 **30/30**——把推测写成事实（c1）、凭空补信息（c2）、过度概括（c3）、未发生写成已发生（c11）、编造冲突（c12）**每轮全中**，且 13/14 用例跨轮稳定。
2. **"判断无误"（不误报）也站得住**：干净节点误报率 3.6%，远低于 §10 设的 0.2 警戒线；陷阱负例 c5/c7/c8（代指消解、具体锚点、近期表述）**零误报**。
3. **唯一系统性误报：`c4` 的「下周」被报 granularity（5/5 全轮）**。prompt 明文列了「上周五/这周二/下周一/明天」不许报，但**没列裸周/裸月**；而按系统设计「下周」是 `_EXPLICIT_PERIOD_RE` 认的显式时段锚点，不该被劝删。→ 已修（并由词扫描发现同类共 12 个词），见 §11.4–11.5。
4. **弱项是 granularity，不是 unsupported**：除「下周」外，`c9`（多事合并）5 轮中 4 轮报对、1 轮报成 unsupported（类别错）、1 轮漏——granularity 的**边界判断**比 unsupported 难，符合预期。

### 11.4 时间词扫描：还有哪些"没写进清单却被误报"的词

只修「下周」是治标——**清单式写法必然打地鼠**。于是给基准加一段**词扫描**：把 65 个时间词各自独立成 `thing` 节点，跑 3 轮，看哪些被报。

**ground truth 不手写，直接取自检索侧词表**（显式 / 模糊映射 / 人生阶段 / 仅锚点 = 该 clean；系统完全不认识的 = 该报 granularity），与 §T1 单一来源原则一致，避免判据漂移。

改「下周」之前扫出的偏差：

| 词 | 误报轮数 | 所属类别 |
|---|---|---|
| 后来 / 之后 / 最近 / 近来 / 这段时间 / 那段时间 / 近年来 | 3/3 | 模糊映射 / 仅锚点 |
| 当时 | 2/3 | 模糊映射 |
| 那天 / 当天 / 毕业 / 入职 | 1/3 | 模糊映射 / 仅锚点 |

漏报 0 个。**12 个词全被误报，且全不在原清单里**；而清单里列了的那几个（前几天/前两天/这两天/这几天）**零误报**——证明"列出即不报"，也证明靠列举补不完。

### 11.5 改动与三轮验证

| 版本 | unsupported F1 | granularity P / R / F1 | 干净误报率 | 词扫描 |
|---|---|---|---|---|
| 原始 | 0.984 | 0.737 / 0.933 / 0.824 | 5/140 = 0.036 | — |
| ① 补「裸周/裸月/裸年」 | 0.984 | 0.933 / 0.933 / **0.933** | 1/140 = 0.007 | **误报 12 词**，漏报 0 |
| ② 改封闭集（措辞越界） | 0.938 ↓ | 1.000 / 0.733 / 0.846 ↓ | 0/140 = 0.000 | 误报 0，**漏报 3 词** |
| ③ **限定作用域 + 补齐封闭集** | 0.984 | 0.933 / 0.933 / **0.933** | 1/140 = 0.007 | **误报 0，漏报 0** |

改动 ② 的教训：把"除第一类词外，任何时间表述一律不要报"写成**无限定语**，连"多件事件合并成一条"那条也一起压住了——`c9` 从"报对 granularity 4/5"退化成"4/5 报成 unsupported"，召回掉到 0.733。**排除规则必须限定作用域**，否则会误伤同类的另一条判据。

最终版（③）把 `SOURCE_AUDIT_PROMPT` 的 granularity 规则改成：

1. **该报的做成封闭枚举**（小而有限，适合穷举）：「过两天/过几天/过些天/过阵子/回头/改天/以后/晚点/有空/再说/将来」；
2. **该不报的用通则**（开放集，无法穷举）：「除第一类词外，任何时间表述单独成节点都不算粒度问题」，再补一份"包括但不限于"的示例；
3. 并明确声明**该限定只作用于第一类**，"多件事合并"那条该报照报。

**结论：这三处改动是纯改善**——granularity F1 0.824 → 0.933、干净误报率 3.6% → 0.7%、unsupported 与 missing 召回不变、词扫描偏差归零。按"若无大影响直接改即可"已保留。

⚠️ 词扫描的 `C-无法定位` 组是**对照组**：它保证"收紧排除清单"没有变成"干脆不报 granularity"——最终版 10 个词全报、0 漏。
