# 巡检自动化 · 记忆保真 e2e · C3 准确性报告（0912）

> 范围：MCP 链路（ALM 侧未改动）。承接 [0911 计划](./0911——记忆保真计划（Source层与决策理由）.md) 的 A/B/C1/C2/C3/D 六项，本文汇总其后的三块工作：**巡检工具自动化**、**全链路 e2e**、**C3 准确性基准与 prompt 修正**。
> 一句话结论：巡检从"被动等人调"变成"空闲自动跑且绝不抢在线请求"；全链 e2e 跑通（总均分 4.80），**决策理由首次在回复层被观测到**；C3 的判对/判错首次被量化，并据数据修 prompt，把 granularity F1 从 0.824 提到 0.933、干净节点误报率从 3.6% 压到 0.7%。

## 一、巡检工具自动化（离线空闲检测 + 并发保护）

### 1.1 问题

`dba_review_graph` / `dba_review_sources` 原先是**纯被动工具**——只有上层 agent 主动调用才会跑，而 agent 只在"用户说了话"之后才有机会调工具。于是巡检永远发生在**刚被使用过**的时刻：既不是空闲时段，也可能与正在跑的检索/维护抢资源。

### 1.2 落地

新增 [review_scheduler.py](../dba_pipeline/extraction/review_scheduler.py)（`IdleReviewScheduler`），在 [mcp_server.py](../dba_pipeline/mcp_server.py) 的 `main()` 中启动，**默认关闭**。

五条并发/让路保护：

| # | 保护 | 实现 |
|---|---|---|
| 1 | 不抢占在线请求 | 距最后一次活动超过 `idle_seconds` 才启动（`server.is_idle()`） |
| 2 | **一有人来就让路** | 逐批核对（`review_sources` 会调 LLM）之间复查 `last_activity()`；出现新活动即**中止并丢弃结果、不落盘**，等下次空闲重来 |
| 3 | 不重叠 | 复用 `server._review_running` **非阻塞**互斥：手动调用与自动巡检互相排斥，拿不到直接跳过、不排队 |
| 4 | 不与 DBA 维护撞车 | `ReviewConfig.from_env()` 强制 `idle_seconds > maintenance_idle_timeout`，过小则提升到 `idle_timeout + 60` 并告警 |
| 5 | 不写图 | 只读 `review_*`，报告原子落盘到 `<图谱目录>/reviews/review-<时间戳>-<触发>.json`，保留最近 20 份 |

**活动追踪**：`DBAServer.touch()` / `last_activity()` / `idle_seconds()` / `is_idle()`；`handle_call_tool` 的 dispatch 层对**所有**工具统一 `touch()`，因此巡检自己跑完也会重新计时（天然自我节流）。

**配置**（默认关闭属部署决策——自动巡检会消耗 LLM 额度）：

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `ARIADNE_REVIEW_IDLE` | 未设 | 距最后活动多少秒算空闲；未设 = 不启动；非法/≤0 也视为关闭 |
| `ARIADNE_REVIEW_INTERVAL` | 1800 | 两次自动巡检的最小间隔（秒），下限 60 |
| `ARIADNE_REVIEW_SOURCES` | 3 | 单次最多核对多少批原文；0 = 只做确定性体检，不调 LLM |

### 1.3 核验时抓出的一个真 bug（已修）

调度器**整轮持锁**后再调用 `review_graph()`，而后者[自己也取同一把锁](../dba_pipeline/mcp_server.py)。`threading.Lock` 同线程重入返回 `False` → 体检结果被**静默替换成 `{"error": "已有一次巡检正在进行"}`**，自动巡检的图谱体检等于白跑。

- **修复**：`_review_running` 由 `Lock` 改为 **`RLock`**（同线程重入放行，跨线程仍互斥）。
- **测试为何漏过**：原断言只写 `report["graph"] is not None`，而错误字典也不是 `None`。已改为断言 `"error" not in report["graph"]` 且 `scanned == 2`。
- **反向验证**：临时换回 `Lock` 跑测试，精准报出 `✗ 体检不该因重入而报错: {'error': ...}`，证明新断言有效（不是空断言）。
- 附带：`RLock` 在 Python<3.14 没有 `locked()`，测试改用 `acquire(blocking=False)` 判断锁是否已释放。

### 1.4 验证

```
python -m eval.test_review_scheduler
→ ① 配置解析 ② 活动追踪 ③ 正常巡检(只读+落盘) ④ 中途让路 ⑤ 工具级互斥
   ⑥ 触发条件 ⑦ 报告轮转 ⑧ 后台线程生命周期      8 段全通过（不调 LLM，秒级）
```

## 二、记忆保真 e2e

### 2.1 与既有 e2e 的分工

| | 图从哪来 | 覆盖的链路 |
|---|---|---|
| [smoke_run_e2e.py](../eval/smoke_run_e2e.py) | **预置图谱** `smoke_companion.yaml` | 检索 → 故事化 → 回复 → 判分（只是后半段） |
| [test_memory_fidelity_e2e.py](../eval/test_memory_fidelity_e2e.py) | **原始对话现跑抽取** | 抽取(A/B/C1) → 贯通 → 巡检(C2/C3) → 检索 → 回复 → 判分（全链） |

本轮六项优化全在**抽取侧**，用预置图谱测不到，所以 e2e 必须从原始对话起跑。回复/判分链路直接 `import` 自 `smoke_run_e2e`，不重复维护两套 prompt。

### 2.2 数据集（自建 · 可复用）

三段时间对话，每段对应本轮一个优化点（`DATASET[...]["target"]` 已标注）：

| 段 | 内容 | 靶子 |
|---|---|---|
| s1 | 3 人群聊（带昵称）+ 具体日期词 + 手机号/邮箱 | 说话人归属 / 时间锚点 / 脱敏 |
| s2 | 选服务器方案的取舍（弃「直接上云」与「自建机房」+ 自述依据） | 任务 A（决策理由）+ 任务 B（evidence） |
| s3 | 全是推测口吻 + 「过两天」 | 任务 C3 的 unsupported / granularity |

查询 3 条：q1「当初为什么没直接上云？」（任务 A 的**价值闭环**）、q2 陪伴倾诉、q3 事件追问。

### 2.3 断言分两层

- **硬失败**（确定性不变量，任一不满足即 exit 1）：昵称归属（绝对代称「用户」= 0、3/3 命中）、REASON 节点存在且被放弃选项/依据进入内容、`evidence_stats` 非空、`source_ref` 覆盖 > 0、重载三字段零丢失、原文落盘已脱敏、C2 体检命中人工注入的重复对且不改图、C3 巡检**可用 + 只读 + `audited_nodes` > 0 且无逐批解析失败**、时序 exact 命中与不存在日期拒答、q1 故事同时带回「依据」与「被放弃选项」。
- **软观测**（依赖 LLM，只看多次采样中位数）：judge 判分均值、`evidence` 合规率、C3 的 `unsupported`/`granularity` 召回、批次节点数。

### 2.4 3 轮结果

```
抽取  s1_nodes 13  s2_nodes 6  s3_nodes 5
      placeholder_user=0   speakers_hit=3/3
      reason_nodes=5  abandoned_hit=2  rationale_hit=3
      source_ref_cov=24   evidence kept/dropped = 9/5, 6/0, 4/1
贯通  reload_lost {timestamp:0, evidence:0, source_ref:0}   source_redacted=True
巡检  rg_found_pair=True（只报 1 对，无噪声）  dup_warning=True
      rs_audited_n=5  rs_summary{unsupported:1, missing:1}
时序  tl_exact_type=exact   tl_absent_rejected=True
回复  q1 mean=5.0 (rationale✓ abandoned✓) / q2 4.53 / q3 4.87   总均分 4.80
```

**任务 A 的价值首次在回复层被观测到**：q1 三轮回复都在复述「预算砍了一半 → 云成本太高 → 自建又要自己运维」——正是外部反馈里"当初为什么做某个选择基本会丢失"要补的那一块。

### 2.5 两个副产物

1. **C3 召回不能做单轮硬断言**：三次独立构建中 `unsupported` 观察值为 1/0/1、`granularity` 为 1/1/0。且 `0` 的正常含义是"LLM 核对后认为没问题"，**不是"没操作"**（`audit_source` 的契约：没调用→无 `batches`；正常调用→空列表=判断干净；解析失败→`{"error": "JSON 解析失败"}`）。
2. **发现一处真实歧义并堵住**：`review_sources` 的汇总用 `len(r.get("unsupported") or [])`，某批返回 `{"error": …}` 时**同样计 0**——会把"解析失败"伪装成"没发现问题"。e2e 已补硬不变量：逐批检查 `b.get("error")`，有即失败。

## 三、C3 准确性基准与 prompt 修正

e2e 只能给出"C3 报了几条"，给不出"报得准不准"——它没有 ground truth。为此新增 [test_c3_audit_accuracy.py](../eval/test_c3_audit_accuracy.py)。

### 3.1 方法

- **14 个用例 / 37 个节点**：28 个 `clean`（不该被报）+ 9 个预置问题（6 unsupported、3 granularity）；
- 负例里埋四类**陷阱**：保留限定口吻的推测（「可能请两天假」）、允许的代指消解/补全省略、具体时间锚点（「上周五」「明天」）、已纳入映射的近期表述（「前几天」「这两天」）——考"判断无误"；
- 每用例 5 轮（共 70 次 `audit_source`），按节点 id **精确匹配**；**类别错放也算错**（标 unsupported 却报 granularity → 前者记 FN、后者记 FP）；
- `missing` 只测召回（"原文还有什么该抽没抽"是开放集，算不了精确率）。

### 3.2 初测结果（原始 prompt）

| 类别 | TP | FP | FN | Precision | Recall | F1 |
|---|---|---|---|---|---|---|
| unsupported | 30 | 1 | 0 | 0.968 | **1.000** | 0.984 |
| granularity | 14 | 5 | 1 | 0.737 | 0.933 | 0.824 |

干净节点误报率 5/140 = 3.6%；`missing` 召回 10/10；解析失败 0/70；跨轮稳定 13/14。

**"抓真问题"几乎满分**：推测写成事实、凭空补信息、过度概括、未发生写成已发生、编造冲突五类**每轮全中**。唯一系统性误报是「下周」被报 granularity（5/5 全轮）——prompt 明文列了「上周五/下周一/明天」不许报，却没列**裸周/裸月**。

### 3.3 词扫描：还有哪些"没写进清单却被误报"的词

只修「下周」是治标。给基准加一段**词扫描**：65 个时间词各自独立成 `thing` 节点跑 3 轮。**ground truth 不手写，直接取自检索侧词表**（显式 / 模糊映射 / 人生阶段 / 仅锚点 = 该 clean；系统完全不认识的 = 该报），与单一来源原则一致。

扫描结果：**误报 12 个词，漏报 0 个**。

| 词 | 误报轮数 | 类别 |
|---|---|---|
| 后来 / 之后 / 最近 / 近来 / 这段时间 / 那段时间 / 近年来 | 3/3 | 模糊映射 / 仅锚点 |
| 当时 | 2/3 | 模糊映射 |
| 那天 / 当天 / 毕业 / 入职 | 1/3 | 模糊映射 / 仅锚点 |

清单里**列了的**那几个（前几天/前两天/这两天/这几天）**零误报**，没列的全中招 → 根因是**清单式写法必然打地鼠**，补词补不完。

### 3.4 三轮改动与验证

| 版本 | unsupported F1 | granularity P / R / F1 | 干净误报率 | 词扫描 |
|---|---|---|---|---|
| 原始 | 0.984 | 0.737 / 0.933 / 0.824 | 5/140 = 3.6% | — |
| ① 补「裸周/裸月/裸年」 | 0.984 | 0.933 / 0.933 / 0.933 | 1/140 = 0.7% | 误报 12 词，漏报 0 |
| ② 改封闭集（措辞越界） | 0.938 ↓ | 1.000 / 0.733 / 0.846 ↓ | 0/140 = 0.0% | 误报 0，**漏报 3 词** |
| ③ **限定作用域 + 补齐封闭集** | 0.984 | 0.933 / 0.933 / **0.933** | 1/140 = 0.7% | **误报 0，漏报 0** |

改动 ② 的教训值得记：把"除第一类词外，任何时间表述一律不要报"写成**无限定语**，连"多件事件合并成一条"那条也一起压住了——`c9` 从"报对 granularity 4/5"退化成"4/5 报成 unsupported"，召回掉到 0.733。**排除规则必须声明作用域**，否则会误伤同一类目下的另一条判据。

### 3.5 最终 prompt 规则

[SOURCE_AUDIT_PROMPT](../dba_pipeline/llm/inference.py) 的 granularity 规则改为三段式：

1. **该报的做封闭枚举**（小而有限，可穷举）：「过两天/过几天/过些天/过阵子/回头/改天/以后/晚点/有空/再说/将来」；
2. **该不报的用通则**（开放集，无法穷举）：「除第一类词外，任何时间表述单独成节点都不算粒度问题」，再附"包括但不限于"的示例（具体日期、裸周/裸月/裸年/学期、模糊映射词、仅锚点词）；
3. **显式声明该限定只作用于第一类**，"多件事合并"那条该报照报。

**结论：纯改善**——granularity F1 0.824 → 0.933、干净误报率 3.6% → 0.7%、unsupported 与 missing 召回不变、词扫描偏差归零。

对照组（`C-无法定位` 组 10 个词）全报、0 漏，保证"收紧排除清单"没有变成"干脆不报 granularity"。
