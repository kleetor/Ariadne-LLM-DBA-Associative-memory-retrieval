# ALM 压测报告（0915）

> 目的：在主办方给出的正式评测口径下（Add 并发 16–64 / Search 并发 16–256 / 请求超时 1200s），
> 验证 ALM 服务能否承载，并给出并发—延迟—成本三者随规模变化的趋势结论。
>
> 工具：[alm/loadtest.py](../alm/loadtest.py)；口径与设计见 [0910——ALM测评接入计划.md](0910——ALM测评接入计划.md) §7.5。
> 原始报告：`eval/outputs/alm_lt_*.json`、`eval/outputs/alm_loadtest_*.json`。

---

## 一、结论摘要

1. **服务端不是瓶颈**。并发从 4 提到 64（16 倍）时，Add 的 p50 只从 7.63s 升到 11.64s（+53%），
   Search 的 p50 从 4.19s 升到 5.98s（+43%）。延迟增长远慢于并发增长，说明排队主要发生在
   上游模型吞吐，而非本服务的锁、落盘或注册表。
2. **超时余量充足**。全程最差一次请求 83.31s（混合并发下的 Add），相对平台 1200s 超时仍有
   **14 倍以上**余量；各阶段 p99 均 ≤ 41.5s（余量 ≈ 29 倍）。
3. **正确性不变量零失败**：跨 user 隔离、Add→Search 可检索性、`data` 结构、`top_k` 上限
   在全部 300+ 次请求中无一违反。
4. **成本可线性预测**：Add ≈ **$1 / 1000 次**、Search ≈ **$0.64 / 1000 次**（按 **gpt-4o-mini 官方价目表**折算 ——
   `alm/tokens.py` 的默认单价），与并发无关；本机全量 749 次 LLM 调用共 ≈ $0.24。
   注：本系统实际部署**不使用** gpt-4o-mini（工业榜对 Add / Search 使用的模型无限制），
   换用其它供应商时必须用 `ALM_PRICE_INPUT_PER_M` / `ALM_PRICE_OUTPUT_PER_M` 覆盖单价，
   否则按 gpt-4o-mini 价目表折算的金额会失真。
5. **两类问题需要处理**：一是压测中抓到一次 LLM 客户端解析层的 500（0.8%，非本服务的图竞态）；
   二是弃权阈值对短问句过于激进（8/8 弃权），直接影响 A 维度得分。

## 三、实测数据

### 3.1 单并发基线（users=8，探针修正后）

| 阶段 | 并发 | 次数 | 失败 | p50 | p95 | max | 单次响应内容峰值 |
|---|---|---|---|---|---|---|---|
| read | 8 | 8 | 0 | 4.19s | 7.34s | 7.34s | 128 字符 |
| churn（重读） | 4 | 4 | 0 | 4.85s | 5.48s | 5.48s | 147 字符 |

### 3.2 中高并发（users=64）

| 阶段 | 并发 | 次数 | 失败 | p50 | p95 | p99 | max | 墙钟 | 吞吐 |
|---|---|---|---|---|---|---|---|---|---|
| write（Add） | 64 | 64 | 0 | 11.64s | 24.96s | 29.11s | 30.85s | 30.9s | 2.07/s |
| read（Search） | 64 | 64 | 0 | 5.98s | 23.48s | 25.09s | 41.47s | 41.6s | 1.54/s |
| **mixed（同 user Add+Search）** | 64 | 128 | **1** | add 12.22 / search 8.08 | 29.32 / 11.24 | 32.68 / 24.42 | 83.31 / 25.12 | 83.3s | 1.54/s |

### 3.3 并发—延迟趋势

| 操作 | 并发 4–8（p50） | 并发 64（p50） | 变化 | 并发倍数 |
|---|---|---|---|---|
| Add | 7.63s | 11.64s | **+53%** | 16× |
| Search | 4.19s | 5.98s | **+43%** | 8× |

- Add：吞吐由 0.25/s（并发 4）升到 2.07/s（并发 64），**8.3 倍**。接近线性，服务端无明显串行点。
- Search：吞吐由 1.10/s（并发 8）升到 1.54/s（并发 64），仅 **1.4 倍** —— 已接近饱和。
  结合本机 CPU 向量化的事实，饱和点大概率来自 embedding 而非 LLM 或服务端；换 API embedding
  后这一项需要重测。
- 长尾：Search 的 p95（23.48s）显著高于 p50（5.98s），是排队效应；但 max 41.47s 仍远低于超时线。

## 四、过程中修掉/发现的问题

### 4.1 已修：Search 白跑一次 LLM 回复生成

[alm/space.py](../alm/space.py) 调 `retrieve_with_story` 时未传 `with_response`，默认 `True`
会触发一次 `generate_response`，而该产物在 ALM 侧从不被读取。

**改动**：显式传 `with_response=False`。
**验证**：Search p50 由 §6.2 记录的 8.0s 降到 4.19s（差 ≈ 3.8s ≈ 一次 LLM 调用），与预期一致。
**附带收益**：同时避开了「Search 阶段生成最终答案」的合规灰区。

### 4.2 发现：弃权阈值对短问句过于激进（影响 A 维度）

压测探针最初用「我叫什么名字？」，**8/8 全部返回空数组**。服务端日志显示不是丢数据：

```
alm.space: 空间 eval***0000 弃权: 最高余弦 0.2307 < 阈值 0.5200
```

节点 `用户叫李000` 确实在库里，但与短问句的余弦只有 **0.23–0.41**，全部低于 `ALM_ABSTAIN_COS=0.52`。
改为「我叫李xxx，我在{city}做什么工作？」后 8/8 命中。

→ `ALM_ABSTAIN_COS` 是「过度弃权伤 A」的直接开关。0.52 由自建 comprehensive 数据集标定，
**接入正式数据前必须重标定**（呼应计划 §6.4 待办 4）。

### 4.3 发现：一次 LLM 客户端解析层的 500（0.8%）

混合并发阶段 128 次请求中出现 1 次 500：

```
{"detail":{"reason":"内部错误: AttributeError: 'NoneType' object has no attribute 'model_dump'"}}
```

调用栈：

```
alm/space.py:174 add → dba.py:419 maintain → dba.py:617 _should_maintain
→ langchain invoke → langchain_openai/chat_models/base.py:1763 _create_chat_result
```

根因定位（读 langchain-openai 源码）：`_generate` 先 `self.client.with_raw_response.create(**payload)`
拿到原始响应，再 `response = raw_response.parse()` —— **这次 `parse()` 返回了 None**，
于是 `_create_chat_result(None)` 炸在 `response.model_dump()`。中间没有异常抛出，因此：

- SDK 自带的 `max_retries` 不生效（没有异常可重试）；
- 也无法被 `except openai.APIError` 捕获，最终以语义错位的 `AttributeError` 冒到接口层。

**重要区分：这不是 §7.3-2 的图读写竞态**——`add` 持锁改图 / `search` 不持锁读图的那条路径上
networkx 未报任何异常，失败发生在 `maintain` 内部的 triage LLM 调用上。同一批 64 并发 Add
（write 阶段）为零失败，说明它是上游偶发返回了「解析为 null 的响应体」。

现状：平台对 5xx 有有限次重试，0.8% 不致命，但会消耗重试配额。是否加固见 §六。

## 五、token 用量与成本

计量实现：[alm/tokens.py](../alm/tokens.py)（`TokenMeter` 挂在共享 LLM 实例上，覆盖 Add / Search
全部调用点），每次调用打一行 INFO，进程退出时打印汇总。

| 项 | 值 |
|---|---|
| 本机累计调用 | 749 次 |
| input | 468,519 tokens |
| output | 277,079 tokens |
| 折算成本 | ≈ **$0.24**（gpt-4o-mini 价目表：input $0.15/M、output $0.60/M） |

**单位成本**（由首轮 12 Add / 16 Search 的干净样本推出，与并发无关）：

| 操作 | LLM 调用数 | input | output | 成本 | 折算 |
|---|---|---|---|---|---|
| Add（一次维护） | 3（triage + 抽节点 + 连边） | ≈1,777 | ≈1,160 | ≈$0.00096 | **≈ $1 / 1000 次** |
| Search | 2（目的推断 + 记忆整理） | ≈1,185 | ≈773 | ≈$0.00064 | **≈ $0.64 / 1000 次** |

调用次数与推算完全吻合：12×3 + 16×2 = 68 次，实测正好 68 次。

**外推**：若正式数据集为 5,000 次 Add + 5,000 次 Search，LLM 成本约 **$8**；按本机观测的吞吐
（并发 64 下 Add 2.07/s、Search 1.54/s，且本机 embedding 偏悲观），单轮全量的墙钟时长在小时量级，
相对平台 6h（普通）/ 72h（full）的总超时有充足余量。

> 注：以上只含 LLM。API embedding 另计（按 token 计价，与 LLM 是两套账），本地 embedding 则为零边际成本。

## 六、未覆盖项与后续建议

| # | 项 | 说明 |
|---|---|---|
| 1 | **LRU 换出未触发** | 需要 `--users > 256`（`ALM_MAX_SPACES` 默认 256）才会把一个空间换出内存再重新载入；本次最大只跑到 64。§7.3-3 的「空间构造位于全局注册表锁内」仍待验证 |
| 2 | **Search 并发未拉到 256** | 本次最高 64。考虑到本机 embedding 已接近饱和，建议直接换 API embedding 口径再测上限 |
| 3 | **是否加固 §4.3 的 500** | 三个方向：(a) 接受 0.8%、交给平台重试；(b) 在 Add 路径对这类「非 APIError 的解析失败」重试一次；(c) 调整客户端配置（如显式注入 `http_client` / 关闭 `with_raw_response` 路径）。建议先确认上游是否稳定复现，再决定是否动 ALM 链路 |
| 4 | **弃权阈值重标定** | §4.2；接入正式数据前必须做，否则 A 维度会被过度弃权直接吃掉 |
| 5 | **Append 到计划文档** | §7.3-2 的结论需回写：同 user 并发未复现图竞态，但抓到 LLM 解析层异常 |

## 附：复现命令

```bash
# 服务（注意与已有 8770 实例错开端口）
python -m alm --port 8771 --data-dir data/alm_loadtest --log-level INFO

# 写入 / 检索 / 同 user 混合并发
python -m alm.loadtest --base-url http://127.0.0.1:8771 --scenario write  --users 64 --add-concurrency 64
python -m alm.loadtest --base-url http://127.0.0.1:8771 --scenario read   --users 64 --search-concurrency 64
python -m alm.loadtest --base-url http://127.0.0.1:8771 --scenario mixed  --users 64 --mixed-concurrency 64

# 撑大 user 数触发 LRU 换出（本次未跑）
python -m alm.loadtest --base-url http://127.0.0.1:8771 --scenario write  --users 300 --add-concurrency 64
python -m alm.loadtest --base-url http://127.0.0.1:8771 --scenario churn  --users 300 --churn-users 64
```

`--out report.json` 可落盘结构化结果；token 用量由服务端 stderr 汇总（`ALM_TOKEN_VERBOSE=0` 可只留汇总）。
