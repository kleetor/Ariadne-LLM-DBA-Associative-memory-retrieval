# 0915 —— 面板图谱库与 MCP 图谱切换

新增两个互不耦合的能力：

1. **面板内图谱库**（不涉及 MCP）：在面板里管理、切换、导入、导出多份图谱。
2. **把图谱载入 MCP**：面板选一份图谱，让 MCP 进程切换过去（含向量索引重建）。

---

## 一、关键前提（已核实）

**运行期状态全部按「图谱所在目录」取，与文件名无关**：

| 派生项 | 出处 | 是否随文件名变 |
| --- | --- | --- |
| `auth.json` | `webauth.auth_path_for` | 否 |
| `.ariadne_secret` | `webauth.secret_path_for` | 否 |
| `operations.log` | `oplog.default_oplog_path` | 否 |
| `ariadne.log` | `logbus.default_log_file_path` | 否 |
| `retrieval_params.yaml` | `params_mod.params_path_for` | 否 |
| **`<yaml>.lock`** | `filelock.lock_path_for` | **是**（每份图谱一把锁） |

⇒ **在同一目录内切换图谱是零迁移的**：登录凭据、会话密钥、日志、检索参数都不受影响；只有图谱文件与它自己的写锁跟着换。这是整个方案选择「图谱库 = 图谱目录」的根本原因。

**两个进程的现状**：

- MCP 的 SSE 服务只暴露 `/sse` 与 `/messages/`，没有控制端点；且它的鉴权中间件没有传 `signer`，面板无法用会话 Cookie 调它。
- MCP 已有「按 mtime 检测外部改动」的热重载范式（图谱 YAML、`retrieval_params.yaml` 都是这个套路）。
- MCP 已有后台线程的挂载范式（`IdleReviewScheduler` 在 `main()` 启动、`finally` 停止）。

⇒ MCP 侧走**文件契约 + 自切换**，与既有范式一致，且不需要面板持有 MCP 凭据。

**向量库**：`VectorStore.clear_vectors()`（清空缓存与索引）与 `reconcile(desired)`（按 id 增量对账）都已存在，全量重建 = 前者 + 后者。

## 二、共享契约

新增 `dba_pipeline/graphlib.py`（两个包都要用，故独立成模块，不放 `viz/` 里）：

```
graph_dir(yaml_path)        -> 图谱目录（绝对路径）
list_graphs(yaml_path)      -> 该目录下的图谱文件（*.yaml/*.yml，排除 *.bak/*.tmp/*.lock）
validate_name(name)         -> 仅允许同目录内的纯文件名（拒绝分隔符、..、绝对路径）
pointer_path(yaml_path)     -> <图谱目录>/active_graph.json
read_pointer(yaml_path)     -> dict（不存在返回 {}）
patch_pointer(yaml_path, **fields) -> 在 <图谱目录>/active_graph.lock 内「读-改-写 + 原子替换」
```

指针文件 schema：

```json
{
  "version": 1,
  "active": "memory_graph.yaml",      // 面板请求 MCP 切换到的目标
  "generation": 3,                     // 面板每次请求 +1
  "requested_at": "...",
  "requested_by": "ariadne",
  "applied_generation": 3,             // MCP 已应用到哪一代
  "status": "ok",                      // pending | ok | error
  "detail": "",
  "applied_at": "...",
  "graph": {"nodes": 223, "edges": 266},
  "vector": {"rebuilt": true, "added": 223, "updated": 0, "removed": 0, "seconds": 12.3}
}
```

语义：`generation > applied_generation` ⇒ 有未应用的请求。两个进程都只通过这个文件交换意图与回执。

## 三、功能一：面板内图谱库

### 后端（`dba_pipeline/viz/api_server.py`）

- `GET /api/graphs`
  → `{dir, current, graphs: [{name, size_bytes, mtime, current: bool}]}`
  列表只给文件元信息（不解析 YAML，避免每次开面板都全量 parse）。
- `POST /api/graphs/switch` `{name}` → 面板侧切换：重载 `graph`、重算 `_next_node_id`、换 `_file_lock`/`_last_mtime`、**重建 `ChainRunner`**（否则调用测试还在跑老图）。
- `POST /api/graphs/create` `{name, yaml}` → 导入为**新**图谱（不覆盖同名；先校验可被 `load_graph` 解析）。
- `GET /api/graphs/export?name=` → 导出指定图谱（默认当前）。
- `DELETE /api/graphs?name=` → 删除库中图谱；**禁止删当前激活的**，且仅限图谱目录内的文件。
- 所有 `name` 走 `graphlib.validate_name` 校验（basename、无分隔符、无 `..`）。

### 前端（`static/js/panels.js` + `api.js` + `app.css`）

- 设置页新增「图谱库」区块：列表（当前项打标、显示大小/修改时间）+ 每行 `[切换] [导出] [删除]`，底部 `[导入为新图谱]`（文件选择，复用现有 FileReader 路径）。
- 切换成功后 `ctx.reloadGraph(null)` 刷新 3D 视图，并 toast 提示。
- 顶栏状态区显示当前图谱名（便于确认切到了哪份）。

## 四、功能二：把图谱载入 MCP

### 面板侧

- `POST /api/graphs/activate-mcp` `{name}` → 校验后写指针（`generation + 1`、`status = pending`、`active = name`），立即返回「已请求」。面板**不等** MCP 完成（重建向量可能几十秒）。
- MCP 应用进度与结果并入 `GET /api/graphs` 的响应（`mcp`: `{applied, status, detail, applied_at, vector}`），前端轮询展示；不新增轮询定时器（复用设置页打开时的刷新）。

### MCP 侧（`dba_pipeline/mcp_server.py`）

- `DBAServer.switch_graph(new_path) -> dict`：
  1. 校验：同目录、存在、`load_graph` 能解析（**先解析成临时对象，成功才替换**，失败不改动现状）；
  2. 在 `self._lock` 内替换：`graph` / `yaml_path` / `_file_lock` / `_last_yaml_mtime`；
  3. **全量重建向量**：`vector_store.clear_vectors()` → `reconcile(self._graph_contents())`，并重置 `_vector_mtime`；
  4. 返回 `{nodes, edges, vector: {...}}`。
- `GraphSwitchWatcher(threading.Thread)`：每 3s（`ARIADNE_GRAPH_POLL` 可调）读一次指针文件；`generation > applied_generation` 时调用 `switch_graph`，把结果（成功或错误详情）写回指针。挂载方式与 `IdleReviewScheduler` 一致（`main()` 启动、`finally` 停止）。

## 五、边界与风险

| 风险 | 处置 |
| --- | --- |
| 面板与 MCP 切到不同图谱，导致一边写 YAML 一边读旧图 | 功能一与功能二**解耦**：面板切换只影响面板；要让 MCP 跟随必须显式点「载入 MCP」。UI 上分别展示「面板当前」与「MCP 当前」，避免误以为已同步 |
| `name` 越权（`../` 或绝对路径） | `graphlib.validate_name` 强制 basename，且文件必须位于图谱目录内 |
| 切换失败把图谱搞坏 | 先解析校验、后替换；指针文件里回写 `status=error` + `detail` |
| 全量重建耗时（大图 + API embedding） | 面板不阻塞等待；MCP 侧在回执里报耗时；重建期间 MCP 工具调用被 `_lock` 串行化 |
| 删掉 MCP 正在用的图谱 | 删除接口拒绝「当前激活」，并在响应里提示先从 MCP 切走 |
| 指针文件被两个进程同时写 | 统一走 `active_graph.lock` + 原子替换 |

## 六、验证方式

1. `node --check` + `py_compile` 覆盖改动文件。
2. 手工验证：
   - 面板列出图谱目录下的文件，切换后 3D 视图与状态栏节点数变化、`/api/config` 的 `yaml_path` 跟着变；
   - 切换后编辑节点仍落在新文件（看 mtime 与文件内容）；
   - 导入为新图谱 → 列表出现新项；重名被拒；`../x` 被拒；
   - 删除当前激活项被拒；
   - 点「载入 MCP」→ 指针 `generation` 增加 → MCP 日志出现切换与向量重建 → 回执 `status=ok` 且节点数一致；
   - MCP 侧故意给一个坏 YAML → 回执 `status=error`，且 MCP 仍在用原图谱（检索不受影响）。

## 七、执行结果（2026-09-15）

**新增/改动**

| 文件 | 内容 |
| --- | --- |
| `dba_pipeline/graphlib.py`（新） | 图谱库契约：目录/命名校验、`list_graphs`（按「能解析成图谱」过滤 + `(mtime,size)` 缓存）、指针文件读写与跨进程锁 |
| `dba_pipeline/mcp_server.py` | `DBAServer.switch_graph()`（就地 `load_into` + 清空重建向量）、`GraphSwitchWatcher` 线程、`main()` 启停接线 |
| `dba_pipeline/viz/api_server.py` | `MemoryGraphAPI.switch_graph()`、`export_yaml(path=)`、5 个 `/api/graphs*` 路由、`_parse_graph_yaml`/`_write_text_atomic` 抽公用 |
| `dba_pipeline/viz/chain_runner.py` | `rebind()`：切换图谱后丢弃已装配链路 |
| `static/js/{api,panels}.js`、`static/{index.html,css/app.css}` | 图谱库区块、MCP 应用回执、状态栏「图谱」、客户端方法 |

**实测结果**（真实进程 + 真实 HTTP）

| 验证项 | 结果 |
| --- | --- |
| 列表过滤 | 只列出 `LiFEMem.yaml`(322) / `memory_graph.yaml`(223) / `sample_graph.yaml`(0)；`LiFEMem_purposes.yaml`、`LiFEMem_queries.yaml` 这类非图谱 YAML 被排除（同时消除了误删评测数据的入口） |
| 命名/越权 | `../evil.yaml` → 400「图谱名只能是文件名」；非图谱文件 → 400 明确原因；不存在 → 400 |
| 面板切换 | 切到 `LiFEMem.yaml` → `changed=true, 322 节点/410 边`，`/api/config` 的 `yaml_path` 同步变更 |
| **MCP 自切换** | `activate-mcp` 后 2 个轮询周期（6s）内完成：`status=ok`、`graph={322,410}`、`vector={added:322, rebuilt:true}`（全量重建） |
| 删除保护（面板占用） | 400「这是面板当前正在使用的图谱」 |
| 删除保护（MCP 占用） | 用临时图谱 `zz_mcp_hold.yaml` 实测：面板切走后删除 → 400「MCP 当前正在使用该图谱」；MCP 切走后 → 200 删除成功 |
| 导入/重名/非法内容 | `create` → 201；重名 → 400；`a: 1`（无 nodes）→ 400 |
| 前端渲染 | 图谱库区块 3 行（当前项无「切换/删除」按钮）；MCP 回执行 `mcp-apply ok`：「已应用 … · 223 节点 / 266 边 · 向量重建 +223 ~0 -0」；状态栏显示当前图谱；控制台无报错 |

**过程中额外修掉的一处不一致**：MCP 切换图谱时原本无条件先 `clear_vectors()`，而既有 `reconcile_vectors` 对**空图谱**是刻意「不清空既有索引，避免误删」。已改为先判断目标图谱非空再清空，与既有约定对齐。

**已知边界（非缺陷，但需知晓）**

- MCP 目前只认「已经 applied 过」的占用状态来做删除保护；若面板刚发出请求而 MCP 尚未应用，此时删除该文件会让本次切换失败（MCP 会把错误写回指针，面板可见）。
- `sample_graph.yaml` 只有 0 节点，切过去会得到空图；向量索引按上面的约定保留旧索引不被清空。
- 图谱库固定为 `--yaml` 所在目录，不支持跨目录（凭据与运行期状态以目录为锚点）。
- **MCP 重启后不会自动回到面板登记的图谱**：它以命令行的 `--yaml` 启动，而指针文件里仍是上次的 `active`/`applied_generation`（两者相等，故监听线程不会补切）。此时面板会显示「已应用 LiFEMem.yaml」而 MCP 实际在用 `--yaml` 指定的那份，属静默分歧。处置方式需要你定：要么「启动时以指针为准自动切换」，要么「`--yaml` 优先并回写指针纠正显示」。

## 八、第二轮：启动不再由参数决定用哪份图谱

上面那条分歧的处理结论是——**别让启动参数决定用哪份图谱**，改为「初次不指定（或空图谱启动），之后全部由面板选择并把选择记下来」。

**改动**

| 项 | 内容 |
| --- | --- |
| 指针文件 | 新增 `panel_active` 字段（面板自己当前用的那份），与 MCP 的 `active`（切换请求目标）分字段，互不干扰 |
| 解析顺序 | `resolve_startup()`：**指针记录 → `--yaml` 提示 → 目录内的空图谱占位**（`sample_graph.yaml`，缺失时自动创建） |
| 图谱目录 | `--graph-dir` / `ARIADNE_GRAPHS_DIR` → `--yaml` 所在目录 → `./data` |
| 参数 | 面板与 MCP 的 `--yaml` 均改为**可选**（只在没有历史记录时当启动提示）；MCP 新增 `--graph-dir`，轮询间隔可用 `ARIADNE_GRAPH_POLL` 调 |
| 面板切换 | 切换成功时除换本面板外，同时写 `panel_active` 到共享指针 |

**实测**

| 场景 | 结果 |
| --- | --- |
| 无参启动、指针无 `panel_active` | 面板落到 `sample_graph.yaml`（空图谱占位） |
| 面板切到 `LiFEMem.yaml` | 指针写入 `panel_active: LiFEMem.yaml`，且原有 MCP 字段完好 |
| 再以**无参**重启面板 | 面板当前 = `LiFEMem.yaml`，`/api/config` 的 `yaml_path` 同步 —— 记住了 |
| MCP 以**无参**重启 | 日志：`图谱目录: ...\data；启动图谱: memory_graph.yaml（指针记录）` |

这样两端各自的「当前图谱」都跨重启被记住，且互不干扰（面板的选择不会偷偷改 MCP，MCP 的切换也只由「载入 MCP」触发）。启动命令因此可以简化成：

```bash
python -m dba_pipeline.viz.api_server --port 8765        # 本地：不用再传 --yaml
python -m dba_pipeline.mcp_server --sse --port 8766
```

首次启动是空图谱，在面板「设置 → 图谱库」里选一份即可；之后重启都会回到上次的选择。
