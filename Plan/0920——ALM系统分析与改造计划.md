## 一、现状分析

### 1.1 架构：ALM 是 MCP 之上的薄适配层

两侧共用同一个检索与建图内核：

| 环节 | MCP 调用点 | ALM 调用点 | 是否共用 |
|---|---|---|---|
| 建图抽取 | `dba_temporal_lookup` / `dba_add_conversation` → `GraphBuilder` + `MemoryDBA.maintain` | `engine.add` → `space.add` → 同一个 `maintain` | ✅ 同一内核 |
| 联想检索 | `query_memory` → `retriever.retrieve_with_story(...)` | `space._search_locked` → 同一个 `retrieve_with_story(...)` | ✅ 同一内核 |
| 时序检索 | **`dba_temporal_lookup`** → `retriever.temporal_lookup(...)` | **无** | ❌ **ALM 缺失** |

ALM 独有的是：契约层（HTTP 端点、`data[]` 组装、鉴权、错误体）、弃权机制、`/data` 下的按 `user_id` 隔离存储与 30 天清理。

### 1.2 `/search` 实际路径（已核对代码）

[alm/space.py](../../alm/space.py) `_search_locked()`：

```
retrieve_with_story(query,
                    with_response=False,          # 不生成最终答案（主办方红线）
                    render_timestamps=<config>,   # 默认 False
                    seed_k=_effective_seed_k(),   # 自适应
                    max_hops=<config>,
                    expand_k=<config>)
  → 取 stories[0] 作为唯一返回条目（score=1.0）
  → 叙事缺失时退回采纳节点原文（避免与「弃权」混淆）
  → best_cos ← hop_history（T1 种子 + T2 图扩展）候选池的最大余弦
  → 弃权两段：硬下限 0.35 → 模糊带 [0.35, 0.50) 交 LLM 判定
  → _normalize_scores 按返回顺序折算分数
```

**未传入 `purpose`**：`retrieve_with_story` 内部自行完成目的推断（即每次 Search 的 2 次 LLM 之一：目的推断 + 叙事整理）。**这一点是时序路由的接入点**（见 §3.2）。

### 1.3 已删除的 ALM 自造层（0920 重构）

| 已删 | 删除理由 | 事后判定 |
|---|---|---|
| `alm/rerank.py`（层内重排） | 平台无检索侧指标，排序不构成门槛 | ✅ 成立 |
| options `guard` / `contrast` 两档 | A/B 净收益 0（A/B 记录 §7.10.2） | ✅ 成立 |
| `search_shape` 三形态开关 | 只留对 MCP 的忠实映射 | ✅ 成立 |

**T4 的删除理由错误**：MCP 的时序能力在**另一个工具** `dba_temporal_lookup` 里，我只看了 `query_memory` 就下了结论。此错导致 `/search` 现在**无法还原两段工具式检索**——本计划的主体工作之一就是补回它，且必须按"串联"而非"并集"的方式补（见 §3.2）。

### 2.1 Add 侧（建图抽取）

| 项 | 现状 |

| 抽取算法 | 与 MCP **同一内核**（`GraphBuilder` + `MemoryDBA.maintain`），无差异 |

**对「边数 +37% / 节点 −8% 在 3 轮下是否稳定」的回答**

- **「边数 +37%」不复现。** 第 2、3 轮方向相反（−23.0%、−7.7%），Δ% 中位 **−7.7%**。
  更关键：**A 臂自身的跨轮跨度 [189, 344]（1.82×）远大于任何一轮的跨臂差** ——
  "边数"这个量在**同一臂内**的 run 间波动就已超过两臂之间的差。
  → **该指标落在噪声内，无法判定前缀对其有影响**；首轮的 +37% 是**单轮假信号**。
- **「节点 −8%」无法判定。** 3 轮 Δ% 为 −8.1% / **+8.2%** / −6.6%（中位 −6.6%）**跨 0**；
  两臂区间重叠（A [61,62] 与 B [57,66]）。
- **时间锚点与 TEMPORAL 边**：首轮的"锚点 19/19 完全一致"**未复现**（第 2、3 轮为 18/15、17/16）；
  TEMPORAL 边两臂中位数相同（18/18）。两者区间均重叠 → 无法判定。
  （锚点仍由 `timestamp` 字段与节点内容生成，这一**机制性**判断不受影响；受影响的是
  "有无前缀会导致锚点数差异"这一步。）
- **一条附带观察（n=3，仍只是观察，不足以下结论）**：A 臂三轮节点数 62/61/61（跨度 1），
  B 臂 57/66/57（跨度 9）——**去前缀后节点产出看起来更不稳**。

**结论**：3 轮不足以对任一指标下结论，**§2.1 的"待确认"项不能关闭**；也**不能**判定前缀有害。
按本项目一贯口径（§7.10.5 F / §7.10.7 F1），这 3 轮唯一可带走的产出是：
**在前缀 A/B 的可比指标里，"边数"是跨轮最不稳定的量（同臂 1.8× 波动），
后续任何依赖边数的单轮对照结论都不可采信。**

> 原首轮单轮读法（"边数 +37% 是唯一显著项"、"去前缀 → 连边更密方向不算坏"、
> "时间锚点完全一致 → 前缀不是时间信息来源"）**已被上表作废**，保留于 git 历史，不再引用。

### 2.2 Search 侧（两段工具式检索）

| 能力 | MCP | ALM 现状 |
|---|---|---|
| 联想通道（PAR + 叙事） | `query_memory` | ✅ 有 |
| 时序通道（时间锚点 → 共时事实） | `dba_temporal_lookup` | ❌ **无** |
| 通道选择 | 由上层 LLM **按问题类型选工具** | ❌ 无（单端点，平台不会替我们选） |

**结论**：`/search` 必须**在内部还原"选工具 + 两段串联"的语义**。

## 三、改造计划

### 3.0 前置：上下文落盘的两段拆分

现状与 0901 时期的差距：当时 `collect_context_*.py` 与 `judge_*.py` 分离，判分只读落盘 JSON；
现在的评测脚本"建库 + 组装 + 判分"一条龙，导致**每换一个 judge 模型都要重建库**。

- 本次改造**不依赖**判分，故**不阻塞**，但任何后续评测实验开工前应先拆。

### 3.1 阶段一：抽取文本化的 A/B（便宜、先做）

**问题**：ALM 的 `[role@timestamp]` 前缀是否影响建图？

**方法**：同一段对话，两个臂各灌一次，比图。

| 臂 | 输入 |
|---|---|
| A | `[小林@2024-01-01T10:00:00] 内容...`（现状） |
| B | 纯文本 `内容...`（不带任何前缀） |

**比对指标**：节点数 / 边数 / TEMPORAL 边数 / 时间锚点数 / 「用户」「助手」归属称法 / 噪声节点数 / deprecated 数。

**注意**：两侧必须**同一次运行内**比较。跨运行比无效——抽取是 LLM 非确定性，且 §7.10.5 已实测到
检索层波动远大于故事层（R@all std ±11.4pp）。若要坐实结论需重复 2–3 轮取中位数。

**产出**：结论写入 §2.1 的"待确认"栏；若前缀有害，则改文本化方式（如把时间戳移到单独字段或省略）。

### 3.2 阶段二：`/search` 内部还原两段工具式检索（主体）

**定案设计（用户定案，串联三段）**：

```
/search 内：
  ① 目的判定 —— 只看 query，一次定死（复用 retrieve_with_story 内部已有的目的推断）
  ② 若判定为时序 → 调 temporal_lookup(query, ...) 取时间锚点 + 共时事实
  ③ 用时序产出驱动主通道：把锚点/事实文本**追加**进 purpose
     → retrieve_with_story(query, purpose=…, ...)
  ④ 非时序 → 直接走 ③（无追加）
```

**为什么是"串联"而不是"并集"**：被删掉的 T4 是"两路候选取并集"，实测 97% 已被主链召回、对 gold
命中贡献 0。本设计是**以时序结果为入口起跳**，对应 MCP 里 agent 的真实序列（先 temporal_lookup，
读完事实再联想）。

**可行性（已核接口，无需改检索器）**：

- `retrieve(query, seed_k, max_hops, expand_k, **purpose: Optional[List[str]]**, on_stage)`：
  `purpose` 是现成参数，目的匹配节点会并入种子（`purpose_seeds`）；
- `seed_ids` 为内部计算，**外部不能注入种子**——故**走 `purpose` 通道是唯一正解**；
- `temporal_lookup(query, k_seed, max_facts, max_anchors)` 现成可用。

**必须遵守的约束（用户指出风险后定死）**：

| # | 约束 | 原因 |
|---|---|---|
| ① | 目的判定**只看 query、一次定死**，见到任何检索结果后**不得更改** | 防止时序返回污染目的判定 |
| ② | 时序产出**只能追加**到 `purpose`，不得覆盖/重写 | 同上 |
| ③ | **主通道检索无条件必经**，不受 LLM 影响 | 防止"调了时序却不调主检索"，导致联想通道整体丢失 |
| ④ | 路由**必须打日志**（是否命中时序 / 主通道是否执行 / 追加了哪些锚点） | 上述失效模式**静默**，无日志则不可观测 |

**LLM 的影响面被限制为"二元分类：是不是时序问题"**，不碰控制流。
理由：MCP 能把选工具交给 LLM，是因为上层 agent 本就负责回答、且有完整对话上下文；
而 `/search` 是契约端点，职责就是返回证据——把控制流交给 LLM 会引入**静默劣化**。

**时序判定方式（待定，二选一）**：

| 方案 | 做法 | 取舍 |
|---|---|---|
| 纯 LLM 二元判定 | 与现有目的推断**合并到同一次调用** | 最简单、最一致；不额外增加 LLM 调用 |
| 关键词预筛 + LLM 确认 | 关键词挡掉明显非时序，LLM 只处理灰区 | 省判定开销；但判定逻辑分两段，多一处可漂移 |

> 参考：MCP 的 `dba_temporal_lookup` 工具描述本身就列了典型信号（昨天/今天/上周/上个月/高中学期…），
> 说明该判定在 MCP 侧也是**关键词驱动**的。
>
> **倾向**：纯 LLM 二元判定（与目的推断合并）。理由是不引入第二处可漂移逻辑，且不增加调用数。

**实现注意**：`retrieve_with_story` 目前**内部自行完成目的推断**（ALM 未传 `purpose`）。
接入时需确认：显式传入 `purpose` 时，内部推断是**跳过**还是**合并**——这决定改造点是在 `space.py`
（传参）还是在检索器内部（在推断之后追加）。

### 3.3 实施结果（0920）

改动 4 个文件：

| 文件 | 改动 |
|---|---|
| `alm/space.py` | 新增 `_route_purposes(query)`：显式调 `infer_purpose` 取 purposes + temporal 标签 → 命中才调 `temporal_lookup` → **追加**锚点/事实文本；`_search_locked` 传 `purpose=` 并加"主通道已执行"日志 |
| `dba_pipeline/llm/inference.py` | 目的推断 prompt 增加 `"temporal": true/false` 布尔字段（**不新增 LLM 调用**），判据保守"拿不准一律 false" |
| `dba_pipeline/retrieval/retriever.py` | `retrieve_with_story` 补 `purpose` 参数并透传（原签名没有它，不改无法注入）；`None` 时行为逐字不变 |
| `alm/config.py` | `temporal_route` 开关 + 三个参数（`temporal_k_seed` / `temporal_max_facts` / `temporal_max_anchors`） |

**关键技术事实**：`retrieve()` 的 `purpose` 语义是"**提供时跳过内部的目的推断**"，故 ALM 显式传
`purpose` 时必须自己先调 `infer_purpose` —— 一进一出，**每次 Search 的目的推断仍是 1 次 LLM 调用**。
`temporal_lookup` 本身只用向量检索 + 图单跳，无 LLM。

**实跑验证**（真数据灌 2 段对话）：

```
时序「上周三的需求评审会定了什么方案」
  → 判定=时序 目的数=4 → 时序查询 match_type=exact 锚点=['n1'] 事实数=2 可并入=3
  → 追加后目的 4→7 → 主通道已执行 峰值=36 叙事=1 → best_cos=0.6731
  → 返回叙事含该时间点事实
非时序「用户叫什么名字」「小林喜欢什么运动」ON vs OFF
  → 均判定=非时序、未调时序工具、主通道无条件执行
  → 配对样本 峰值数 与 best_cos 逐对完全相同
确定性等价检验（固定目的、绕过 LLM 抖动）
  → 注入 purpose 峰值数 == 内部推断峰值数（两类查询均一致）→ 非时序路径与改造前等价
```

`compileall` exit=0；`pytest tests/test_alm_contract.py` **33 passed**（基线 33，无回归）。

**默认值定案：`temporal_route` 默认 `False`（用户定，选项 B）。**

初版给的是默认 `True`。改为 `False` 的理由：链路虽已实现并验证，但"时序产出并入 `purpose`"对种子
选择的**实际权重未标定**（§六风险 2），且**没有 A/B 证据**。按本项目对冻结行为的既定处理
（`render_timestamps` 即"改动须由 A/B 分数决定"，净 0 即回退），在拿到净收益证据前不默认改变线上行为。
三处已同改并实测：dataclass 默认 `False`、`from_env` 兜底 `False`、`.env` 未显式设置
（`ALM_TEMPORAL_ROUTE` 为 `None`）→ `from_env().temporal_route = False`。
置 `ALM_TEMPORAL_ROUTE=1` 即启用完整串联链路。

**（0920 补测）** §3.5 的 ON/OFF A/B 结果显示净收益**方向为正但不显著**（增益由单条查询驱动、
幅度与实测噪声同量级）→ **证据不足以支持开启，维持默认关闭**。「现有 A/B 证据支持开启」这一条
**不成立**，本值不改。

**如实说明的未完成项**：① `purpose` 追加文本对种子选择的权重未标定（无 A/B）；② 裸"上周"这类查询
会被 `temporal_lookup` 的字面硬校验拒掉（既有行为，未改），此时路由命中但退回仅目的通道——偏保守；
③ 时序路由尚未在平台 smoke 上验证。

### 3.4 阶段三：验证

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 时序路由命中 | 一个 A 类问题（非时序）+ 一个时序问题，各打一发 | 前者不调时序、后者调；日志可见 |
| 主通道必经 | 同上两发 | 两发的主通道**都**执行（日志确认） |
| 从锚点起跳 | 时序问题一发 | 追加的锚点出现在 `purpose`，且返回叙事里含该时间点的事实 |
| 目的不被改写 | 同上 | ①的原始目的与最终 `purpose` 呈**追加**关系（日志比对） |
| 抽取前缀 A/B | 阶段一方案 | 图指标差异在噪声内（或定位到具体受损项） |

**回归**：`compileall alm`、`pytest tests/test_alm_contract.py`（当前 33 passed）、`alm/smoke.py` 四端点契约用例。

### 3.5 时序路由 ON/OFF 的 A/B 实测（0920）

**问题**：`temporal_route` 的净收益是多少？（§3.3 定案为"无 A/B 证据前默认关闭"，本节即补该证据。）

**探针**：临时脚本 `eval/probe_temporal_route_ab.py`（**测完即删**，日志留
`eval/outputs/temporal_route_ab.log`）。

**测量设计（关键）**：叙事生成与目的推断都是 **LLM 非确定性**，同一臂两次运行本身就有差异。
故：**只灌一次**（4 段对话，257.2s），两个引擎共用同一 `data_dir` 做只读检索（避免"两次抽取"
这个额外变量），**每臂各跑 2 遍**——先用臂内两遍之差量出自波动，再看臂间差是否明显大于它。

**查询分组**（取自 `groupchat_mixed_queries.yaml` 的 13 条有 gold 的查询）：

| 组 | 口径 | 条目 |
|---|---|---|
| 时序组（4 条 / 10 项 gold） | 题干含明确时间词或时间疑问 | q2（上周三）、q8（这周六）、q11（原本什么时候）、q13（定在哪天） |
| 非时序组（9 条 / 24 项 gold） | 其余 | q1/q3/q4/q5/q6/q7/q10/q12/q14 |

**分组汇总**

| 组 | 臂 | 两遍命中 | 区间 | 中位 | 叙事总长（两遍） |
|---|---|---|---|---|---|
| 时序组 /10 | OFF | 7, 8 | [7, 8] | 7.5 | 1466 / 1509 |
| | ON | **10, 10** | **[10, 10]** | **10.0** | 1259 / 1275 |
| 非时序组 /24 | OFF | 21, 23 | [21, 23] | 22.0 | 1814 / 2204 |
| | ON | 23, 23 | [23, 23] | 23.0 | 1951 / 1948 |

| 项 | 时序组 | 非时序组 |
|---|---|---|

| 臂内自波动（OFF 两遍） | 0~1 项 | 0~2 项 |
| 臂内自波动（ON 两遍） | 0 项 | 0 项 |

**逐条命中（时序组）**

| id | OFF 两遍 | ON 两遍 | 路由（ON，两遍一致） |
|---|---|---|---|
| q2 | 2/2, 2/2 | 2/2, 2/2 | 判定=时序，`match_type=exact`，锚点 `n2`，追加 4 条 |
| q8 | **0/2, 0/2** | **2/2, 2/2** | 判定=时序，`match_type=exact`，锚点 `n46`，追加 3 条 |
| q11 | 3/3, 3/3 | 3/3, 3/3 | 判定=时序，但 **`match_type=rejected`**（锚点 0 / 追加 0）→ 退回仅目的通道 |
| q13 | 2/3, 3/3 | 3/3, 3/3 | **判定=非时序**（未调时序工具） |

**非时序组**：9 条中有 **8 条在 4 次观测（2 臂 × 2 遍）中命中数完全相同**；唯一差异是
q6（OFF: 0/2 → 2/2），而 q6 判定=非时序、**根本没走时序工具**。

**路由健康度（约束 ①②③④ 的实测）**

| 约束 | 实测 |
|---|---|
| ③ 主通道无条件必经 | **13/13 条、两遍共 26 次全部执行**（日志 `主通道已执行`）→ 无"调了时序却不调主检索"这一静默失效 |
| ② 只追加不覆盖 | 日志呈"目的 3 → 7（追加 4 条）"形式，未出现覆盖 → 成立 |
| ① 只看 query、一次定死 | 每查询只调用 1 次 `infer_purpose`，目的数两遍一致或 ±1 → 成立 |
| ④ 可观测 | 判定 / `match_type` / 锚点 id / 追加条数全部落日志，只含数值与 ID（合规） |

**判定稳定性（开臂两遍）**：13 条中 **q12 判定翻转**（第 1 遍=时序、第 2 遍=非时序）；
时序组 4 条中 3 条被判时序（**q13 漏判**）；**非时序组 9 条中有 4 条被误判为时序**
（q1/q3/q4/q12）。

**判读（方向 + 区间 + 限制，不下"有效/无效"结论）**

- **方向为正**：时序组 ON 两遍均高于 OFF，且区间 [7,8] 与 [10,10] **不重叠**。
- **但增益几乎全部来自单条查询 q8**：+2~+3 项中，恒定的 +2 全部是 q8（OFF 两遍 0/2、
  ON 两遍 2/2，**4/4 一致**）；另一 +1 出现在 q13 的 OFF 第 1 遍，而 **q13 未被路由**，属噪声。
  q2 路由命中并追加了 4 条锚点文本，命中数却**完全没变**；q11 路由命中但被字面硬校验拒掉。
- **噪声地板**：非时序组是天然的"空操作配对"（两臂在该组只差"`infer_purpose` 由 ALM 显式调用
  还是检索器内部调用"，**语义等价**），实测臂间差 0~2 项、臂内差 0~2 项；
  时序组臂内差 0~1 项。时序组的 **+2（第 2 遍配对）恰好等于该噪声地板**。
- → **这是一个方向为正、但由 1 条查询驱动、幅度与实测噪声同量级的信号；时序组样本仅
  4 条 / 10 项 gold → 不足以判定"时序路由有效"。** 同时**未观察到伤害**（非时序组 8/9 条
  四遍逐字相同，无弃权、无长度异常）。

**已知限制（如实列出）**

1. **两臂顺序执行、未交叉**：OFF 两遍全部跑在 ON 两遍之前，若 LLM 供应商在此期间漂移，
   会与臂效应混淆。
2. **噪声只能由同臂重复估计**，n=2/臂；"臂内差 0"不等于真值 0。
3. 真正产出锚点的时序查询只有 **2/4**：q11 被 `temporal_lookup` 的字面硬校验拒掉（§3.3 未完成项 ②
   记录的既有行为）、q13 未被判定为时序。
4. **非时序组误判率偏高（4/9）**，判定偏激进，与 §六风险 1「阈值应偏保守（宁漏不误）」的取向
   不一致；本轮未造成可观测伤害，但**不能据此认为误判无害**。
5. 只用了 1 张 60 节点级图、13 条查询；未测回答级/判分维度（按既定决策不做）。

**结论**：**证据不足以支持开启 → 维持默认关闭（`temporal_route = False`）**，
实现与开关保留；日志与全部数值见 `eval/outputs/temporal_route_ab.log`。

**成本**：写入 257.2s + 4 遍检索 1616.5s ≈ **31 分钟**（另加模型加载约 1 分钟）。
偏高原因：本次运行时 LLM 单次调用延迟（8~63s/次，多数 20~50s）**远高于 §7.6 记录的 2.7s**，
而非检索链路本身变慢（检索侧 best_cos 逐查询在 4 次观测中完全一致，说明向量/图侧是确定的）。

## 四、明确不做的事

| 项 | 理由 |
|---|---|
| 判分侧任何优化（三维对照、多模型交叉、弱基线臂） | 用户决定停在记录状态；且实测判分是**对比打分**，会放大效果相近两方的差距（§7.10.7 F1） |
| 填充 `score` / `created_at` 的效用验证 | 二者是可选字段，且是给**扁平返回数组 + 无内部时序**的记忆系统用的；本系统时序处理是内建的，属冗余选项（§7.10.7 F2） |
| 检索侧排序/召回精度优化 | 平台**无检索侧指标**，排序与条数不构成门槛（§7.10.6） |
| `render_timestamps` 变更 | A/B 净收益 0，已回退（§7.10.5 F） |
