# 检索预算口径与输出量上限实验报告（0925）

> **问题的由来**：同一份代码、同一量级的图，**离线实验的读出量是"几十条"，ALM 线上却是"几百条"**
> （线上日志 `喂入点 max 379 / 采纳 max 378`）。这个矛盾一度被怀疑成平台侧异常或图规模差异，
> 决定不再靠猜，改为把输入输出抓出来看。
>
> **结论（两条）**：
> 1. **不是平台异常，是两边注入的检索预算不是一套。** 历史评测走 `retrieve()` 的**自带默认**
>    `seed_k=5 / expand_k=None→5`；ALM 线上注入 `seed_k=_effective_seed_k()`（200 节点→20、
>    322 节点→32）与 `expand_k=40`。同一张图、同一查询、同一份代码，只换预算就读出量差 5–7 倍。
> 2. **因此"把输出量压回几十条"是错的方向。** 沿两个可动旋钮做正交 A/B，发现**两个旋钮都伤
>    gold 覆盖，`max_peak_nodes` 尤其致命**——当年那 37 条只覆盖 **48.3%** 的 gold，而现行宽预算
>    覆盖 **93.1%**。宽预算不是缺陷，它是在为召回付费。
>
> **工具**：`eval/exp_budget_cap_ab.py`；产物 `eval/outputs/exp_budget_cap_ab.json`；
> 相关：`eval/outputs/scale_retrieval.json`（"几十条"的原始出处）。

---

## 一、根因：两套预算口径

### 1.1 "几十条"的原始出处，是窄预算的签名

`eval/outputs/scale_retrieval.json` 记录了 50 / 100 / 200 三个规模的 Ariadne 候选数：

| 规模 | 50 | 100 | 200 |
|---|---|---|---|
| `n_candidates` | 26 | 26 | **26** |

**三档恒为 26，不随图规模变化**——这正是"读出量由预算封顶、而非由图规模决定"的签名。
而产出它的 [scale_retrieval.py](../../eval/scale_retrieval.py) 是这样调的：

```python
out = retriever.retrieve_with_story(QUERIES[0], with_response=False)   # 没传 seed_k / expand_k
```

`retrieve()` 的签名默认是 `seed_k: int = 5, expand_k: int = None`，而 `expand_k=None` 在循环里
落成 `top_k = seed_k = 5`。eval 下绝大多数脚本都是这个调法
（`param_sweep.py`、`run_temporal_*`、`_dump_raw.py`、`smoke_*`、`run_p_baseline.py`）。

### 1.2 ALM 线上注入的是另一套

[alm/space.py](../../alm/space.py) 的 `_search_locked()` 显式注入：

```python
seed_k = self._effective_seed_k()   # total<=40 → 全量；否则 max(5, min(40, total//10))
expand_k = self.config.expand_k     # 40
max_hops = self.config.max_hops     # 5
```

`_effective_seed_k()` 是后来为修「小图全量取种子 / 孤立节点召回」加的，历史基线 `seed_k=5` 是为
另一个目的设的——**两者从未在同一张图上对齐过**，所以两边的账面数字对不上。

### 1.3 放大机制：峰值容忍带取"整轮并集"

`_collect_peak_tolerance()` 的判据是**轮均分**：只要某一轮的 `mean_score ≥ peak_mean − 0.10`，
就把它那一轮的**全部候选**收进来。于是读出量 ≈ 带宽内所有轮的候选并集，而每轮候选数由
"前沿宽度 × 节点度数"决定。前沿宽度又由 `expand_k` 决定——`expand_k` 从 5 提到 40，
前沿宽 8 倍，5 跳下来就是数量级的差别。

## 二、正交 A/B 设计

两个可动旋钮做成正交因子，另加一行历史口径作锚点：

| 因子 | 档位 |
|---|---|
| A `expand_k` | 40（现行） / 20 / 10 / 5 |
| B `max_peak_nodes` | 0（不限，现行） / 40 / 20 |
| 锚点 | `seed_k=5 / expand_k=5 / 不限`（`retrieve()` 自带默认） |

- `seed_k` **固定**为 ALM 现行 `_effective_seed_k()` 取值，故输出差异只由 A/B 解释；
- 目的（purposes）由查询集直接注入，**全程不调用 LLM**，结果可复现；
- `max_hops=5`；`max_peak_nodes` 按 `combined_score` 降序截断（不按收集顺序，否则只留早期轮）。

### 语料

| 语料 | 图规模 | 查询数 | gold |
|---|---|---|---|
| `comprehensive` | 163 节点 | 76 条（含 `multi_hop` 9 / `knowledge_update` 6 / `temporal` 10 / `abstention` 6） | 有（对齐率 229/229） |
| `lifemem`（`data/LiFEMem.yaml`） | **322 节点 / 392 边** | 5 条 | 有 |
| `scale_200` | 200 节点 | 3 条 | 无（只量规模） |

`lifemem` 就是被记作"300 节点实验"的那张图。`abstention` 类 `gold_expected` 为空，不计入 gold 指标。

## 四、结论

1. **矛盾定案，且平台侧没有特殊路径。** 本地复现完全一致（`scale_200` 上 28 条 → 158 条），
   说明是**配置口径差异**，不是平台触发了不同的代码分支。这也意味着：**不需要在平台上抓正文
   就能定位**，本报告的结论全部由本地产物支撑。

2. **"压回几十条"会丢掉一半召回。** LiFEMem 上历史口径 37 条只覆盖 48.3% 的 gold，现行 181 条
   覆盖 93.1%；comprehensive 上 `multi_hop` 从 96.3% 掉到 79.6%（历史口径）。当年那几十条
   不是"刚好合适"，是**在漏召回**。

3. **两个旋钮都贵，`max_peak_nodes` 最贵。** 因为上限按 `combined_score` 降序截断，而**多跳
   gold 恰恰不是高分节点**——它们靠图扩展捞回来，分数天然偏低，正是被上限砍掉的那批。
   `exp40/上限40` 在 LiFEMem 上只剩 27.6%，**比历史口径的 48.3% 还差**。

4. **真正该修的不在检索预算，而在 StoryRank 的取舍。** 检索负责召回（现行 93%），收敛该由
   StoryRank 负责——而线上实测采纳/喂入 = **96%（极端 378/379）**，它没在做筛选。0828 检索理论文
   的设计输出区间 5–37 说的是 **StoryRank 的输出**，不是检索的输出；"检索给 133–205 条、
   StoryRank 压到 ≤37"本来就是设计里的一环。现在第一步做对了、第二步空转 → 喂给 Answer 的块
   近乎全图 → 这正是 B2 / D1 / F1 三个 0 的统一解释。

## 五、落地改动

| 文件 | 改动 | 默认 |
|---|---|---|
| [dba_pipeline/retrieval/retriever.py](../../dba_pipeline/retrieval/retriever.py) | `_collect_peak_tolerance(hop_history, max_nodes=None)`：按分数降序截断；`retrieve()` / `retrieve_with_story()` 新增 `max_peak_nodes`；返回体新增 `path_edge_types`（喂入边型直方图） | `None` = 不限 |
| [alm/config.py](../../alm/config.py) | 新增 `max_peak_nodes`（env `ALM_MAX_PEAK_NODES`） | `0` = 关 |
| [alm/space.py](../../alm/space.py) | 透传 `max_peak_nodes`；新增默认关闭的 `trace_io` 输入输出留痕（env `ALM_TRACE_IO`） | `trace_io=False` |
| [alm/server.py](../../alm/server.py) | 启动横幅单列「检索参数 ↑ max_peak_nodes」与「输入输出留痕」状态 | — |

**两处默认都保持关闭**，线上行为与改造前逐字一致（本项目对冻结行为的既定处理：改动须由 A/B 决定）。
`max_peak_nodes` 作为封顶长尾的能力保留，但**本报告不建议上线**。

`path_edge_types` 的用途：只知边数不够——边数达标但全是被动关系（`scenario`/`social`/`attribute`）
时，StoryRank 规则 4 要的因果链依然无从表达，这是"补边补了很多、B2 仍是 0"的必要观测。

## 六、复现

```bash
python -m eval.exp_budget_cap_ab                        # 三语料全网格（约 6 分钟）
python -m eval.exp_budget_cap_ab --corpus lifemem        # 只跑 322 节点那张
python -m eval.exp_budget_cap_ab --expand-ks 40 10 --caps 0 20
```

全程零 LLM 调用（目的由查询集注入），只记计数与节点 id，不落记忆正文。

## 七、后续与未决

1. **转修 StoryRank 的采纳率**（本报告的主要去向）：先量"采纳率为什么是 96%"——是 prompt 没要求
   取舍，还是规则让它倾向全留。本地可测（322 图 + 5 条 gold 查询，5 次 LLM 调用）。
2. **`temporal_route` 仍为默认 False**：它与本报告的预算问题无关，属另一条线（时序串联），
   等 A/B 证据。
3. **`max_peak_nodes` 的未来用法**：若 StoryRank 修好，检索侧更不需要封顶；若 StoryRank 短期
   修不动，它就是"保召回、砍长尾"的兜底——但需先证 `cap` 不会像本实验一样砍掉多跳 gold。
4. **`peak_tolerance` 0.10→0.05**：先前实测可免费降峰 19%（gold 覆盖不掉），与本报告的
   `expand_k` / `max_peak_nodes` 是第三个旋钮，尚未纳入本网格，可作下一轮的正交因子。
