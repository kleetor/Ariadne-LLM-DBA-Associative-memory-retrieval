## 二、A 级：已在生产发生的故障

### A1. ✅ `KeyError: 'from'` 使整个 Add 请求失败（`graph_builder._resolve_edge_ids`）

**这是本次审查最有价值的发现：不是推测，生产日志里有完整栈。**

```
2026-09-26 06:22:18,172 ERROR alm: Add 处理失败 user_id=u_f5***a0b4 error_id=ee0d278b
  File ".../alm/engine.py", line 235, in add
    stats = space.add(request.messages)
  File ".../alm/space.py", line 644, in add
    result = self.dba.maintain(conversation, timestamp=grp_ts)
  File ".../dba_pipeline/extraction/dba.py", line 561, in maintain
    result2 = self.builder.apply_ops([], edge_ops)          # ← 只写边的分支
  File ".../graph_builder.py", line 222, in _apply_ops_impl
    resolved_edge_ops = self._resolve_edge_ids(edge_ops or [], id_mapping)
  File ".../graph_builder.py", line 587, in _resolve_edge_ids
    op["from"] = id_mapping.get(op["from"], op["from"])
                                ~~^^^^^^^^
KeyError: 'from'
```

**根因**：`_resolve_edge_ids` 用 `op["from"]` / `op["to"]` **直接取值**，且这一行**不在任何 try 内**
（`_apply_ops_impl` 外层只对节点分支做 rollback+break）。LLM 只要吐出一个缺 `from` 的边对象，
整个 `maintain` 抛出 → `alm/server.py` 的 add 处理器捕获后返回 5xx。

**为什么畸形对象能走到这里**：`dba.py` 的"截断挽救"（`_salvage_truncated_ops`）只保证**花括号成对
且自身是合法 JSON**，**不校验字段完整性**。所以"救回来的对象缺 `from`"是必然存在的形态。

**代价**：该批内容**完全未落库**（连兜底都没走——异常直接冒到 server），平台收到 5xx 后重试；
重试若再次产出同样的畸形 op，就会**重复失败**。日志里 16 轮只出现 1 次，属低频但**确定性**故障。

**改法**：`_resolve_edge_ids` 改用 `op.get("from")` / `op.get("to")`，缺键的 op 计入 `skipped`
（这条路本来就有 skip 语义）；`maintain` 对边步骤加 try 兜底，失败也走 `no_ops → _divert_raw`
把内容转入文档通道，而不是让整个请求 5xx。⚠️（改法为我的建议，未实施）

## 三、B 级：会导致错误结果

### B1. ✅ 补边时 `is_reverse` 被丢弃，**因果方向可能整条反掉**

```python
# retriever.py:925
for nb, rel_type, _is_reverse in self.graph.get_neighbors(nid):   # ← 第三项被丢弃
# retriever.py:939-941
return [{"from": frm, "to": to, "rel_type": rel_val, "is_reverse": False} ...]
```

`get_neighbors` 对**双向边会以两个方向各出现一次**（代码自己的注释在 L929-930 说了这点）。
对一条**有向边 A→B**，当遍历先命中 B 时拿到的是 `(A, rel, is_reverse=True)`，
但输出被硬编码成 `from=nid, to=nb, is_reverse=False` → 变成 **`[B] --rel--> [A]`**。
而 L932 的 `if pair in seen or (nb, nid) in seen` 去重**只保留先遇到的那一个方向**。

→ **方向取决于节点在 `group` 里的遍历顺序**，与图里真实方向无关。

**影响面**：`_augment_edges_from_graph` 正是"为补全因果链而加"的机制；种子层检索
（注释自述占线上 69.6%）是它的主力场景。**这直接命中 B2「因果链、路径与中间步骤恢复」**——
叙事里的因果被讲反，答案模型自然选错。

**改法**：透传真实方向，或统一按图的方向输出 `from/to`。⚠️（建议，未实施）

### B2. ✅ 文档通道的"分数"不是余弦，却与图余弦一起 `max()` 成 `best_cos`

```python
# dba_pipeline/embedding/store.py:457
1.0 / (1.0 + max(0.0, float(score)))      # score 是 FAISS 距离
# alm/space.py:1344-1346
doc_best = max((d["score"] for d in doc_nodes if d.get("score") is not None), default=0.0)
best_cos = max(graph_best, doc_best)      # graph_best 来自 _cosine()
```

**核验后的精确结论**（我原先"中等区间被系统性抬高"的说法不够准）：

`store.py:431-432` 的 docstring 自己写了 `relevance = 1 / (1 + distance)`，而 FAISS 返回的是
**平方 L2 距离**。对归一化向量 `L2² = 2 − 2cos`，代入得：

```
doc_score = 1 / (3 − 2·cos)

cos=0.30 → 0.417     cos=0.48 → 0.490     cos=0.60 → 0.556
cos=0.80 → 0.714     cos=0.90 → 0.833
```

→ 该映射**单调递增**（所以"越大越相关"成立，`max` 不是无意义），但**与 cos 不是同一把尺**，
且两者**在 cos ≈ 0.5 处交叉**：**cos < 0.5 时文档分被高估（0.30→0.417）、cos > 0.5 时被低估
（0.90→0.833）**。后果：
1. 检索日志的 `文cos=` 与 `图cos=` **不可比**；
2. `RetrievalStats.record_search(best_cos)`（标定 `abstain_cosine` 的唯一依据）被**两个尺度的
   混合分布**污染；
3. 一旦弃权改回 0.48/0.60：文档密集空间在 **cos<0.5 区更容易被误放行**、在 **cos>0.5 区更容易
   被误弃权**——**两个方向都会错**。

当前弃权是 0/0，所以暂时只伤观测。**重新开启弃权之前必须先统一尺度。**

### B3. ✅（两路审查独立报同一处）叙事缺失的兜底分支**恒不可达**，文档型查询会返回空数组

```python
# alm/space.py:1302-1311
for node_id, _peak_content in (result.get("peak_memories") or []):
    if node_id in self._doc_index:      # ← 永不成立
```

`peak_memories` 只由图节点构成；文档块（`extra_nodes`）只被拼进 StoryRank 的 `path`，
**从不回写 `peak_memories`**。所以文档块 id（`d*`）不可能出现在这里。

**触发**：文档通道取回内容 + StoryRank 生成失败（`stories` 为空）→ 循环只补图节点 →
`items` 可能为空 → 返回 `data: []`，**与"弃权"在平台侧无法区分**。
而这恰恰是注释声称要避免的失效（"不能静默返回空数组"）。

**改法**：兜底来源改为「图候选 ∪ 本次文档块」。⚠️

### B4. ✅ `_split_by_chars` 在 `budget <= 0` 时**死循环**（无日志、不返回）

```python
# alm/space.py:139-174（无入口守卫）
if len(text) <= budget: return [text]        # budget=0 且 text 非空 → False
...
end = min(start + budget, len(text))         # = start
floor = start + budget // 2                  # = start → 两个回看 range 均为空
chunks.append(text[start:end])               # 追加 ""
start = end                                  # start 不变 → 无限循环
```

**调用点**：`alm/space.py:571` `_split_by_chars(text, self.config.doc_chunk_chars)` ——
**直接把配置值传进去，没有 `> 0` 守卫**（`_split_add_batches` 那条路径有守卫，文档通道这条没有）。
`_env_int` 也不校验正负。

**触发**：`ALM_DOC_CHUNK_CHARS` 被配成 `0` 或负数，且该批被判为文档型 → **该请求永久挂住**
（占住线程池的一个 worker，直到进程被杀）。

**改法**：函数入口 `if budget <= 0: return [text]`，并对 `doc_chunk_chars` 做正数下限校验。⚠️

### B5. ⚠️ MCP 侧 `triage` 默认开启且**没有 `_divert_raw` 兜底** → SKIP 即丢内容

> **核验后降级**：这不是"漏改"，而是**文档化的设计取舍**——`dba.py:432-435` 与 `:810` 明确写了
> "保留本方法与下面的长度闸，是为了 MCP 侧（默认 `triage_enabled=True`）行为不变……
> 这段判断对**短寒暄**仍然有效"。所以分叉是**有意**的。
> **但两点仍是真问题**：

1. **MCP 侧 SKIP 无兜底**：ALM 侧 SKIP 会经 `_divert_raw` 转文档通道；MCP 侧 SKIP 后调度器
   当"空转跳过"，缓冲区已清空且**无任何落库** → 内容静默丢失。**该行为未写进 MCP 契约文档**，
   使用方无从得知"某些输入会被丢弃"。
2. **闸门实测在其"有效范围"内也在误判**：日志里
   `DBA 维护: triage 判定跳过（对话 1047 字符）` 跨 9 轮共 **300 次** ——
   **1047 字符的对话**（远超"短寒暄"）被判 SKIP。所以"只对短寒暄有效"这个前提在实测里不成立。

**建议**：MCP 侧补一个 `_divert_raw` 式兜底；并把"哪些内容可能被丢弃"写进契约文档。 ⚠️

### C2. 🔥 **目的推断有 ~8% 的系统性失败率，失败时静默回退默认目的**
> 这条是**跨 16 份日志横向扫描才浮出来的**，单轮看只是零星 WARNING。

```
×57  16 轮（09-23 05:01 ~ 09-27 05:32）  目的推断 JSON 解析失败（响应长度 3），按默认目的处理
```

**每轮约 3.6 次**，且失败形态**高度一致**——`响应长度 3`，对应 `alm.tokens` 里
`LLM #256: in=291 out=2`（输出仅 2 个 token）。这不是随机抖动，是**该 prompt 与模型组合的
系统性退化**。

**失败后的回退**是 `{"purposes":["理解"], "condense": false, "state": false}` —— 于是
**`condense`（压缩）/ `state`（当前值）/ 时序路由同时失活**。这**部分解释了此前的困惑**：
某轮 `压缩=是` 只有 1/46，"时序路由召回太低"未必是判定质量差，而可能是**推断根本没跑成**。

**改法**：推断失败时重试一次；并对 `out <= 5 token` 直接判为失败并记录专门计数（现在
只能靠 WARNING 文本反推）。⚠️

### C3. ⚠️ QA 反馈护栏只作用于 `payload`，超出 `max_messages_per_add` 的部分未过滤

```python
payload = messages[:limit]; overflow = messages[limit:]
feedback = [m.content for m in payload if _is_qa_feedback(m.content)]   # 只看 payload
payload = [m for m in payload if not _is_qa_feedback(m.content)]
```

若 QA 反馈落在第 65 条起，它会经 `overflow → _divert_raw() → _store_documents()`
**作为文档块入库**，且不产生 `[IO] qa_feedback` 留痕。实测平台每次只回写 1 条且紧跟 search，
**很难触发**，但逻辑上有洞。

**改法**：把过滤提到 `payload/overflow` 切分**之前**（对整批过滤后再切片）。⚠️

### C4. ⚠️ `used` 与实际正文不自洽，`采纳` 这一列会被读偏

- 模型自报 `used`（可选整数），可能给 40/45/60，而正文被硬截断到 2000 字符时**实际写进去的
  远少于这个数**（实测 `采纳=40` 的返回正文只有 806 字符）。
- 降级分支 `used = len(picked)`（取前 40 条），但拼接结果被 `[:2000]` 截断，**同样不自洽**。

→ `采纳=` 现在只能当"**模型自报做了减法**"的粗指标，**不能当准确条数用**。
在记录里必须明确这一点，否则又会误判"选择层生效了"。

### C5. ⚠️ 语言约束的**粒度冲突**：user 指令要求"整批同一种语言"，system 原则要求"按各自原文段"

- user 侧（`dba.py:56-60`，注入到 `_LANGUAGE_DIRECTIVE`）用 `source_language(整段 conversation)`
  判一个语言，要求整批 `content` 同语言；
- system 侧原则 7（`dba.py:106-109`）明确"同批含多种语言时**以该条事实所在原文段为准**"。

中英混排批次上两者给出**不同要求**。且**日志里没有记录"入参语言"**，所以
"语言错配率"这个指标**无法自证**（见 §5.3）。⚠️

### C6. ⚠️ QA 反馈留痕被 `trace_io` 绑死 → Full 评测期会丢掉唯一的题目归属信道

建议拆成**不含正文、不含题面**的独立日志（只留平台自己的题号与分数）。⚠️
