# 写链成本优化与模型迁移计划（gpt-4o-mini 赛道）

> 起因：2026-09-30 Full 首跑在 **12%（1,119 题）** 处因成本与资源双重压力中止，账单 **≈¥151**；按同一结构外推全量（9,000 题）会到 **¥1,500~2,000+**，超出预算。
> 本计划同时处理两件事：**① 把写链成本压到可承受区间；② 迁移到 gpt-4o-mini 赛道**（模型替换会改变缓存经济学，二者必须一起设计）。

---

## 一、结论先行

| 口径 | 每 1,119 题 | 全量 9,000 题 |
|---|---|---|
| 当前实测 | **¥151** | **¥1,500+**（含检索约 ¥2,000） |
| 只改提示词（本轮讨论过的"省 50%"） | ¥75 | ¥750~1,000 ❌ 仍超预算 |
| **改调用结构（P0 项）** | **¥15~25** | **¥150~250** ✅ 可接受 |

**关键判断：50% 是"在现有调用结构里微调"的上限；真正没被动过的乘数是「调用次数/题（44 → 6~8）」。** 换 gpt-4o-mini **本身不省钱**（其缓存折扣只有 2 折，而 deepseek-flash 命中价是未命中的 1/50），所以结构优化必须照做。

## 二、实测基线（全部来自账单 CSV 与线上日志）

账单口径（2026-09-30 16:00–24:00，key `mcp`，占账单 99%；`pic` 仅 ¥1.3）：

| 指标 | 值 |
|---|---|
| 请求数 | **49,288**（/ 检索 1,119 = **44 次调用/题**） |
| 输入·未命中 | **74.6M tok** → ≈ **¥75（占总账单 49%）** |
| 输出 | **18.6M tok** → ≈ **¥74（占 49%）** |
| 输入·命中 | 42.2M tok → ¥0.8（**命中率仅 36%**） |
| 单价 | 命中 ¥0.02/M、未命中 ¥1/M、输出 ¥4/M（18:00 后为对折价；之前 ¥0.04 / ¥2 / ¥8） |
| 平均每次 | 输入 2,370 tok、输出 377 tok |

资源侧（同一次全量）：

| 指标 | 值 | 说明 |
|---|---|---|
| `/data` | **2.5 GB（12% 进度）** | 单空间 `.index` **33~131 MB** → 按 4 KB/条算 ≈ **0.8~3.3 万条向量/空间** |
| 容器内存 | 1.70 GiB（宿主仅 3.8 GiB、无 swap） | 宿主一度只剩 941 Mi 可用 |
| 单文件日志 | **84 MB** | `trace_io=1` 时写满一次轮转仅约 60 秒 |
| 磁盘 I/O | BLOCK I/O **14 GB** | [store.py:527-536](../../dba_pipeline/embedding/store.py#L527) 每次保存**全量重写**索引 + 未压缩 `savez` |

## 三、成本模型

```
成本 ≈ 每次调用的(固定前缀 + 变动内容) × 调用次数
     = 44 次/题 × 2,370 tok/次 × 64% 未命中率 × ¥1/M   +   44 × 377 tok × ¥4/M
       └────────────── 输入 ¥75 ──────────────┘          └──── 输出 ¥74 ────┘
```

两个乘数**相乘**：`调用次数`（44）与`单位输入成本`（未命中率）。当前两者都未优化。

## 四、优化清单

### P0-1 埋点（**没有它，后面所有优化都无法验收**）

| 项 | 改动 | 文件 |
|---|---|---|
| 缓存命中 | `extract_usage` 补 `prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens`、`prompt_cache_miss_tokens`；日志打 `in=… hit=…`，汇总加"命中率" | [alm/tokens.py](../../alm/tokens.py) |
| 调用身份 | 各调用点打标签（LangChain `with_config(tags=[...])`）：`extract` / `maintain` / `triage` / `purpose` / `story`；日志增加 `role=` 列，汇总**按侧**出 token 与成本 | [alm/tokens.py](../../alm/tokens.py)、[dba_pipeline/llm/inference.py](../../dba_pipeline/llm/inference.py) |
| 成本口径 | `ALM_PRICE_*` 按赛道真实价目覆盖（deepseek: ¥1/¥4 折后价、¥2/¥8 标准价；gpt-4o-mini: $0.15/$0.60，缓存输入 $0.075） | [alm/config.py](../../alm/config.py) |

> 现状缺陷：计量器是**进程内累计**，容器一重启就归零（本次账单 49,288 次请求，计量器只记到 8,241 次 = 17%）。埋点后以**账单为准、计量器为辅**。

### P0-2 合并 triage 与抽取（调用数 ÷2）

现状每个批次各调一次：`triage`（判是否建图）+ `extract`（抽取）+ `maintain`（边/摘要）。
**改法**：`triage` 的判定并入 `extract` 的输出——让抽取调用顺带返回 `skip: true/false`，判空即不建图。保留原有"跳过率"语义（本次线上 160 次跳过）。
预期：**44 → 22 次/题**。

### P0-3 放大批大小（调用数 ÷3~5）

现状 `add_batch_size=6 条 / add_max_chars=1500 字`（[alm/config.py](../../alm/config.py)）——对一个**整段对话**来说批次过碎。
**改法**：结合 P0-2 后按"字符数为主、条数为辅"设批（如 `add_max_chars=6000`、条数上限放宽到 20~30），并同步提高 `max_messages_per_add`。
预期：**22 → 6~8 次/题**（合计 P0-2+3 后为原来的 **1/6**）。

### P1-1 前缀稳定化（提缓存命中率，输入侧再降）

要求：**静态内容（规则 / few-shot / JSON schema）逐字节稳定且位于最前**，任何动态内容（题面、节点正文、时间、随机 id）**一律置于其后**。
现状命中率仅 36%，说明前缀被污染或调用过于分散。
⚠️ **赛道差异**：deepseek 命中价是未命中的 **1/50**（提升命中率收益极大）；gpt-4o-mini 仅 **1/2**（收益有限）。故在 gpt-4o-mini 赛道，**P0-2/P0-3 的优先级高于本条**。

### P1-2 输出瘦身（输出占 49%）

- 抽取与判定的输出改**紧凑 JSON**（无缩进、无解释性文字、字段名缩写）；
- `edge_ops` **拆批**：单次曾产出 `out=32768` 撞顶（`截断=1`），既浪费又丢边；
- StoryRank 的"缩喂重试"已有护栏（本版硬截断 8→0），保持。

### P2 存储与索引（解决 2.5 GB / I/O 14 GB）

| 项 | 改动 | 预期 |
|---|---|---|
| 向量 dtype ✅ | 写盘前 `astype(np.float32)` | 索引**砍半** |
| ~~npz 命名 bug~~ ❌**已证伪** | 原写「`content_vectors.npz` 是固定文件名、全空间互相覆盖」——**实测不成立**：`save(path)` 的 `path` 是索引**目录**，`dirname` 得到的是 `<user>.index/`，早就每空间独立（见 版本变更记录 §4.19.1） | **撤销此项**，不改命名 |
| 索引写方式 ✅ | `save_local` + `savez` 每次**全量重写** | 已完成：**索引不落盘** + `path/vectors/*.npz` 追加式分片（墓碑/后写覆盖/碎片超限才 compact） |
| 文档块 | 块 1800 字、每次只召回 `8±1` 块 | 放大块（4000~6000 字）或对超长文档限量存块 |

### P0-4 数据体积（容器建图 data）——**本次中止的直接原因之一，由 P2 提级**

**基线**：`/data` **2.5 GB / 12% 进度** → 全量外推 **≈20 GB**，宿主机 40 GB 盘必死。
**构成**：单空间 `.index` **33~131 MB**（≈0.8~3.3 万条向量 @4 KB；而一个空间的图只有几百节点 → **绝大部分是文档通道的分块**）。

| 改动 | 预期 | 风险 |
|---|---|---|
| 向量写盘前 `astype(np.float32)` ✅**已完成** | 索引**砍半** | 无 |
| ~~`content_vectors.npz` 改 `<user_id>.npz`~~ ❌**已证伪，撤销**：现实现早就是每空间独立的 `<user>.index/` 子目录（版本变更记录 §4.19.1） | — | — |
| 索引**增量写**（原每次全量重写，BLOCK I/O 已 14 GB）✅**已完成** | I/O ↓90%+（待平台复核绝对量） | 无 |
| 索引**不再落盘**（新增项）：`save_local` 的 docstore 把全部正文 pickle 成 `index.pkl`，是盘上**第三份**正文 ✅**已完成** | 单空间索引体积显著下降 | 无（load 用向量在内存重建，recall 不变） |
| 文档块策略：块 1800→4000~6000 字 | 块数 ÷2~3 | 低（粒度略粗） |
| 超长文档**限量存块** | 进一步 ↓ | **中**（须单独验证召回） |
| 每轮跑完 `alm.cleanup` | 防跨轮累积 | 无 |

**验收**：200 题增量 `/data` ≤ 200 MB；全量峰值 ≤ 6 GB。
**守护指标**：文档通道轨道的召回条数与命中率（不得下降）。

### P0-5 日志体积——**同样由 P1 提级**

**基线**：`trace_io=1` 时**单文件 84 MB**、约 60 秒写满一次轮转（100m×10）；单条 `[IO]` 含完整题面+正文可达数 MB。

| 改动 | 预期 |
|---|---|
| `ALM_TRACE_IO=0`（仅保留不受其控制的 `[QA]` 行） | 写量降一个数量级 |
| **留痕截断**：trace 站点对 query / 选项 / 正文各截 N 字符（默认 4000，可配） | 单条记录有界，grep 可用 |
| 轮转上限按窗口设定（如 `100m × 10`），并在跑完做快照后清空 | 磁盘有界 |
| 关留痕后按 `truncate + rm 轮转文件` 清理（勿用 `rm` 删当前文件） | 空间立即回收 |

**验收**：单文件 ≤ 5 MB/轮；全轮日志总量 ≤ 500 MB。
**守护指标**：`[QA]` 行必须完整（题目归属与分数是唯一不可失的信道）。

## 五、模型迁移：deepseek-flash → gpt-4o-mini

### 5.1 差异与必改项

| 项 | deepseek-flash（现状） | gpt-4o-mini | 动作 |
|---|---|---|---|
| **最大输出** | 32768（已设） | **16,384** | **必须下调**，否则请求 400 |
| 缓存语义 | 自动，命中价 **1/50** | 自动，前缀 ≥1024 tok，命中价 **1/2** | 优先级重排（见 P1-1 注） |
| 单价 | ¥1 / ¥4（折后） | $0.15 / $0.60（缓存输入 $0.075） | 覆盖 `ALM_PRICE_*` |
| 上下文 | 64k+ | 128k | 无风险 |
| 中文叙事 | 强（当前提示词为中文） | 明显弱于 deepseek | **规则 1~12 需英文化或补英文示例**；本赛道语料（locomo / scriptMem）本身为英文，风险可控 |
| JSON 稳定性 | 较高 | 略低 | 保留 `_STORY_RETRY_NOTICE` 与解析兜底；抽测 20 次 JSON 成功率 |
| thinking 参数 | `thinking=关`（banner） | 不适用 | 迁移时确认不再下发该参数 |
| 并发/限流 | — | 有 TPM/RPM 限 | 200 题定标跑时观察 429 |

### 5.2 迁移不省钱的算术（必须写进预期）

| 口径 | gpt-4o-mini（现结构，44 次/题） | 结构优化后（7 次/题） |
|---|---|---|
| 每题输入 | 104k tok → $0.0157（无缓存）/ $0.0086（90% 命中） | 16.5k tok → $0.0025 / $0.0014 |
| 每题输出 | 16.6k tok → $0.0100 | 2.6k tok → $0.0016 |
| **每题合计** | **≈$0.026 / $0.019 ≈ ¥0.19 / ¥0.14** | **≈$0.004 ≈ ¥0.03** |
| **全量 9,000 题** | **≈ ¥1,230~1,680** ❌ | **≈ ¥260~300** ✅ |

**结论：换模型不解决预算问题；P0-2 / P0-3 才是决定性动作，且对两个赛道同样有效。**

## 六、开发流程：**本地估算 → 平台烟测 → 才谈全量**（本轮确立）

**原则：所有优化先在本地用离线脚本估算，达标后再上平台跑烟测；平台只用于"验证"，不用于"试错"**——本次 ¥150 就是"在平台上试错"的代价。

### 6.0 第一步：本地脚本估算（不消耗平台额度）

本地具备完整的离线条件：`eval/.cache/alm_data_r3`（现场 4 空间快照，含真实图与生产向量）、`dba_pipeline` 全链路可脱离 HTTP 直接调用、`alm/loadtest.py` 可做并发压测。

**必须产出的数字（每项优化前后各一组）**：

| 维度 | 指标 | 取自 |
|---|---|---|
| 成本 | 调用次数/题（**按 role 分侧**）、缓存命中率、输入/输出 token、折算 ¥/百题 | 埋点（P0-1）+ 本地 harness |
| 数据 | 每空间 `.index`/`.npz`/`.docs.*` 字节数、增量 `/data` 每百题 MB | 落盘目录直接统计 |
| 日志 | 每百题日志字节数（`trace_io` 开/关各一次） | 捕获 stdout 计数 |
| 质量（守护） | 边/节点比、`跳`分布、triage 跳过率、精确轨喂入点数、文档通道召回条数 | 链路内部读数 |

**本地门槛（不达标不上平台）**：调用次数/题 ≤ 8、¥/百题 ≤ ¥3、每百题数据增量 ≤ 100 MB、每百题日志 ≤ 50 MB（`trace_io=0`）。

### 6.1 第二步：平台烟测（小样本验证）

本地达标后，用**平台的小样本轮次**（如 200 题）只做一件事：**确认本地估算在生产环境成立**（并发、真实语料分布、网关限流）。烟测通过才允许开全量。

## 八、风险与回滚

| 风险 | 影响 | 对策 |
|---|---|---|
| 批放大后抽取质量下降 | 边变少、图变稀 | 定标跑对比"边/节点比"与 `跳` 分布；必要时降到 8~12 条/批 |
| 合并 triage 后跳过率失控 | 该建图的没建 | 保留跳过计数指标，超出历史区间（本次 160 次）则回滚 |
| 前缀英文化影响中文场景 | 叙事质量 | 保留中英双版规则，按赛道切换 |
| gpt-4o-mini JSON 失败率上升 | 重试增加成本 | 抽测 20 次；失败率 >10% 则回滚模型 |
| 结构改动引入回归 | 正确性 | 79 条单测 + 200 题定标；镜像按版本号保留可回滚 |

## 九、执行顺序

1. **P0-1 埋点**（含价格口径）→ 打一个镜像，**先只跑 200 题**拿基线；
2. **P0-2 合并 triage/抽取** → 200 题，看"调用次数/题"是否减半；
3. **P0-3 放大批** → 200 题，看是否到 6~8 次/题、成本是否到 ¥0.03/题；
4. **P1-2 输出瘦身 + edge-ops 拆批** → 消除 `out=32768`；
5. **P1-1 前缀稳定化**（deepseek 赛道优先，gpt-4o-mini 赛道可选）；
6. **P2 存储**（向量 float32 + npz 独立命名 + 增量写 + 文档块限量）；
7. 达标后开全量；否则回到第 2 步继续压。

> 每一步都是"改一件、200 题验证、记录数字"，避免再出现"跑到 12% 才发现撑不住"。
