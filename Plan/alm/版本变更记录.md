> **用途**：记录 ALM 接入过程中各轮的**实际改动集**。既是内部回溯依据，也直接服务提交材料的

## 二、按轮次的变更集

### 轮次 1（0919 收口）— 自托管上线与契约收口

来源文档：`0910——ALM测评接入计划.md`（该文档是滚动账本，§6 与 §7.x 记录了 0910–0920 多批工作）。

**① 自托管部署链（新建）**
- 新增顶层 `alm/` 服务端模块：`config` / `contract` / `engine` / `space` / `server` / `smoke` / `judge` / `cleanup` / `loadtest` / `tokens`
- 新增 `Dockerfile.alm`、`docker-compose.alm.yml`、`.env.alm`（ALM 专用，与根 `.env` 隔离）
- 独立变量 `ALM_EMBEDDING_LOCAL`（默认 `false`）——避免 compose 用根 `.env` 的 `EMBEDDING_LOCAL=1` 插值，把 GB 级本地模型拖进镜像
- 安全闸：非回环监听且 `ALM_API_KEYS` 为空时**拒绝启动**（不是放行）

**② 契约与输出形态**
- `search` 显式 `with_response=False`（省一次 LLM；主办方把 Search 阶段生成答案划为红线）
- `/search` 收拢为**只返回叙事一条**（叙事缺失时退回采纳节点原文，避免与「弃权」混淆）
- 输出加节点类型前缀（`[status] …`），类型信息是 A/B 维度判断「是事实、偏好还是情绪」的依据
- 补 `created_at`（`_node_created_at()`，`YYYY-MM-DD`，无时间戳不输出）——平台 Answer 模板要求相对时间换算
- `add` 返回的 `messages` 改为「收到的总条数」；三个 ID 逐字节回显

**③ 弃权（两段式，替换单一阈值）**
- 新增 `alm/judge.py`；硬下限 `abstain_cosine` 0.52 → **0.35**，模糊带上界 `abstain_verify_hi`=**0.50**，`judge_top_n=3`
- 依据：探针实测「有答案 / 无答案」两类余弦区间重叠，单阈值必然错一边；两段式做到 A 召回 95% / H 准确 100%

**④ 健壮性（§7.9 十项审查修复）**
- 空间租约 `_lease()`（`add`/`search` 登记在用计数，`_evict_locked` 跳过在用空间）
- 按 `request_id` 幂等缓存（LRU 8192），收紧 `_should_fallback`
- `search()` 全程持空间锁（并顺带解决 `path_tracker.start_session()` 不持锁问题）
- `best_cos` 改在 T1–T4 **完整并集**上计算
- 兜底节点上限 `fallback_max_nodes` 64 → **256**，超量走兜底落库 + WARNING
- 500 响应只回传 `error_id`；叙述 id 空集合时退回正文派生

**⑤ 持久化与写放大**
- FAISS 索引随 YAML 落盘：`<user_id>.index/` 独占子目录 + 「节点集合指纹」校验，不一致回退重建
- `store.py` 的 `np.savez` 改回不压缩（读写只发生在载入，换取写盘更快）

**⑥ 合规**
- `_configure_logging` 显式把 `dba_pipeline` 钉在 **WARNING** 以上（该 logger 可能打印节点内容节选）
- 新增 `alm/cleanup.py`（`--older-than-days 30`，默认预演）+ 注册控制台脚本；文档写明「必须先停服再清理」与 `_dirty` 不变量

**⑦ 观测与工具**
- `RetrievalStats`：每次 Search 记录候选最高余弦与弃权与否，进程退出打印分位数（只含数值）
- `alm/loadtest.py`（并发-延迟-成本压测）、`alm/tokens.py`（TokenMeter + `ALM_PRICE_*` 单价覆盖）
- 开关 `ALM_RENDER_TIMESTAMPS`（默认 `0`）

## 三、本轮详细：语言错配与 embedding 更换

### 3.1 起因：平台语料是英文，我们的链路是中文

平台 smoke 的留痕（`ALM_TRACE_IO=1`）实测语言构成：

| 环节 | CJK 占比 |
|---|---|
| add 入参正文 | 24.5% |
| add 落库节点 | **50.8%** |
| search query | **1.2%**（46 条里 42 条纯英文） |
| search 返回正文 | **74.9%** |

**输入是英文、存储是中英混杂、输出是中文，而提问是英文。** 抽取把英文记忆改写成了中文，
embedding 又是中文专用模型 `bge-large-zh-v1.5`——跨语言余弦失配贯穿全链路。

### 3.2 四处 prompt 的语言硬约束

| 位置 | 约束 |
|---|---|
| `NODE_EXTRACTION_PROMPT` | 新增原则 7：content 必须用源对话语言、**禁止翻译**；并声明「示例中的中文只是示意写法」 |
| `PURPOSE_INFERENCE_PROMPT` | 去掉硬编码的中文目的词表，改为「purposes 必须与用户消息同语言」 |
| `EDGE_LINKING_PROMPT` | `reason` 等自然语言字段用源语言 + few-shot 免责说明 |
| `_STORY_RANK_SYSTEM` | 顶部加「输出语言（硬约束）」，四个 prompt 变体共享 |

> 四条**必须一起改**：只把节点改成英文而 purposes 保持中文，会让目的向量与英文节点的余弦**更差**，
> 反而放大目的过滤的误杀。

### 3.3 Embedding 更换与索引失效安全阀

- 模型：`BAAI/bge-m3`（多语，**1024 维**，与 bge-large-zh 同维）
- 落点 7 处：`.env`、`.env.alm`、`.env.example`、`docker-compose.alm.yml`、`Dockerfile.alm`、
  `store.py::LocalEmbeddings` 默认、`viz/chain_runner.py` 默认
- ⚠️ **同维正是危险所在**：`<user_id>.index/` 里存的是旧模型向量，而原指纹只认节点集合，
  换模型后会判定「一致」照常加载 → 旧模型节点向量与 bge-m3 查询向量混用，余弦全乱且**无任何报错**。
  已把模型名纳入 `MemorySpace._index_digest()`，换模型即自动回退重建，旧索引无需人工清理
- 已实测 SiliconFlow 端点接受 `BAAI/bge-m3` 并正常返回向量

### 3.4 四个余弦阈值重标

工具：`eval/probe_threshold_retune.py`（同一 API 端点、同一批中英对照样本，只换模型）。
结果（p50，单位余弦）：

| 类别 | bge-large-zh | **bge-m3** | 位移 |
|---|---|---|---|
| 目的 ↔ 直接相关 | 0.461 | 0.508 | +0.047 |
| 目的 ↔ **功能等价（必须放过）** | 0.402 | 0.456 | +0.054 |
| 目的 ↔ 无关 | 0.335 | 0.400 | **+0.065** |
| 查询 ↔ 有答案 | 0.712 | 0.730 | +0.018 |
| 查询 ↔ **无答案** | 0.479 | 0.552 | **+0.073** |
| 节点 ↔ 应去重 | 0.923 | 0.929 | +0.006 |
| 节点 ↔ **不应去重** | 0.858 | 0.902 | **+0.044** |

**关键不是「整体抬高」，而是「无关那一侧涨得更多」→ 两类间距被压缩**，旧值不只是偏移，是失效：

| 阈值 | 旧 | 新 | 依据 |
|---|---|---|---|
| `purpose_filter_threshold` | 0.2 | **0.30** | 必须低于「功能等价」类最低值 0.404（0.303→0.404）；这正是 0828 把 0.3 放宽到 0.2 的原因 |
| `abstain_cosine` | 0.35 | **0.48** | 「无答案」最低余弦 0.360→**0.506**，旧值落在这类分布**之下**，硬下限形同不存在 |
| `abstain_verify_hi` | 0.50 | **0.60** | 「无答案」最高余弦 0.520→**0.583**；若上界仍 0.50，无答案查询**全部越过上界** → 不进模糊带、不被拦 → 该弃权时不弃权，H 会崩 |
| `graph_dedup_threshold` | 0.85 | **0.92** | 「只改数值」的句子 p50 已到 0.902 → 会**成片误吞新值**，直接伤 D1 |

⚠️ 探针样本仅 14 组，这批值是**起点**。`graph_dedup_threshold` 的两类样本本身**有重叠**
（不应去重 max 0.948 > 应去重 min 0.915），单阈值分不干净，0.92 只是折中——根治要靠写侧改进。
全部走环境变量（`ALM_PURPOSE_FILTER_THRESHOLD` / `ALM_ABSTAIN_COS` / `ALM_ABSTAIN_VERIFY_HI` /
`ALM_GRAPH_DEDUP_THRESHOLD`），**改回不需重建镜像**。

## 四、写入路由：对话通道分批 + 文档通道隔离

起因：即使语言与阈值修好，B2 与 D1 仍为 0，而本地实验（k=6 批量、对话语料）成绩良好。
导出线上 220 个图文件逐一看结构后，定位到**两个独立的写侧病因**。

### 4.1 病因一：单次 Add 的消息没有分批（D1 写侧从不触发）

平台单次 Add 的消息条数（135 批实测）：`messages=20` 出现 **59 次**、中位 8、**>6 条占 54.1%**。

| messages | 批数 | 节点/条 | 含 update 批 | 含 deprecate 批 |
|---|---|---|---|---|
| 1-2 | 28 | **5.47** | 0/28 | 3/28 |
| 3-4 | 23 | 4.08 | 1/23 | 0/23 |
| 5-6 | 11 | 4.05 | 2/11 | 0/11 |
| 7-9 | 10 | 2.34 | **0/10** | **0/10** |
| 15+ | **62** | **1.21** | **0/62** | **0/62** |

**值变更（update + deprecate）只在 ≤6 条的批次里出现过，7 条以上一次都没有。**
全库 20495 个节点只有 70 个 `deprecated` = **0.34%**。

配套的 LLM 压力证据：抽取调用 `in` token 中位 2376、**max 21843**；`out` token 中位 622、
**max 8192（正是模型输出上限）**，并出现 `LLM 输出疑似被截断，已挽救 node_ops=0 edge_ops=343`
（整批丢节点、只救回边 → 边指向不存在的节点）。另有 8 次 `目的推断 JSON 解析失败（响应长度 3）`。

**修法**：`space.add()` 按 `ALM_ADD_BATCH_SIZE`（默认 **6**，对齐 `0828前置数据管理与后处理.md`
§5.5 的 M=6；MCP 侧走的是 `maintenance_scheduler.proactive_batch_size=6`，ALM 侧此前**没走**
这个调度器）切分，逐组调 `maintain()`。每组用自己的时间戳（比原来的整批时间戳更准）。

### 4.2 病因二：知识库式长文档被当成对话抽记忆（32 个零边图）

按 `thing`（兜底原文档块的节点型）占比分桶，关系是断崖式的：

| thing 占比 | 图数 | 节点中位 | 边/节点中位 |
|---|---|---|---|
| 0% | 84 | 8 | 1.42 |
| 0-20% | 54 | 300 | 2.10 |
| 60-99% | 12 | 202 | 0.81 |
| **≈100%** | **32** | 6 | **0.00** |

最大一个零边图：**289 个 `thing` 节点、0 条边**，内容是一整部易卜生《人民公敌》剧本
（`SCENE.—DR. STOCKMANN'S sitting-room…`）+ `scriptmem_official_exact` 的 QA 反馈。
平台把**整篇文档当一次 Add 灌进来**，抽取判 `no_ops`，兜底把原文切成 500 字块 →
孤立节点灌进图 → 被当成记忆种子 → 峰值落在 hop0 → `跳=1`。

**关键澄清**：这**不是语言问题**。判别性检验显示存在健康的英文图（442 节点 / 996 边 /
343 有向边，thing 仅 10%），也**不是"图规模"问题**——是**内容类型**问题：平台混了两类输入，
一类是对话记忆（本系统设计目标），一类是文档/剧本/任务轨迹。语言错配只是伴随现象。

**修法**：`add()` 入口按形态路由（`ALM_DOC_ROUTE`，纯计数、不调 LLM）：

| 形态 | 判据 | 去向 |
|---|---|---|
| 对话型 | 单条平均 < 500 字，或消息数 > 2 | 现有 DBA 链路（含 6 条分批） |
| 文档型 | 单条平均 ≥ 500 字 **且** 消息数 ≤ 2 | **文档通道**：切块 + 向量，不抽节点、不建边、**不进图** |
| 空内容 | 无有效文本 | 丢弃 |

判据有效性交叉验证：该刀切下去，**文档型 18 批里值变更 0 次，值变更 6 次全部落在会话侧**。

文档通道的存储与检索都与图完全隔离（`<space>.docs.yaml` + `<space>.docs.index/`）：
- 写侧 `_store_documents()`：按 `ALM_DOC_CHUNK_CHARS`（1800）切块、embed、按块序存；
- 读侧 `_document_lookup()`：向量 top-k + **相邻块扩展**（`ALM_DOC_NEIGHBOR=1`）——
  块序是文档唯一的"边"，"谁说了这句"这类问题往往需要跨块上下文；
- 取回的原文摘录经 `retrieve_with_story(extra_nodes=…)` 并入 StoryRank 的输入
  （只进 `path.nodes`、不进 `path.edges`），一次 LLM 调用统合叙事与原文证据。

**块大小 1800 是实测的**（`eval/probe_m3_limit.py`）：英文 16000 字仍 200；
中文 8000 字 200、16000 字报 400 code=20015。1800 对中英都安全且留足余量。

### 4.5 一轮补齐：分组双约束、语言注入、embedding 预算

本轮（2026-09-26）在 4.1–4.3 之上又补齐四处，全部经本地针对性烟雾验证。

**① 分组从"只限条数"改为"条数 + 字符双约束"**（`ALM_ADD_MAX_CHARS=1500`）

`add_batch_size=6` 只约束条数，而**条数不约束长度**：平台有"3~6 条一批、单条均长 505 字"
这类长消息对话，6 条就是 3000 字。实测（按线上 135 批反推）：

| 方案 | 组数 | 中位 | p90 | max | **>1500 字的组** |
|---|---|---|---|---|---|
| 只按 ≤6 条 | 292 | 583 | 1467 | **2934** | **26 / 292 = 9%** |
| 双约束 | 307 | 627 | 1328 | **1494** | **0 / 307** |

单条消息本身超预算时，在**该消息内部**按句末标点切（纯规则，不调 LLM），切分单元保持在
段落 / 句子粒度而非孤立小句——抽取原则 3 的指代消解需要这个上下文。
**为什么不加独立的 LLM 分句调用**：抽取 prompt 的原则 2（"一个事实一个节点"）本身就是
语义分句，它做不好的原因只是输入太长；加一次调用是把同一件事做两遍，成本翻倍且多一个失败点。

**② 语言约束改为注入到 user 消息末尾**（`dba.source_language` + `_LANGUAGE_DIRECTIVE`）

4.3 里"在 system prompt 顶部加英文硬约束"的做法**实测无效**：英文输入 + 生产模型
`deepseek-v4-flash`，**首批（图里还没有任何已有节点可供污染）依然输出中文节点**
（`用户是杭州一家互联网公司的后端开发工程师`）。判断原因是两条叠加——LLM 对**紧邻数据**
的指令遵循度高于 system 里的规则，而中文的指令正文与中文举例在持续"拉"它说中文。
故改为由代码判定源文语言，把指令拼到 user 消息末尾（近因位置），system 里的约束保留作兜底。

语言判定用**汉字占比 ≥ 10%**，不是简单比大小：英文几乎不含汉字（占比≈0），而中文常夹英文
专名（`我用 Go 和 PostgreSQL` 汉字 3 / 拉丁 12 = 20%，比大小会误判成英文）。

**③ embedding 单条预算 500 → 2000**（`store.OpenAIEmbeddings._MAX_CHARS`）

这是**上一轮引入的一个 bug**：`_call` 会把每条文本截到 `_MAX_CHARS`，而文档块是 1800 字
——于是**文档块只有前 500 字进了向量**，尾部永远检索不到，"放大块以保留语义完整性"这个
设计被静默截掉一大半。实测端点上限（`eval/probe_m3_limit.py`）：英文 16000 字仍 200，
中文 8000 字 200 / 16000 字 400。取 2000 对中英都安全且高于文档块大小。
同时把该值纳入索引指纹——它决定长文本向量是"全文"还是"仅前缀"，改它必须触发重建。

**④ `_split_by_chars` 补空白回退**

回看窗口内没有句末标点时，退而切在**最近的空白处**（原来是直接按预算硬切，会把单词劈成
两半——线上实测出现过 `[n2] n. You must include units…` 这种以半个词开头的块）。空白是
所有语言都有的词边界，严格优于硬切。

**⑤ `_TRIAGE_TRUST_MAX_CHARS` 1500 → 900**

依据：线上 9 次 triage 判 SKIP 的对话长度是 45 / 80 / 310 / 541 / 930 / 1019 / 1047 / 1381 / 1412，
其中 5 次（930~1412）都落在 1500 以下，triage 照跑照 SKIP，长度闸形同不存在。1500 是按离线
探测集定的，而那批对话中位 2522——**探针集里没有 1000~1500 这一段**，线上漏判却正好全挤在这里。
取 900 后语义更清楚：窗口覆盖 ≥56% 才采信 triage 结论。

### 4.7 打镜像前的全链路审查：修正一个会让指标倒退的判据

```

```

阈值扫描显示**长度这条路走不通**：抬到 3000 仍误吞 7 批、5000 仍误吞 4 批。原因是
"8000 字符的单条消息"到底是长对话还是文档，长度区分不出来——而已确认为文档的那些

故把分流点从"形态"改到"抽取之后"：

| 判据 | 作用 |
|---|---|
| `doc_chars_per_msg` **500 → 10000** | 只作**极端保护闸**（挡超大输入，别去打爆 LLM）。取值落在"实测最大可抽取单条 7987 字符"与"实测最小文档 1 万字符"之间 |

**副带修复的三项**（同一次审查发现）：

- **文档区索引缺一致性校验**（静默失效）：`_save_documents` 先写条文再存索引，中途中断会让条文
  比索引多；而 `_load_documents` 见索引存在就直接复用、不校验条数 → 多出的块永远检索不到且
  永不重建。已按 `ntotal == len(docs)` 校验，不等即重建，且重建时换**全新** `VectorStore`

- **本地路径的 bge-m3 可用性**：根 `.env` 原为 `EMBEDDING_LOCAL=1`，而本地只缓存了
  bge-large-zh-v1.5，换 bge-m3 后配合 `HF_HUB_OFFLINE=1` 会**直接报错**。已改为 `0`（走 API，
  与线上一致），并在注释里写明要用本地模型需先联网下一次。
- **合规声明的落盘清单陈旧**：`docker-compose.alm.yml` 里仍写"记忆只在 /data 下落盘
  （`<user_id>.yaml` + `<user_id>.index/`）"，现为**四份**（多了 `.docs.yaml` / `.docs.index/`）。
  这条是给主办方的留存条款说明，必须准确。

**审查中确认无误的项**（不再改动）：`Dockerfile.alm` 的模型预下载是条件性的（默认不下载，构建不受影响）；
compose 刻意不在 `environment:` 透传 `EMBEDDING_MODEL`（透传会插值成空串反而清掉 `.env.alm` 的值）；

### 4.9 平台侧首轮复验暴露的两个问题（均为 4.2/4.7 引入）

2026-09-26 平台冒烟（134 批写入 / 46 次检索）分析后确认修掉两项。**先说成功的三项**：
语言（落库节点 CJK 中位 **0.0%**、含中文 39% = 入参 39%，改造前是 24.5% vs 50.8%）、
边型（**有向边 52%**，改造前 30.6%；causal 2014 = 40.7%，改造前 21.9%）、值变更（update 8→18）。
双约束也确认生效：`分批` 与 `max(ceil(msg/6), ceil(chars/1500))` 一致率 93%（134 批）。

**问题 A：分批把 triage 重新拉回来了（两处改动相互抵消）**

```
421 个组里 173 个被 triage 判 SKIP = 41%
兜底率 11.1% → 50.7%（兜底=triage 173 次，no_ops 仅 2 次）
```

机制：`_TRIAGE_TRUST_MAX_CHARS` 是"超过它就绕过 triage 直接抽取"。改造前整批 2000~3000 字
> 1500 → triage **从不参与**；分批后组均 ~500~1000 字 → 落回 900 以下 → **triage 重新参与**
→ 41% 的组被判 SKIP → 内容经 `_divert_raw` 转出图，图只拿到约 59%。

修法：`MemoryDBA(triage_enabled=...)` 新增开关，**ALM 侧默认关闭**（`ALM_TRIAGE=0`）；
MCP 侧不经 `ALMConfig`，其默认仍是 True，行为不变。判断依据是"triage 的错判不在窗口覆盖率上"
（实测 113 字符、覆盖 100% 的组仍误判 SKIP），且 ALM 数据全为评测对话、"值得存"先验极高。

**问题 B：弃权门看不见文档证据（4.7 把内容移出图时留下的漏洞）**

```
弃权率 1/46 → 9/46 = 20%
其中 6 个空间同时出现「文档通道取回」与「弃权」
  u_40***7f55: 文档通道取回 23 块 → 弃权: best_cos=0.5386
```

根因：`best_cos` 只由 `_collect_par_candidates(result)`（图候选）算，**文档通道的命中不在其中**
→ 文档密集空间的 `best_cos` 被系统性低估 → ① 可能触发硬下限直接弃权；② 更多 query 落进
`[0.48, 0.60)` 模糊带 → 判定调用与弃权都变多。

修法：`best_cos = max(图候选最大余弦, 文档通道直命中最高分)`（邻块扩展项的 score 为 None，
不作为命中证据）。`检索` 日志行同步加上 `图cos=` `文cos=` `文档块=`，便于下次直接看两项各是多少。

**刻意没动的两项**（避免同时改多个变量）：
- **弃权阈值 0.48/0.60**：9 次弃权的 best_cos 是 0.4875/0.5709/0.5686/0.5289/0.5796…，全部
  高于硬下限、走的是模糊带判定。但 B 修好后 best_cos 会整体抬高、弃权率应自然下降，
  **先看 B 的效果再决定是否下调**。
- **`doc_lookup_k=8`**：经邻块扩展（±1）放大到约 24 块（单次最多取回 23 块 ≈ 41,000 字符），
  是新的 token 大头。是否降到 4~5 待单独 A/B。

**成本确认**（符合分批的预期）：LLM 调用 381 → **839（2.2x）**；in token 合计 **1,612,627**；
per-call in 中位 2376 → 1922 ↓；被截断告警 8 → **1** ✓；JSON 解析失败 8 → **5** ✓。
A 修掉后还会少掉 173 次 triage 调用。

**修复后的本地复验**（`eval/smoke_local_d1b2.py`，真实 LLM）：


### 4.10 B2 恒为 0 的机械根因：StoryRank 的输出契约在规模上不可满足（0926）

**起因**：平台复验（同日第二次）里 B2 仍是 **唯一恒为 0、且一次"运气分"都没有**的能力项，
而 D1 还有小波动。这个形态不像质量问题（judge 判分下总会有偶然部分分），像**机械性失败**。

#### 4.10.1 第一步：把弃权排除掉（0910 §7.7 规划却从未执行的上界实验）

弃权在本项目里是**被重新引入**的：0818（LiFEMem）已把它定论为**错误设计**
（"无使用场景，检索器/评测层无需拒答能力……**不做实现**"，见
[0818——LiFEMem实验总结与发现 §9](0818——LiFEMem实验总结与发现.md)）；0910 引入 ALM 时的
唯一依据是一句文档转述——把 H 维度的"**最小披露**"误读成"库里没答案时拒答"。
本轮拿到平台 H 的细分项后确认：**H = 认识论安全与隐私，子项 H2 = 敏感信息最小披露/隐私**，
是**隐私行为**维度。而弃权只吃 `best_cos` 一个数，既看不到 query 的隐私语义，也看不到返回
内容是否越界披露——**结构上不可能服务 H2**。且阈值（0.48/0.60）从未在英文、也从未在
bge-m3 上定稿（探针集是 14 组中文样本）。

改法（`ALM_ABSTAIN_COS=0` + `ALM_ABSTAIN_VERIFY_HI=0`，两段串联须一起置 0）后复验：

| | 旧轮 `8ae7…` | 新轮 `a5e0…` |
|---|---|---|
| 弃权 | 8 次 / 46 | **0 次** |

**证据 4 —— 输出契约本身就是不可满足的**

```
   adopted_ids；没写进正文的节点一律不得列入。二者不一致视为输出错误。
```

在 443 节点规模上，这等于要求：`story` 覆盖 443 条中文节点（≈12,000+ token）
**加上** 443 个 id 的 JSON 数组（≈1,200 token）——合计 **≈13,000+ token > 8192**。
所以降级不是偶发，**是必然**。

**证据 5 —— 本该做"减法"的两层都没在做**

#### 4.10.3 根治前先确认一件事：8192 是可调的吗

| **off** | **不传** | **length** | **8192** | 13,689 |

### 4.11 追根：真正的病因是"叙事替 answer 模型下结论"（0927）

§4.10 把 B2 恒零归到"输出契约在规模上不可满足"，方向对，但**只说到一半**。本轮把范围收窄到
最小可证的一点，同时修正 §4.10 的一处技术误判。

#### 4.11.1 修正 §4.10：`max_tokens` 是靠 `extra_body` 才生效的

§4.10.3 的探针证明显式设 32768 时端点能返回 19,001 token，于是按
`ChatOpenAI(max_tokens=config.llm_max_tokens)` 落地。**但线上 banner 显示 `max_tokens=32768`，
`out=8192` 与 `finish_reason=length` 依旧存在。**

本地复现抓到真因：

```
ChatOpenAI(max_tokens=32768)._get_request_payload()
  → {'model': …, 'stream': False, 'temperature': 0.0, 'max_completion_tokens': 32768}
                                            ↑ langchain-openai 把它**改名**了（OpenAI o 系的名字）
```

deepseek 端点不认 `max_completion_tokens`，于是**静默退回自带的 8192**。改成
`extra_body={"max_tokens": …}`（逐字透传请求体）后：

```
设 32768 → finish_reason=stop   out_tokens=19001   正文字符=31,892     ← 真生效
```

> **教训（与"必须实测、不许推断"同源）：参数"设了"不等于"送达了"。** langchain 会重命名参数。
> 验证必须看 `finish_reason=stop` 或 out 超过旧上限，**而不是看自家 banner 的显示值**——
> 本轮就是这样多跑掉一轮。

#### 4.11.2 新发现：平台会把**题目本身**（含选项与上次得分）回灌进记忆空间

除记忆正文外，平台还会以 `role=user` 发来一条 **QA 反馈 JSON**：

```json
[user] Streaming online QA feedback:
{"method": "locomo_llm_judge", "predicted_answer": "Yesterday.",
 "qa_id": "locomo1:q0000:step01", "question": "When Jon has lost his job as a banker?",
 "schema_version": "streaming-online-feedback-v1", "score": 0.0}
```

两个后果：

1. **污染种子位**：它含"题目 + 上一次的答案"，抽成节点后与查询余弦近乎 1.0，会抢走种子；
   并且把**上一次的错误答案**写进记忆，反过来误导下一轮。实测污染样本：`u_44***7417` 的
   `n524`（`(thing) The QA question asks what a courtroom demonstration of unfastening a chain…`）。
2. **但它同时是唯一的"题目归属"信道**：`qa_id` 前缀即数据集（`locomo1` / `scriptMem-angry`…），
   并带 `method`（判分方式）与 `score`（该题真实得分）。**此前"哪道题属于哪一能力项"只能靠猜，
   现在可以按 `(query, qa_id)` 对齐做逐题归因。** 这一步的价值高于治理本身。

**改法**：写入侧在**形态判定与分批之前**剔除这类消息，故既不进图，也不进文档区与向量区；
判据用平台自己的 schema 标记（`Streaming online QA feedback:` / `streaming-online-feedback`），
逐字匹配——实测真实记忆消息 **1491 条零误伤**、反馈 **4/4 命中**。同时留痕
`[IO] qa_feedback 空间=… qa_id=… method=… score=…`（受 `trace_io` 控制）。

#### 4.11.3 契约改动的平台复验：机制全生效

| 指标 | R3（`8ae7…`） | R5（`2744e17…`） | R6（`223218b…`） |
|---|---|---|---|
| 弃权 / `search 返回` | 8 / 38 | **0 / 46** | **0 / 46** |
| `StoryRank JSON 解析失败` | 3 | 7 | **0** |
| `路径=拼接` | — | 7 | **0** |
| **采纳**（中位 / max） | 28 / 443 | 28 / 443 | **10 / 118** |
| **正文字符**（中位 / max） | 2,108 / 22,747 | 2,108 / 19,962 | **665 / 10,534** |
| **逐题得分** | 1/4 | 2/4 | **1/4** |

`采纳` 从"清一色 30"（旧规则 8 的 `至多 30` 上限诱导模型凑数）变成 6/7/12/18/20/24/30
的一组变化值，说明**"凑满 30 条"被消除**，选择层开始真正运作。

#### 4.11.4 病因修正：不是"漏掉证据"，而是"叙事替 answer 模型下了结论"

R6 逐题：`locomo5` 保持 1.0、`locomo1` 仍 0、**`scriptMem-angry`（锁链门）1.0 → 0.0**、
`scriptMem-enemy`（Billing 立场）仍 0。

同一道题三次，**正文长度几乎相同，只有选中节点不同**：

| 轮 | 采纳 | 正文字符 | predicted | score |
|---|---|---|---|---|
| R3 | 30 | 2,316 | (B) | **1.0** |
| R5 | 30 | 2,565 | (B) | **1.0** |
| **R6** | 45 | 2,567 | **(C)** | **0.0** |

**而且 needle 命中是反的**：R5 那次返回里 `chain / door / lock / apartment` **命中 0**，答对；
R6 第一次把 needle 写进了叙事（"the user never knew the door was locked, and is angry that it
was locked without their knowledge"），**却答错**。

→ **紧凑而有观点的叙述，比平铺的叙述更容易把 answer 模型带偏。** 规则 2「整合成连贯故事」
与规则 6「先定位，再叙述」合起来，实际上是在**替 answer 模型组织因果与结论**——而它需要的只是
**线索**。这同时解释了为什么"减少输出量"对 D1 有效（答案就在一个值变化上），对 B2 却可能有害
（答案在跨幕的多条证据上）。

> ⚠️ **附带更正一个此前的过度解读**：R5 的锁链门是在 needle 命中 0 的情况下答对的，说明
> 它可能来自 **answer 模型的先验**（它知道《十二怒汉》的剧情）——**不能把 1.0 当作我们流水线
> 有效的证据**。同理，两个 1.0 里 `locomo5` 靠"相对时长 + 对话日期"一步算术即可，也不构成证据。

#### 4.11.5 本轮改动（去框架化 + 硬预算 + 截断可见）

| # | 改动 | 文件 | 性质 |
|---|---|---|---|
| 1 | 规则 2 加"只陈述节点里已经写明的事实：不解释含义、不推断立场/动机/意图/心理、不用因果替读者下结论" | `dba_pipeline/llm/inference.py` | **去框架化** |
| 2 | 规则 6 的自检句由"读者能否**直接回答**「用户当前消息」"改为"相关**事实**是否都已写进正文"，并加"**不要替它下结论**" | 同上 | 去框架化（原句实际上在**鼓励**它替答案组织逻辑） |
| 3 | 篇幅改**硬约束**：超限 → 前置 `_STORY_RETRY_NOTICE` 强制压缩**重试一次**；仍超 → `_truncate_at_sentence()` 硬截断到句边界（优先句末标点，其次退空白，不切断词） | 同上 | **根治** |

**依据**：
- 规则 6 的"不超过 2000 字符"在 R6 只在 **42/46** 次被接受，另有 4 次写出
  `2033 / 2520 / 4087 / 10487` 字符 —— 篇幅约束对模型只是**倾向**，调小数字同样会被越过，
  故用"重试 + 强指令"而非调参数。
- R6 有一次**写入侧**抽取 `LLM #846 in=4533 out=32768` **撞满上限**，而 `finish_reason` 当时
  只在 `story_rank` 记录，这条**完全隐形**，只能靠"out 恰好等于上限"反推。

#### 4.11.6 未决

1. **"只提供线索"的正确形态未定**：恒返回 1 条叙事意味着**我们必须替 answer 模型做取舍**。
   候选是改成**多条返回**（第 1 条叙事 + 第 2~N 条精准命中），但这会同时影响 H2（多披露），
   且会与本轮 n=4 的抖动读数混在一起。**先积累逐题得分，再决定形态。**
2. **`max_tokens=32768` 是全局的**：它同时放宽了写入侧抽取，R6 实测有 `out=32768` 撞满 +
   一次 `ERROR 无法提取有效的 JSON`（该批经 `no_ops` → 文档通道兜住，**内容未丢**，见
   §4.2 的兜底设计）。是否回退 8192，取决于本轮 `被截断` 汇总是否为 0。
3. **单轮读数噪声大**：锁链门三次 1.0/1.0/0.0，同长度不同选择。后续判断应优先用
   **同题跨空间样本**（该题在 2 个空间共出现 3 次、`Tarsem Singh` 6 次、`Portal→CEO` 6 次），
   而不是按轮均分比较。

| 全部错误 | 725 | 0.757 | 1,238 | 21.4 | 156.0 | 100% |

- **`返回=0` 或 `正文=0` 的答错题：0 条。** 每一道错题都拿到了非空叙事（均值约 1,238 字、约 21 个文档块、约 156 个喂入点）。
- 更反直觉的是：**缺料式的正文比正确题还长**（1,297 vs 1,157，且 61 条 ≥1,600 字），**喂入点却更少**
  （159 vs 187），`跳` 更高（5.0 vs 4.5）。→ 与 §7.6 的"找不到匹配时峰值发散"一致：**信号缺失时，
  检索反而给了更多分散节点、叙事被注水，信息密度下降**。缺料不是"没给"，是"给了但没命中答案点"。

#### 4.18.2 缺料式的形态：**高度集中在时间型问题**

| 组 | n | 时间型（When / How long / What time…） | 首词 Top |
|---|---|---|---|
| 正确 | 393 | 15（**3.8%**） | what=242, how=61, which=18… |
| 缺料式 | 179 | **70（39.1%）** | when=56, what=55, how=35… |
| 答错式 | 546 | 130（23.8%） | what=245, when=114, how=71… |

**时间型问题在正确组只占 3.8%，在缺料式里占 39.1%（10 倍）。** 样例清一色是
"When did Jon go to a fair…" / "When was Jon in Rome?" / "When did Gina interview for a design internship?"
→ 即 **时间锚点（`created_at` 对应的具体日期）没有被组织进叙事**，模型只能回"记忆里没提"。

**反例核查（避免把"假前提"误算成"缺料"）**：`locomo1:q0018「When was Jon in Rome?」`——
原文里"Rome"**确实存在且已入图**，但主语是 **Gina**（`[n40](status) Gina has been to Rome once.`）。
所以这类题的真实失败可能是**归属/假前提**（问 Jon、事实在 Gina），而不是"图里没有"。
→ 结论：**这 179 条里有一部分不是"覆盖缺失"，而是"归属或前提判断"**，修复动作落在**叙事侧的
人称归属与前提处理**，不是"多召回"。

#### 4.18.3 上限估算（二值，互斥口径）

| 假设 | 结果 |
|---|---|
| 现状 | 393 / 1,118 = **35.2%** |
| 只把 **缺料式** 全部救回 | 572 / 1,118 = **51.2%**（+16.0 pt） |
| 只把 **答错式** 全部救回 | 939 / 1,118 = **84.0%**（+48.8 pt） |

#### 4.18.4 结论（对优先级排序的直接含义）

1. **"检索没返回东西"这个假设被否定**——725 条错题全部拿到了非空叙事。**瓶颈不在"给不给"，在"给的对不对 / 读得对不对"。**
2. **答错式 546 条（75.3%）是主战场**：料在叙事里，模型挑了别的（噪声、同类干扰、归属错）。这正是
   §4.16 精确证据路由想解决的问题，但**该路由目前只对"带选项的 MCQ 形态"生效**（`判型=是`），
   locomo 的开放题全程 `判型=否` → **开放题没有享受收拢**，是明确的收益缺口。
3. **缺料式 179 条（24.7%）里，39% 是时间型** → 指向一个具体、可定位的子系统（**时间锚点的组织与
   呈现**），而不是泛泛的"召回不够"。另有相当比例是**归属/假前提**（同 §4.18.2 的 Rome 例）。
4. **scriptMem 100% 是答错式** → 该赛道完全不吃"检索补给"，只吃**叙事质量与判定**，与 §4.15.5
   "可能本来就不依赖我们返回的记忆"相互印证。

> **成本侧联动**：既然"给得更多"不解决问题（缺料式的正文反而更长），当前
> `正文 ~1,238 字/题` 的篇幅有相当部分是**无效注水**，与
> [1001——写链成本优化与模型迁移计划](1001——写链成本优化与模型迁移计划.md) §四 P1-2「输出瘦身」方向一致。

### 4.19 向量落盘改造：索引不落盘 + 追加式分片（1001）

**动因**：1001 计划 §P0-4 把「数据体积」提为 P0。线上基线 `/data` **2.5 GB / 12% 进度**
（外推全量 ≈20 GB）、BLOCK I/O **14 GB**，根因在 [store.py](../../dba_pipeline/embedding/store.py)
的落盘方式。

#### 4.19.1 先纠正一处**结论错误**（原计划文档不成立）

1001 §P2 与 §P0-4 的表格里有一条：

> `content_vectors.npz` 现为**固定文件名**（`dirname(path)` 恒为 `/data`）→ 所有空间互相覆盖、互相读入

**经实测证伪。** `VectorStore.save(path)` 里的 `path` 是**索引目录**而不是文件：

| 调用点 | 传入 `path` | `dirname(path)` |
|---|---|---|
| 图谱索引 [space.py#L545](../../alm/space.py#L545) | `<data>/<stem>.index/faiss` | `<data>/<stem>.index` ← **每空间独立** |
| 文档索引 [space.py#L637](../../alm/space.py#L637) | `<data>/<stem>.docs.index/faiss` | `<data>/<stem>.docs.index` ← **每空间独立** |

即 ALM 侧早就靠「每空间独占 `.index/` 子目录」把这条堵住了（[space.py#L491-L496](../../alm/space.py#L491-L496)
的注释正是那次修复）。新增 `test_two_spaces_do_not_share_vector_cache` 锁定该不变式。
**结论：不需要改命名，该项从优化清单中撤销。**

#### 4.19.2 真正的三条问题与改法

| # | 原实现 | 问题 | 改法 |
|---|---|---|---|
| 1 | `FAISS.save_local(path)` | docstore（**全部正文**）被 pickle 进 `index.pkl`，而正文在 YAML / docs.yaml 已有一份；`save` 又把 `_contents` 写进 npz → 同一空间**盘上三份正文** | **索引一律不落盘**，`load` 时用向量在内存重建（`FAISS.from_embeddings`，O(N) 内存拷贝） |
| 2 | `save` 全量重写索引 + 整个向量缓存 | 一次 Add 通常只新增个位数向量，却重写整个索引（BLOCK I/O 14 GB 的机制） | **追加式分片**：`<index>/vectors/{seq:04d}.npz`，只写**本次变更** |
| 3 | `np.stack(...)` 未指定 dtype | 向量以 **float64** 落盘，白占一倍磁盘 | 全链路 `float32`（与 faiss 内部精度一致） |

#### 4.19.3 分片是"日志"而不是"快照"

行格式 `ids / vectors / deleted / contents`，按文件名**升序回放**即可得到权威状态：

- **删除** → 写墓碑（`deleted=1`，向量位用零向量占位，npz 是定长数组不能跳行）
- **更新** → 写新行，同 id **后写覆盖先写**
- **compact** → 分片数 > 16 **且** 总行数 ≥ 2×存活数才合并。**两个条件缺一不可**：
  合并本身是一次全量重写，若分片里大多是存活行，合并比继续追加更贵。
- **`clear_vectors()`** 置 `_cleared`，下次 `save` 先整体清空分片；否则 `load` 会把已清空的向量"复活"。
- **旧格式迁移**：`load` 在分片目录为空时回退读 `<index>/../content_vectors.npz`，下次 `save` 自动转为分片，无需人工干预。

**保持不变**：检索仍是 `IndexFlat` **精确检索（recall 不变）**；`self.store` 仍是 LangChain `FAISS`
实例（`graph_builder` / `space._load_documents` 等外部读取点无需改动）；`_contents` 仍随分片落盘
（保证 `reconcile` 语义与 MCP 侧不受影响）。

#### 4.19.4 验收

- **单测**：`tests/test_vector_store.py` 新增 8 条 —— 跨空间隔离、增量只追加、
  无变更不写、墓碑不复活、更新后写覆盖、落盘 dtype=`float32`、`clear_vectors` 作废分片、
  compact 前后状态一致、旧格式可载入。
- **全量**：`131 passed / 4 failed`。4 条失败全部是
  `tests/test_mcp_server.py` 的 `'FakeVectorStore' object has no attribute 'reconcile'`
  —— **既有失败**（测试替身缺方法），与本次改动无关。
- **待平台验证**：`/data` 每百题增量、单空间索引字节数、BLOCK I/O 绝对量（需一次烟测）。

#### 4.19.5 本地测试环境（新增）

### 4.21 埋点（P0-1）· 日志体积（P0-5）· 边连接拆批（P1-2）（1001）

#### 4.21.1 P0-1 按侧归因 + 缓存命中埋点

**问题**：全部调用点共用同一个 `ChatOpenAI` 实例，账单只能给总数——0926 账单是
"44 次调用/题"，但**算不出写侧占多少、读侧占多少**，于是无法判断该先优化哪一侧。

**改法**（三步）：

| 步 | 内容 | 位置 |
|---|---|---|
| ① | 新增**角色标签**：`with_role(runnable, role)` 把 `role:<name>` 打进 LangChain 运行标签 | [dba_pipeline/llm/roles.py](../../dba_pipeline/llm/roles.py)（中立层，避免 `dba_pipeline → alm` 反向依赖成环） |
| ② | 9 个调用点全部打标；`TokenMeter` 在 `on_llm_end` 的 `kwargs["tags"]` 里读 | [dba.py](../../dba_pipeline/extraction/dba.py)、[inference.py](../../dba_pipeline/llm/inference.py)、[judge.py](../../alm/judge.py) |
| ③ | `summary()` / `report()` 输出**按 role 分桶**的调用数、input、命中率、output、成本 | [alm/tokens.py](../../alm/tokens.py) |

**为什么用 tags 而不是在各调用点手工累加**：tags 是**逐运行**传递的，不依赖全局状态、
并发不串；且新增调用点只要包一层 `with_role` 就被覆盖，不会漏计。
⚠️ 该做法依赖"标签会出现在 `on_llm_end` 的 kwargs 里"这个实现细节——**已实测确认**
（langchain-core 1.4.8 / langchain 1.3.10），并写了端到端断言
`test_tags_reach_meter_on_llm_end` 钉住它。**这个细节一旦随版本变化，归因会静默退化成
全部计入 `unknown`，而 `unknown` 桶看起来"也有数据"，很难被发现**——故必须有测试。

**缓存命中**：`extract_usage` 补三种供应商形态（deepseek `prompt_cache_hit_tokens`、
OpenAI `prompt_tokens_details.cached_tokens`、Responses API `input_tokens_details`），
并**分开计价**（新增 `ALM_PRICE_CACHE_PER_M`）。取不到时按"全部未命中"降级——**宁可高估**
成本。理由是 deepseek 命中价是未命中的 **1/50**，混算等于把缓存策略的收益完全抹平。

**role 词表**（写进 `roles.py` docstring）：`extract` / `link` / `triage`（写侧）、
`purpose` / `status` / `story` / `abstain`（读侧）、`audit` / `answer`（旁路）。

**配套**：[.env.alm](../../.env.alm) 补 `ALM_PRICE_*`（按 deepseek 标准价 ¥2 / ¥0.04 / ¥8，
币种 CNY；夜间折后价是标准价的 1/2），并注明切 gpt-4o-mini 赛道时改成 0.15 / 0.075 / 0.60 USD。

#### 4.21.2 P0-5 留痕截断

新增 `ALM_TRACE_MAX_CHARS`（默认 4000，0=不截断）+ `_clip_for_log()`，作用于三处正文留痕
（`[IO] add 入参` 原文、`[IO] add 落库` 节点、`[IO] search 入参` 的 query 与选项）。

**为什么**：0930 实测 `trace_io=1` 时单文件 **84 MB**、约 60 秒写满一次轮转；平台上确有
把整份文档当 query 送进来的轨道，**单条 `[IO]` 可达数 MB，一条就能顶掉一次轮转**。
截断保留头部（形态判定看开头）并标注原长。

同时把 `.env.alm` 的 `ALM_TRACE_IO` 置 **0**（Full 期本就必须如此）。注意
`[QA] qa_feedback` 是**独立信道、不受 trace_io 控制**，关掉留痕不会把题目归因一起关掉。

#### 4.21.3 P1-2 边连接拆批

`maintain` 的边步骤改为经 `_link_edges()`：新节点数超过 `EDGE_BATCH_SIZE=24` 时按批调用
并把 `edge_ops` 合并。

**为什么**：`edge_ops` 条数与「本轮新节点 × 候选旧节点」同阶，单次输出线性膨胀——0927
实测一次 `out=32768` 撞顶，JSON 在数组中途断掉、**该批的边整批丢**。

**阈值取 24 的理由**：0930 实测单次 Add 平均 10.8 条消息、约 5.1 组，每组十几个节点 →
24 是"确实异常多"的门槛，**多数调用不会触发拆批**（`<=` 时行为与改造前逐字一致，
含 `new_ids` 为空时仍照常调一次）。拆批的代价是旧节点上下文按批重复发送，故不轻易触发。

> ⚠️ **读数更正**：原计划把 edge-ops 当作撞顶主因，但 0930 日志实测——
> `StoryRank 输出被 max_tokens 截断` **33 次**、`out=32768` 共 **40 次**。
> 即**主因是读侧的 StoryRank（33/40），边连接只占 ≤7 次**。本项仍然值得做（它防的是
> "整批边丢失"这种不可恢复的失败），但**不能指望它解决大部分截断**——那要动 StoryRank 的
> 输出契约或 `max_tokens`，见 §4.20.2 的现场不一致提示。

## 七、改动复审与分流（0927 战略转向：**保系统健康**，不再追榜）

**背景**：平台记分板显示 B = 多跳推理、**B2 = 因果链**（smoke 与 full 同一子项）；我们在 smoke 里
B2 恒 0，而别的项目在 full 里 B2 = 26.89。同时确认：**smoke 只作"结构与功能健康性确认"，
full 的子项多得多**（smoke 约 8 个 vs full 约 24 个）。据此**改变战略**：
一切以**系统自身健康**为准，此前所有"为分数"的改动需重新审视。

**"健康"的操作定义**（本节判据）：
① 正确性（不产生错误结果）；② **不静默失效**（失败必须可见）；③ 数据不丢、不被污染；
④ 可观测、可复现；⑤ ALM 与 MCP 行为一致；⑥ 契约合规；⑦ 成本 / 延迟可接受。

**处置原则（已确认）**：
- **健康类 → 保留**；
- **纯形态/口径类（只为分数）→ 加开关、默认关**（代码与文档一律保留，便于复现与回滚）；
- **有健康代价或收益不明 → 单列"需重评"**，先测量再定；
- **`eval/` 工具分"长期资产 / 一次性探针"**，探针归档。

> ⚠️ **执行时机**：本节的处置**在本轮 smoke 跑完后再动手**——正在跑的读数不能被打断。
> 且一律**只改默认值与开关，不删代码**。

2. **不动代码、不删文件**；改动只落在 `alm/config.py` 的默认值与 `.env.alm`；
3. 重跑测试（45 项）→ 重建镜像 → 部署；
4. `eval/` 按 7.4 迁移探针、清理含正文的产物；
5. 之后**只在有明确健康理由时**再改行为；**Full 次数稀缺**（每 track 3 次、第 2 次要等 30 天），**只用于最终判决，不用于试错**。

### 7.6 参数复审：峰值容忍带与目的过滤（0930）

**结论：这两个参数的问题不在"值该调"，而在"从没被接出来 + 当年的标定语料不匹配"。**

| 参数 | 现状 | 关键事实 |
|---|---|---|
| `peak_tolerance` | 库默认 **0.10** | `retriever.py:266` **从未显式传入**（0815——debugPlan 已记录）→ ALM 侧**无入口**；0.10 的标定语料是 0925 实验的 **163 / 322 节点小图**（同质场景少） |
| `purpose_filter_threshold` | **0.30** | 入口已有（config / space / env）；但标定样本是 `probe_threshold_retune.py` 的 **14 组中英对照**，且都是"动机→行为"这类**低同质**对照对 |

**实测证据（0927，600 次线上检索）**：`峰值/候选` 中位 **0.81**（候选≥300 档 **0.79**）——"寻峰"平均只筛掉 19%；该退化**与 embedding 无关**（换 bge-m3 前后均 ≈0.80）。原因：δ 是**绝对**带宽，而真实语料余弦分布很窄（scriptMem 18 次全在 0.5497~0.5884、全距 0.039，δ=0.10 已是全距的 2.5 倍）。

**本轮落地（默认都不改变现行行为）**：
- `dba_pipeline/core/peak_find.py`：新增纯函数 `resolve_peak_tolerance()`——`ratio<=0` 返回绝对带宽（行为逐字不变）；`ratio>0` 返回 `ratio × (peak_mean − min(轮均分))`，**尺度无关**，因而**自动随场景（图规模 / 同质程度）调整**，无需人工分档。
- `dba_pipeline/retrieval/retriever.py`：`__init__` 接受 `peak_tolerance` / `peak_tolerance_ratio` 并**显式传给 `PeakFinder`**（补上历史遗漏）；`_collect_peak_tolerance` 记录带读数。
- `alm/config.py`：`ALM_PEAK_TOLERANCE`（默认 0.10）/ `ALM_PEAK_TOLERANCE_RATIO`（默认 0 = 关）；`alm/space.py` 透传；`alm/server.py` 横幅显式打出（此前**无法核对**生效值）。
- **新增两处观测**（此前完全不可见）：`检索:` 行**追加** `带比 / 带宽 / 带模式` 与 `目的过=out/in`（追加在末尾，不影响既有解析脚本）。**观测先于调值**——见 §7.7。
- `tests/test_peak_find.py`：+3 条（默认不变 / 相对带宽随分布缩放 / spread=0 不清空）。

**未做（需读数或大图）**：两个参数的**数值**不动——旧判据已作废（§7.7），且本地 `data/dba_eval/` 最大只有 **322 节点**，复现不了线上 3000 节点级退化。**需先导出生产图做离线复算。**

**⚠️ 7.6.1 实测修正（0930，生产图离线复算）**：用容器导出的生产图 + **npz 里的生产 bge-m3 向量**
（节点侧零 embedding 成本）跑了两组扫描，**结论与上面的设计相反**：

- **规模纠正**：单空间最大 **688 节点**（中位 ~117；1–49 节点的占 139/210）。日志里的"落库节点 3101"
  是**每轮全部 21 个空间合计**，不是单空间——"3000 节点图"的说法作废。
- **容忍带不是输出量的瓶颈**：δ 从 0.10 收到 **0.03**（5 倍），N 中位**纹丝不动（23）**，
  p90 200→149、max 反而涨到 391。**小图档（≤49 节点）读出恒为 100%**，与带宽完全无关。
- **`ratio × spread` 会反向**：真实图轮均分全距 > 0.2 ⇒ `0.5×spread > 0.10` ⇒ 带宽**变宽**。
  实测 200–499 档 N 中位 170→**224（+32%）**、500+ 档 320→**414（+29%）**。
- **真正的瓶颈是可达集大小**：`_effective_seed_k`（≤40 全量）+ `expand_k=40`，在 ≤700 节点的图上
  一步铺满 ⇒ 大图读出仍有 **~46% 全图**、小图 **100%**。
- ⇒ **改法修正**：`peak_tolerance_ratio` 不作为默认（保留为可选项）；"减少过多输出"应动
  **检索预算（expand_k / 种子策略）** 与 **目的向量侧的发散控制（purpose_filter_threshold /
  purpose_weight_coef）**；若要用带宽，只能用**绝对收紧到 0.02~0.03**，不要用比例式。
- 复现：`python -u -m eval.exp_band_real --round 67ef87ff --tols 0.10 0.05 0.03`
  与 `--ratios 0 0.5`（图 + 向量见 `eval/.cache/alm_data/`，由容器导出）。
- 局限：n=33 案例 / 1 轮（09-25 16:06）；大图样本少（200–499 档 4 例、500+ 档 2 例）；
  目的是 LLM 推断（同一轮内固定、跨轮不可比）；`带比`（带内候选/候选总数）与日志里的
  `峰值/候选` **不是同一个量**，不可直接比。

**⚠️ 7.6.2 B2 现场实测（0930，第二次导出 `alm_data_r3.tgz`）**：拿到 **B2 的 scriptMem 大图**
（`u_d5***f6c9` = Billing 立场演变，**409 节点/1151 边**；`u_9d***dd76` = 锁链门，521 节点；
另加 05:32 轮两个同族空间，共 **4 个案例 / 2 轮独立**）。节点侧仍用 npz 生产向量，零 embedding。

**现行配置的"过多输出"在现场被复现**：`exp=40 / pur=0.30` → 读出 **228~253 点 = 47~49% 全图**
（生产日志该题实测 265/409 = 65%，同量级）。

**唯一有效的旋钮是 `purpose_filter_threshold`（= 用户所说的"目的向量控制发散方向"）**：

| 配置 | 读出 N 中位 | N/全图 | 诱导边/点 | 分量（护栏） |
|---|---|---|---|---|
| **exp=40 / pur=0.30（现行）** | **~226** | **~48%** | 4.4~6.8 | **2** |
| exp=40 / pur=0.32 | ~245 | ~54% | — | — |
| exp=40 / pur=0.38 | **~140（−38%）** | **~28%** | 3.3~4.8 | 3~4 |
| exp=20 / pur=0.30 | ~209（−8%） | ~45% | 4.3~6.8 | 2~5 |
| exp=20 / pur=0.38 | **~102（−55%）** | **~21%** | 3.3~4.8 | 3~5 |

- **`pur 0.30 → 0.38` 使读出腰斩（−38%~−55%，两轮一致）**，而护栏只从"分量 2"退到"3~4"、
  边/点仍 ≥3.3（每点平均还有 3 条以上边）→ **可接受**。
- **对照**：`expand_k` 单独用几乎不改读出（−4~8%）；容忍带（δ 0.10→0.03）同样不改
  （见 §7.6.1）→ **这两个都不是"减少过多输出"的有效旋钮**。
- **结构性矛盾（重要）**：按阈值/分数**逐点**筛会**切碎连通性**（极端配置下分量 2→8、边/点 →2.1）。
  若要"既压输出又保链"，正解是 **先按阈值缩候选，再按弱连通分量整块裁**（整块留/整块丢），
  而不是逐点过滤——这为下一步的"结构化 cap"提供了直接依据。

**建议档位**：低风险 `pur=0.32`（−10%，护栏不变）；有效档 **`pur=0.38`**（−55%，护栏 2→3~4）。

--spaces "u_d5***f6c9,u_9d***dd76" --expand-ks 40 20 --purpose-thrs 0.30 0.32 0.38`。

### 7.7 更正：0925 报告"StoryRank 采纳率 96%"是**坏指标**（0930）

0925 报告 §四.4 的核心依据是"线上实测 采纳/喂入 = **96%**（极端 378/379）"，据此判定"StoryRank 没在做筛选"，并把后续方向定为"转修 StoryRank 的采纳率"。

**该依据不成立**：`采纳` 是后端按**二元组覆盖率 ≥ 0.5** 算的。0930 用**真实节点 + 真实正文**复算某空间：**529 个节点全部通过**（最低覆盖率 0.62）→ 该指标在**句式重复**的数据集上**饱和**，恒等于喂入点（10/10 次比值 0.98~1.00）。**"96%"是度量伪影**，不能用来判断 StoryRank 是否在取舍。

影响：① 日志侧已停用 `采纳`（改打 `正文=`，见 7.2 与审查文档 §11.4）；② §四.4 的结论**需在大图上用可信口径重测**；③ §7.6 的两处新观测正是为避免再犯同类错误。
