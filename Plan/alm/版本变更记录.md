> **用途**：记录 ALM 接入过程中各轮的**实际改动集**。既是内部回溯依据，也直接服务提交材料的

## 二、按轮次的变更集

### 轮次 1（0919 收口）— 自托管上线与契约收口

来源文档：`0910——ALM测评接入计划.md`（该文档是滚动账本，§6 与 §7.x 记录了 0910–0920 多批工作）。

**① 自托管部署链（新建）**
- 新增顶层 `alm/` 服务端模块：`config` / `contract` / `engine` / `space` / `server` / `smoke` / `judge` / `cleanup` / `loadtest` / `tokens`
- 新增 `Dockerfile.alm`、`docker-compose.alm.yml`、`.env.alm`（ALM 专用，与根 `.env` 隔离）
- 独立变量 `ALM_EMBEDDING_LOCAL`（默认 `false`）——避免 compose 用根 `.env` 的 `EMBEDDING_LOCAL=1` 插值，把 GB 级本地模型拖进镜像
- 安全闸：非回环监听且 `ALM_API_KEYS` 为空时**拒绝启动**（不是放行）

**② 契约与输出形态**
- `search` 显式 `with_response=False`（省一次 LLM；主办方把 Search 阶段生成答案划为红线）
- `/search` 收拢为**只返回叙事一条**（叙事缺失时退回采纳节点原文，避免与「弃权」混淆）
- 输出加节点类型前缀（`[status] …`），类型信息是 A/B 维度判断「是事实、偏好还是情绪」的依据
- 补 `created_at`（`_node_created_at()`，`YYYY-MM-DD`，无时间戳不输出）——平台 Answer 模板要求相对时间换算
- `add` 返回的 `messages` 改为「收到的总条数」；三个 ID 逐字节回显

**③ 弃权（两段式，替换单一阈值）**
- 新增 `alm/judge.py`；硬下限 `abstain_cosine` 0.52 → **0.35**，模糊带上界 `abstain_verify_hi`=**0.50**，`judge_top_n=3`
- 依据：探针实测「有答案 / 无答案」两类余弦区间重叠，单阈值必然错一边；两段式做到 A 召回 95% / H 准确 100%

**④ 健壮性（§7.9 十项审查修复）**
- 空间租约 `_lease()`（`add`/`search` 登记在用计数，`_evict_locked` 跳过在用空间）
- 按 `request_id` 幂等缓存（LRU 8192），收紧 `_should_fallback`
- `search()` 全程持空间锁（并顺带解决 `path_tracker.start_session()` 不持锁问题）
- `best_cos` 改在 T1–T4 **完整并集**上计算
- 兜底节点上限 `fallback_max_nodes` 64 → **256**，超量走兜底落库 + WARNING
- 500 响应只回传 `error_id`；叙述 id 空集合时退回正文派生

**⑤ 持久化与写放大**
- FAISS 索引随 YAML 落盘：`<user_id>.index/` 独占子目录 + 「节点集合指纹」校验，不一致回退重建
- `store.py` 的 `np.savez` 改回不压缩（读写只发生在载入，换取写盘更快）

**⑥ 合规**
- `_configure_logging` 显式把 `dba_pipeline` 钉在 **WARNING** 以上（该 logger 可能打印节点内容节选）
- 新增 `alm/cleanup.py`（`--older-than-days 30`，默认预演）+ 注册控制台脚本；文档写明「必须先停服再清理」与 `_dirty` 不变量

**⑦ 观测与工具**
- `RetrievalStats`：每次 Search 记录候选最高余弦与弃权与否，进程退出打印分位数（只含数值）
- `alm/loadtest.py`（并发-延迟-成本压测）、`alm/tokens.py`（TokenMeter + `ALM_PRICE_*` 单价覆盖）
- 开关 `ALM_RENDER_TIMESTAMPS`（默认 `0`）

## 三、本轮详细：语言错配与 embedding 更换

### 3.1 起因：平台语料是英文，我们的链路是中文

平台 smoke 的留痕（`ALM_TRACE_IO=1`）实测语言构成：

| 环节 | CJK 占比 |
|---|---|
| add 入参正文 | 24.5% |
| add 落库节点 | **50.8%** |
| search query | **1.2%**（46 条里 42 条纯英文） |
| search 返回正文 | **74.9%** |

**输入是英文、存储是中英混杂、输出是中文，而提问是英文。** 抽取把英文记忆改写成了中文，
embedding 又是中文专用模型 `bge-large-zh-v1.5`——跨语言余弦失配贯穿全链路。

### 3.2 四处 prompt 的语言硬约束

| 位置 | 约束 |
|---|---|
| `NODE_EXTRACTION_PROMPT` | 新增原则 7：content 必须用源对话语言、**禁止翻译**；并声明「示例中的中文只是示意写法」 |
| `PURPOSE_INFERENCE_PROMPT` | 去掉硬编码的中文目的词表，改为「purposes 必须与用户消息同语言」 |
| `EDGE_LINKING_PROMPT` | `reason` 等自然语言字段用源语言 + few-shot 免责说明 |
| `_STORY_RANK_SYSTEM` | 顶部加「输出语言（硬约束）」，四个 prompt 变体共享 |

> 四条**必须一起改**：只把节点改成英文而 purposes 保持中文，会让目的向量与英文节点的余弦**更差**，
> 反而放大目的过滤的误杀。

### 3.3 Embedding 更换与索引失效安全阀

- 模型：`BAAI/bge-m3`（多语，**1024 维**，与 bge-large-zh 同维）
- 落点 7 处：`.env`、`.env.alm`、`.env.example`、`docker-compose.alm.yml`、`Dockerfile.alm`、
  `store.py::LocalEmbeddings` 默认、`viz/chain_runner.py` 默认
- ⚠️ **同维正是危险所在**：`<user_id>.index/` 里存的是旧模型向量，而原指纹只认节点集合，
  换模型后会判定「一致」照常加载 → 旧模型节点向量与 bge-m3 查询向量混用，余弦全乱且**无任何报错**。
  已把模型名纳入 `MemorySpace._index_digest()`，换模型即自动回退重建，旧索引无需人工清理
- 已实测 SiliconFlow 端点接受 `BAAI/bge-m3` 并正常返回向量

### 3.4 四个余弦阈值重标

工具：`eval/probe_threshold_retune.py`（同一 API 端点、同一批中英对照样本，只换模型）。
结果（p50，单位余弦）：

| 类别 | bge-large-zh | **bge-m3** | 位移 |
|---|---|---|---|
| 目的 ↔ 直接相关 | 0.461 | 0.508 | +0.047 |
| 目的 ↔ **功能等价（必须放过）** | 0.402 | 0.456 | +0.054 |
| 目的 ↔ 无关 | 0.335 | 0.400 | **+0.065** |
| 查询 ↔ 有答案 | 0.712 | 0.730 | +0.018 |
| 查询 ↔ **无答案** | 0.479 | 0.552 | **+0.073** |
| 节点 ↔ 应去重 | 0.923 | 0.929 | +0.006 |
| 节点 ↔ **不应去重** | 0.858 | 0.902 | **+0.044** |

**关键不是「整体抬高」，而是「无关那一侧涨得更多」→ 两类间距被压缩**，旧值不只是偏移，是失效：

| 阈值 | 旧 | 新 | 依据 |
|---|---|---|---|
| `purpose_filter_threshold` | 0.2 | **0.30** | 必须低于「功能等价」类最低值 0.404（0.303→0.404）；这正是 0828 把 0.3 放宽到 0.2 的原因 |
| `abstain_cosine` | 0.35 | **0.48** | 「无答案」最低余弦 0.360→**0.506**，旧值落在这类分布**之下**，硬下限形同不存在 |
| `abstain_verify_hi` | 0.50 | **0.60** | 「无答案」最高余弦 0.520→**0.583**；若上界仍 0.50，无答案查询**全部越过上界** → 不进模糊带、不被拦 → 该弃权时不弃权，H 会崩 |
| `graph_dedup_threshold` | 0.85 | **0.92** | 「只改数值」的句子 p50 已到 0.902 → 会**成片误吞新值**，直接伤 D1 |

⚠️ 探针样本仅 14 组，这批值是**起点**。`graph_dedup_threshold` 的两类样本本身**有重叠**
（不应去重 max 0.948 > 应去重 min 0.915），单阈值分不干净，0.92 只是折中——根治要靠写侧改进。
全部走环境变量（`ALM_PURPOSE_FILTER_THRESHOLD` / `ALM_ABSTAIN_COS` / `ALM_ABSTAIN_VERIFY_HI` /
`ALM_GRAPH_DEDUP_THRESHOLD`），**改回不需重建镜像**。

## 四、写入路由：对话通道分批 + 文档通道隔离

起因：即使语言与阈值修好，B2 与 D1 仍为 0，而本地实验（k=6 批量、对话语料）成绩良好。
导出线上 220 个图文件逐一看结构后，定位到**两个独立的写侧病因**。

### 4.1 病因一：单次 Add 的消息没有分批（D1 写侧从不触发）

平台单次 Add 的消息条数（135 批实测）：`messages=20` 出现 **59 次**、中位 8、**>6 条占 54.1%**。

| messages | 批数 | 节点/条 | 含 update 批 | 含 deprecate 批 |
|---|---|---|---|---|
| 1-2 | 28 | **5.47** | 0/28 | 3/28 |
| 3-4 | 23 | 4.08 | 1/23 | 0/23 |
| 5-6 | 11 | 4.05 | 2/11 | 0/11 |
| 7-9 | 10 | 2.34 | **0/10** | **0/10** |
| 15+ | **62** | **1.21** | **0/62** | **0/62** |

**值变更（update + deprecate）只在 ≤6 条的批次里出现过，7 条以上一次都没有。**
全库 20495 个节点只有 70 个 `deprecated` = **0.34%**。

配套的 LLM 压力证据：抽取调用 `in` token 中位 2376、**max 21843**；`out` token 中位 622、
**max 8192（正是模型输出上限）**，并出现 `LLM 输出疑似被截断，已挽救 node_ops=0 edge_ops=343`
（整批丢节点、只救回边 → 边指向不存在的节点）。另有 8 次 `目的推断 JSON 解析失败（响应长度 3）`。

**修法**：`space.add()` 按 `ALM_ADD_BATCH_SIZE`（默认 **6**，对齐 `0828前置数据管理与后处理.md`
§5.5 的 M=6；MCP 侧走的是 `maintenance_scheduler.proactive_batch_size=6`，ALM 侧此前**没走**
这个调度器）切分，逐组调 `maintain()`。每组用自己的时间戳（比原来的整批时间戳更准）。

### 4.2 病因二：知识库式长文档被当成对话抽记忆（32 个零边图）

按 `thing`（兜底原文档块的节点型）占比分桶，关系是断崖式的：

| thing 占比 | 图数 | 节点中位 | 边/节点中位 |
|---|---|---|---|
| 0% | 84 | 8 | 1.42 |
| 0-20% | 54 | 300 | 2.10 |
| 60-99% | 12 | 202 | 0.81 |
| **≈100%** | **32** | 6 | **0.00** |

最大一个零边图：**289 个 `thing` 节点、0 条边**，内容是一整部易卜生《人民公敌》剧本
（`SCENE.—DR. STOCKMANN'S sitting-room…`）+ `scriptmem_official_exact` 的 QA 反馈。
平台把**整篇文档当一次 Add 灌进来**，抽取判 `no_ops`，兜底把原文切成 500 字块 →
孤立节点灌进图 → 被当成记忆种子 → 峰值落在 hop0 → `跳=1`。

**关键澄清**：这**不是语言问题**。判别性检验显示存在健康的英文图（442 节点 / 996 边 /
343 有向边，thing 仅 10%），也**不是"图规模"问题**——是**内容类型**问题：平台混了两类输入，
一类是对话记忆（本系统设计目标），一类是文档/剧本/任务轨迹。语言错配只是伴随现象。

**修法**：`add()` 入口按形态路由（`ALM_DOC_ROUTE`，纯计数、不调 LLM）：

| 形态 | 判据 | 去向 |
|---|---|---|
| 对话型 | 单条平均 < 500 字，或消息数 > 2 | 现有 DBA 链路（含 6 条分批） |
| 文档型 | 单条平均 ≥ 500 字 **且** 消息数 ≤ 2 | **文档通道**：切块 + 向量，不抽节点、不建边、**不进图** |
| 空内容 | 无有效文本 | 丢弃 |

判据有效性交叉验证：该刀切下去，**文档型 18 批里值变更 0 次，值变更 6 次全部落在会话侧**。

文档通道的存储与检索都与图完全隔离（`<space>.docs.yaml` + `<space>.docs.index/`）：
- 写侧 `_store_documents()`：按 `ALM_DOC_CHUNK_CHARS`（1800）切块、embed、按块序存；
- 读侧 `_document_lookup()`：向量 top-k + **相邻块扩展**（`ALM_DOC_NEIGHBOR=1`）——
  块序是文档唯一的"边"，"谁说了这句"这类问题往往需要跨块上下文；
- 取回的原文摘录经 `retrieve_with_story(extra_nodes=…)` 并入 StoryRank 的输入
  （只进 `path.nodes`、不进 `path.edges`），一次 LLM 调用统合叙事与原文证据。

**块大小 1800 是实测的**（`eval/probe_m3_limit.py`）：英文 16000 字仍 200；
中文 8000 字 200、16000 字报 400 code=20015。1800 对中英都安全且留足余量。

### 4.5 一轮补齐：分组双约束、语言注入、embedding 预算

本轮（2026-09-26）在 4.1–4.3 之上又补齐四处，全部经本地针对性烟雾验证。

**① 分组从"只限条数"改为"条数 + 字符双约束"**（`ALM_ADD_MAX_CHARS=1500`）

`add_batch_size=6` 只约束条数，而**条数不约束长度**：平台有"3~6 条一批、单条均长 505 字"
这类长消息对话，6 条就是 3000 字。实测（按线上 135 批反推）：

| 方案 | 组数 | 中位 | p90 | max | **>1500 字的组** |
|---|---|---|---|---|---|
| 只按 ≤6 条 | 292 | 583 | 1467 | **2934** | **26 / 292 = 9%** |
| 双约束 | 307 | 627 | 1328 | **1494** | **0 / 307** |

单条消息本身超预算时，在**该消息内部**按句末标点切（纯规则，不调 LLM），切分单元保持在
段落 / 句子粒度而非孤立小句——抽取原则 3 的指代消解需要这个上下文。
**为什么不加独立的 LLM 分句调用**：抽取 prompt 的原则 2（"一个事实一个节点"）本身就是
语义分句，它做不好的原因只是输入太长；加一次调用是把同一件事做两遍，成本翻倍且多一个失败点。

**② 语言约束改为注入到 user 消息末尾**（`dba.source_language` + `_LANGUAGE_DIRECTIVE`）

4.3 里"在 system prompt 顶部加英文硬约束"的做法**实测无效**：英文输入 + 生产模型
`deepseek-v4-flash`，**首批（图里还没有任何已有节点可供污染）依然输出中文节点**
（`用户是杭州一家互联网公司的后端开发工程师`）。判断原因是两条叠加——LLM 对**紧邻数据**
的指令遵循度高于 system 里的规则，而中文的指令正文与中文举例在持续"拉"它说中文。
故改为由代码判定源文语言，把指令拼到 user 消息末尾（近因位置），system 里的约束保留作兜底。

语言判定用**汉字占比 ≥ 10%**，不是简单比大小：英文几乎不含汉字（占比≈0），而中文常夹英文
专名（`我用 Go 和 PostgreSQL` 汉字 3 / 拉丁 12 = 20%，比大小会误判成英文）。

**③ embedding 单条预算 500 → 2000**（`store.OpenAIEmbeddings._MAX_CHARS`）

这是**上一轮引入的一个 bug**：`_call` 会把每条文本截到 `_MAX_CHARS`，而文档块是 1800 字
——于是**文档块只有前 500 字进了向量**，尾部永远检索不到，"放大块以保留语义完整性"这个
设计被静默截掉一大半。实测端点上限（`eval/probe_m3_limit.py`）：英文 16000 字仍 200，
中文 8000 字 200 / 16000 字 400。取 2000 对中英都安全且高于文档块大小。
同时把该值纳入索引指纹——它决定长文本向量是"全文"还是"仅前缀"，改它必须触发重建。

**④ `_split_by_chars` 补空白回退**

回看窗口内没有句末标点时，退而切在**最近的空白处**（原来是直接按预算硬切，会把单词劈成
两半——线上实测出现过 `[n2] n. You must include units…` 这种以半个词开头的块）。空白是
所有语言都有的词边界，严格优于硬切。

**⑤ `_TRIAGE_TRUST_MAX_CHARS` 1500 → 900**

依据：线上 9 次 triage 判 SKIP 的对话长度是 45 / 80 / 310 / 541 / 930 / 1019 / 1047 / 1381 / 1412，
其中 5 次（930~1412）都落在 1500 以下，triage 照跑照 SKIP，长度闸形同不存在。1500 是按离线
探测集定的，而那批对话中位 2522——**探针集里没有 1000~1500 这一段**，线上漏判却正好全挤在这里。
取 900 后语义更清楚：窗口覆盖 ≥56% 才采信 triage 结论。

### 4.7 打镜像前的全链路审查：修正一个会让指标倒退的判据

```

```

阈值扫描显示**长度这条路走不通**：抬到 3000 仍误吞 7 批、5000 仍误吞 4 批。原因是
"8000 字符的单条消息"到底是长对话还是文档，长度区分不出来——而已确认为文档的那些

故把分流点从"形态"改到"抽取之后"：

| 判据 | 作用 |
|---|---|
| `doc_chars_per_msg` **500 → 10000** | 只作**极端保护闸**（挡超大输入，别去打爆 LLM）。取值落在"实测最大可抽取单条 7987 字符"与"实测最小文档 1 万字符"之间 |

**副带修复的三项**（同一次审查发现）：

- **文档区索引缺一致性校验**（静默失效）：`_save_documents` 先写条文再存索引，中途中断会让条文
  比索引多；而 `_load_documents` 见索引存在就直接复用、不校验条数 → 多出的块永远检索不到且
  永不重建。已按 `ntotal == len(docs)` 校验，不等即重建，且重建时换**全新** `VectorStore`

- **本地路径的 bge-m3 可用性**：根 `.env` 原为 `EMBEDDING_LOCAL=1`，而本地只缓存了
  bge-large-zh-v1.5，换 bge-m3 后配合 `HF_HUB_OFFLINE=1` 会**直接报错**。已改为 `0`（走 API，
  与线上一致），并在注释里写明要用本地模型需先联网下一次。
- **合规声明的落盘清单陈旧**：`docker-compose.alm.yml` 里仍写"记忆只在 /data 下落盘
  （`<user_id>.yaml` + `<user_id>.index/`）"，现为**四份**（多了 `.docs.yaml` / `.docs.index/`）。
  这条是给主办方的留存条款说明，必须准确。

**审查中确认无误的项**（不再改动）：`Dockerfile.alm` 的模型预下载是条件性的（默认不下载，构建不受影响）；
compose 刻意不在 `environment:` 透传 `EMBEDDING_MODEL`（透传会插值成空串反而清掉 `.env.alm` 的值）；

### 4.9 平台侧首轮复验暴露的两个问题（均为 4.2/4.7 引入）

2026-09-26 平台冒烟（134 批写入 / 46 次检索）分析后确认修掉两项。**先说成功的三项**：
语言（落库节点 CJK 中位 **0.0%**、含中文 39% = 入参 39%，改造前是 24.5% vs 50.8%）、
边型（**有向边 52%**，改造前 30.6%；causal 2014 = 40.7%，改造前 21.9%）、值变更（update 8→18）。
双约束也确认生效：`分批` 与 `max(ceil(msg/6), ceil(chars/1500))` 一致率 93%（134 批）。

**问题 A：分批把 triage 重新拉回来了（两处改动相互抵消）**

```
421 个组里 173 个被 triage 判 SKIP = 41%
兜底率 11.1% → 50.7%（兜底=triage 173 次，no_ops 仅 2 次）
```

机制：`_TRIAGE_TRUST_MAX_CHARS` 是"超过它就绕过 triage 直接抽取"。改造前整批 2000~3000 字
> 1500 → triage **从不参与**；分批后组均 ~500~1000 字 → 落回 900 以下 → **triage 重新参与**
→ 41% 的组被判 SKIP → 内容经 `_divert_raw` 转出图，图只拿到约 59%。

修法：`MemoryDBA(triage_enabled=...)` 新增开关，**ALM 侧默认关闭**（`ALM_TRIAGE=0`）；
MCP 侧不经 `ALMConfig`，其默认仍是 True，行为不变。判断依据是"triage 的错判不在窗口覆盖率上"
（实测 113 字符、覆盖 100% 的组仍误判 SKIP），且 ALM 数据全为评测对话、"值得存"先验极高。

**问题 B：弃权门看不见文档证据（4.7 把内容移出图时留下的漏洞）**

```
弃权率 1/46 → 9/46 = 20%
其中 6 个空间同时出现「文档通道取回」与「弃权」
  u_40***7f55: 文档通道取回 23 块 → 弃权: best_cos=0.5386
```

根因：`best_cos` 只由 `_collect_par_candidates(result)`（图候选）算，**文档通道的命中不在其中**
→ 文档密集空间的 `best_cos` 被系统性低估 → ① 可能触发硬下限直接弃权；② 更多 query 落进
`[0.48, 0.60)` 模糊带 → 判定调用与弃权都变多。

修法：`best_cos = max(图候选最大余弦, 文档通道直命中最高分)`（邻块扩展项的 score 为 None，
不作为命中证据）。`检索` 日志行同步加上 `图cos=` `文cos=` `文档块=`，便于下次直接看两项各是多少。

**刻意没动的两项**（避免同时改多个变量）：
- **弃权阈值 0.48/0.60**：9 次弃权的 best_cos 是 0.4875/0.5709/0.5686/0.5289/0.5796…，全部
  高于硬下限、走的是模糊带判定。但 B 修好后 best_cos 会整体抬高、弃权率应自然下降，
  **先看 B 的效果再决定是否下调**。
- **`doc_lookup_k=8`**：经邻块扩展（±1）放大到约 24 块（单次最多取回 23 块 ≈ 41,000 字符），
  是新的 token 大头。是否降到 4~5 待单独 A/B。

**成本确认**（符合分批的预期）：LLM 调用 381 → **839（2.2x）**；in token 合计 **1,612,627**；
per-call in 中位 2376 → 1922 ↓；被截断告警 8 → **1** ✓；JSON 解析失败 8 → **5** ✓。
A 修掉后还会少掉 173 次 triage 调用。

**修复后的本地复验**（`eval/smoke_local_d1b2.py`，真实 LLM）：


### 4.10 B2 恒为 0 的机械根因：StoryRank 的输出契约在规模上不可满足（0926）

**起因**：平台复验（同日第二次）里 B2 仍是 **唯一恒为 0、且一次"运气分"都没有**的能力项，
而 D1 还有小波动。这个形态不像质量问题（judge 判分下总会有偶然部分分），像**机械性失败**。

#### 4.10.1 第一步：把弃权排除掉（0910 §7.7 规划却从未执行的上界实验）

弃权在本项目里是**被重新引入**的：0818（LiFEMem）已把它定论为**错误设计**
（"无使用场景，检索器/评测层无需拒答能力……**不做实现**"，见
[0818——LiFEMem实验总结与发现 §9](0818——LiFEMem实验总结与发现.md)）；0910 引入 ALM 时的
唯一依据是一句文档转述——把 H 维度的"**最小披露**"误读成"库里没答案时拒答"。
本轮拿到平台 H 的细分项后确认：**H = 认识论安全与隐私，子项 H2 = 敏感信息最小披露/隐私**，
是**隐私行为**维度。而弃权只吃 `best_cos` 一个数，既看不到 query 的隐私语义，也看不到返回
内容是否越界披露——**结构上不可能服务 H2**。且阈值（0.48/0.60）从未在英文、也从未在
bge-m3 上定稿（探针集是 14 组中文样本）。

改法（`ALM_ABSTAIN_COS=0` + `ALM_ABSTAIN_VERIFY_HI=0`，两段串联须一起置 0）后复验：

| | 旧轮 `8ae7…` | 新轮 `a5e0…` |
|---|---|---|
| 弃权 | 8 次 / 46 | **0 次** |

**证据 4 —— 输出契约本身就是不可满足的**

```
   adopted_ids；没写进正文的节点一律不得列入。二者不一致视为输出错误。
```

在 443 节点规模上，这等于要求：`story` 覆盖 443 条中文节点（≈12,000+ token）
**加上** 443 个 id 的 JSON 数组（≈1,200 token）——合计 **≈13,000+ token > 8192**。
所以降级不是偶发，**是必然**。

**证据 5 —— 本该做"减法"的两层都没在做**

#### 4.10.3 根治前先确认一件事：8192 是可调的吗

| **off** | **不传** | **length** | **8192** | 13,689 |

### 4.11 追根：真正的病因是"叙事替 answer 模型下结论"（0927）

§4.10 把 B2 恒零归到"输出契约在规模上不可满足"，方向对，但**只说到一半**。本轮把范围收窄到
最小可证的一点，同时修正 §4.10 的一处技术误判。

#### 4.11.1 修正 §4.10：`max_tokens` 是靠 `extra_body` 才生效的

§4.10.3 的探针证明显式设 32768 时端点能返回 19,001 token，于是按
`ChatOpenAI(max_tokens=config.llm_max_tokens)` 落地。**但线上 banner 显示 `max_tokens=32768`，
`out=8192` 与 `finish_reason=length` 依旧存在。**

本地复现抓到真因：

```
ChatOpenAI(max_tokens=32768)._get_request_payload()
  → {'model': …, 'stream': False, 'temperature': 0.0, 'max_completion_tokens': 32768}
                                            ↑ langchain-openai 把它**改名**了（OpenAI o 系的名字）
```

deepseek 端点不认 `max_completion_tokens`，于是**静默退回自带的 8192**。改成
`extra_body={"max_tokens": …}`（逐字透传请求体）后：

```
设 32768 → finish_reason=stop   out_tokens=19001   正文字符=31,892     ← 真生效
```

> **教训（与"必须实测、不许推断"同源）：参数"设了"不等于"送达了"。** langchain 会重命名参数。
> 验证必须看 `finish_reason=stop` 或 out 超过旧上限，**而不是看自家 banner 的显示值**——
> 本轮就是这样多跑掉一轮。

#### 4.11.2 新发现：平台会把**题目本身**（含选项与上次得分）回灌进记忆空间

除记忆正文外，平台还会以 `role=user` 发来一条 **QA 反馈 JSON**：

```json
[user] Streaming online QA feedback:
{"method": "locomo_llm_judge", "predicted_answer": "Yesterday.",
 "qa_id": "locomo1:q0000:step01", "question": "When Jon has lost his job as a banker?",
 "schema_version": "streaming-online-feedback-v1", "score": 0.0}
```

两个后果：

1. **污染种子位**：它含"题目 + 上一次的答案"，抽成节点后与查询余弦近乎 1.0，会抢走种子；
   并且把**上一次的错误答案**写进记忆，反过来误导下一轮。实测污染样本：`u_44***7417` 的
   `n524`（`(thing) The QA question asks what a courtroom demonstration of unfastening a chain…`）。
2. **但它同时是唯一的"题目归属"信道**：`qa_id` 前缀即数据集（`locomo1` / `scriptMem-angry`…），
   并带 `method`（判分方式）与 `score`（该题真实得分）。**此前"哪道题属于哪一能力项"只能靠猜，
   现在可以按 `(query, qa_id)` 对齐做逐题归因。** 这一步的价值高于治理本身。

**改法**：写入侧在**形态判定与分批之前**剔除这类消息，故既不进图，也不进文档区与向量区；
判据用平台自己的 schema 标记（`Streaming online QA feedback:` / `streaming-online-feedback`），
逐字匹配——实测真实记忆消息 **1491 条零误伤**、反馈 **4/4 命中**。同时留痕
`[IO] qa_feedback 空间=… qa_id=… method=… score=…`（受 `trace_io` 控制）。

#### 4.11.3 契约改动的平台复验：机制全生效

| 指标 | R3（`8ae7…`） | R5（`2744e17…`） | R6（`223218b…`） |
|---|---|---|---|
| 弃权 / `search 返回` | 8 / 38 | **0 / 46** | **0 / 46** |
| `StoryRank JSON 解析失败` | 3 | 7 | **0** |
| `路径=拼接` | — | 7 | **0** |
| **采纳**（中位 / max） | 28 / 443 | 28 / 443 | **10 / 118** |
| **正文字符**（中位 / max） | 2,108 / 22,747 | 2,108 / 19,962 | **665 / 10,534** |
| **逐题得分** | 1/4 | 2/4 | **1/4** |

`采纳` 从"清一色 30"（旧规则 8 的 `至多 30` 上限诱导模型凑数）变成 6/7/12/18/20/24/30
的一组变化值，说明**"凑满 30 条"被消除**，选择层开始真正运作。

#### 4.11.4 病因修正：不是"漏掉证据"，而是"叙事替 answer 模型下了结论"

R6 逐题：`locomo5` 保持 1.0、`locomo1` 仍 0、**`scriptMem-angry`（锁链门）1.0 → 0.0**、
`scriptMem-enemy`（Billing 立场）仍 0。

同一道题三次，**正文长度几乎相同，只有选中节点不同**：

| 轮 | 采纳 | 正文字符 | predicted | score |
|---|---|---|---|---|
| R3 | 30 | 2,316 | (B) | **1.0** |
| R5 | 30 | 2,565 | (B) | **1.0** |
| **R6** | 45 | 2,567 | **(C)** | **0.0** |

**而且 needle 命中是反的**：R5 那次返回里 `chain / door / lock / apartment` **命中 0**，答对；
R6 第一次把 needle 写进了叙事（"the user never knew the door was locked, and is angry that it
was locked without their knowledge"），**却答错**。

→ **紧凑而有观点的叙述，比平铺的叙述更容易把 answer 模型带偏。** 规则 2「整合成连贯故事」
与规则 6「先定位，再叙述」合起来，实际上是在**替 answer 模型组织因果与结论**——而它需要的只是
**线索**。这同时解释了为什么"减少输出量"对 D1 有效（答案就在一个值变化上），对 B2 却可能有害
（答案在跨幕的多条证据上）。

> ⚠️ **附带更正一个此前的过度解读**：R5 的锁链门是在 needle 命中 0 的情况下答对的，说明
> 它可能来自 **answer 模型的先验**（它知道《十二怒汉》的剧情）——**不能把 1.0 当作我们流水线
> 有效的证据**。同理，两个 1.0 里 `locomo5` 靠"相对时长 + 对话日期"一步算术即可，也不构成证据。

#### 4.11.5 本轮改动（去框架化 + 硬预算 + 截断可见）

| # | 改动 | 文件 | 性质 |
|---|---|---|---|
| 1 | 规则 2 加"只陈述节点里已经写明的事实：不解释含义、不推断立场/动机/意图/心理、不用因果替读者下结论" | `dba_pipeline/llm/inference.py` | **去框架化** |
| 2 | 规则 6 的自检句由"读者能否**直接回答**「用户当前消息」"改为"相关**事实**是否都已写进正文"，并加"**不要替它下结论**" | 同上 | 去框架化（原句实际上在**鼓励**它替答案组织逻辑） |
| 3 | 篇幅改**硬约束**：超限 → 前置 `_STORY_RETRY_NOTICE` 强制压缩**重试一次**；仍超 → `_truncate_at_sentence()` 硬截断到句边界（优先句末标点，其次退空白，不切断词） | 同上 | **根治** |

**依据**：
- 规则 6 的"不超过 2000 字符"在 R6 只在 **42/46** 次被接受，另有 4 次写出
  `2033 / 2520 / 4087 / 10487` 字符 —— 篇幅约束对模型只是**倾向**，调小数字同样会被越过，
  故用"重试 + 强指令"而非调参数。
- R6 有一次**写入侧**抽取 `LLM #846 in=4533 out=32768` **撞满上限**，而 `finish_reason` 当时
  只在 `story_rank` 记录，这条**完全隐形**，只能靠"out 恰好等于上限"反推。

#### 4.11.6 未决

1. **"只提供线索"的正确形态未定**：恒返回 1 条叙事意味着**我们必须替 answer 模型做取舍**。
   候选是改成**多条返回**（第 1 条叙事 + 第 2~N 条精准命中），但这会同时影响 H2（多披露），
   且会与本轮 n=4 的抖动读数混在一起。**先积累逐题得分，再决定形态。**
2. **`max_tokens=32768` 是全局的**：它同时放宽了写入侧抽取，R6 实测有 `out=32768` 撞满 +
   一次 `ERROR 无法提取有效的 JSON`（该批经 `no_ops` → 文档通道兜住，**内容未丢**，见
   §4.2 的兜底设计）。是否回退 8192，取决于本轮 `被截断` 汇总是否为 0。
3. **单轮读数噪声大**：锁链门三次 1.0/1.0/0.0，同长度不同选择。后续判断应优先用
   **同题跨空间样本**（该题在 2 个空间共出现 3 次、`Tarsem Singh` 6 次、`Portal→CEO` 6 次），
   而不是按轮均分比较。

| 答错式 | 546 | 0.760 | 1,218 | 21.6 | 155.0 | 100% |
| 全部错误 | 725 | 0.757 | 1,238 | 21.4 | 156.0 | 100% |

- **`返回=0` 或 `正文=0` 的答错题：0 条。** 每一道错题都拿到了非空叙事（均值约 1,238 字、约 21 个文档块、约 156 个喂入点）。
- 更反直觉的是：**缺料式的正文比正确题还长**（1,297 vs 1,157，且 61 条 ≥1,600 字），**喂入点却更少**
  （159 vs 187），`跳` 更高（5.0 vs 4.5）。→ 与 §7.6 的"找不到匹配时峰值发散"一致：**信号缺失时，
  检索反而给了更多分散节点、叙事被注水，信息密度下降**。缺料不是"没给"，是"给了但没命中答案点"。

#### 4.18.2 缺料式的形态：**高度集中在时间型问题**

| 组 | n | 时间型（When / How long / What time…） | 首词 Top |
|---|---|---|---|
| 正确 | 393 | 15（**3.8%**） | what=242, how=61, which=18… |
| 缺料式 | 179 | **70（39.1%）** | when=56, what=55, how=35… |
| 答错式 | 546 | 130（23.8%） | what=245, when=114, how=71… |

**时间型问题在正确组只占 3.8%，在缺料式里占 39.1%（10 倍）。** 样例清一色是
"When did Jon go to a fair…" / "When was Jon in Rome?" / "When did Gina interview for a design internship?"
→ 即 **时间锚点（`created_at` 对应的具体日期）没有被组织进叙事**，模型只能回"记忆里没提"。

**反例核查（避免把"假前提"误算成"缺料"）**：`locomo1:q0018「When was Jon in Rome?」`——
原文里"Rome"**确实存在且已入图**，但主语是 **Gina**（`[n40](status) Gina has been to Rome once.`）。
所以这类题的真实失败可能是**归属/假前提**（问 Jon、事实在 Gina），而不是"图里没有"。
→ 结论：**这 179 条里有一部分不是"覆盖缺失"，而是"归属或前提判断"**，修复动作落在**叙事侧的
人称归属与前提处理**，不是"多召回"。

#### 4.18.3 上限估算（二值，互斥口径）

| 假设 | 结果 |
|---|---|
| 现状 | 393 / 1,118 = **35.2%** |
| 只把 **缺料式** 全部救回 | 572 / 1,118 = **51.2%**（+16.0 pt） |
| 只把 **答错式** 全部救回 | 939 / 1,118 = **84.0%**（+48.8 pt） |

#### 4.18.4 结论（对优先级排序的直接含义）

1. **"检索没返回东西"这个假设被否定**——725 条错题全部拿到了非空叙事。**瓶颈不在"给不给"，在"给的对不对 / 读得对不对"。**
2. **答错式 546 条（75.3%）是主战场**：料在叙事里，模型挑了别的（噪声、同类干扰、归属错）。这正是
   §4.16 精确证据路由想解决的问题，但**该路由目前只对"带选项的 MCQ 形态"生效**（`判型=是`），
   locomo 的开放题全程 `判型=否` → **开放题没有享受收拢**，是明确的收益缺口。
3. **缺料式 179 条（24.7%）里，39% 是时间型** → 指向一个具体、可定位的子系统（**时间锚点的组织与
   呈现**），而不是泛泛的"召回不够"。另有相当比例是**归属/假前提**（同 §4.18.2 的 Rome 例）。
4. **scriptMem 100% 是答错式** → 该赛道完全不吃"检索补给"，只吃**叙事质量与判定**，与 §4.15.5
   "可能本来就不依赖我们返回的记忆"相互印证。

> **成本侧联动**：既然"给得更多"不解决问题（缺料式的正文反而更长），当前
> `正文 ~1,238 字/题` 的篇幅有相当部分是**无效注水**，与
> [1001——写链成本优化与模型迁移计划](1001——写链成本优化与模型迁移计划.md) §四 P1-2「输出瘦身」方向一致。

### 4.19 向量落盘改造：索引不落盘 + 追加式分片（1001）

**动因**：1001 计划 §P0-4 把「数据体积」提为 P0。线上基线 `/data` **2.5 GB / 12% 进度**
（外推全量 ≈20 GB）、BLOCK I/O **14 GB**，根因在 [store.py](../../dba_pipeline/embedding/store.py)
的落盘方式。

#### 4.19.1 先纠正一处**结论错误**（原计划文档不成立）

1001 §P2 与 §P0-4 的表格里有一条：

> `content_vectors.npz` 现为**固定文件名**（`dirname(path)` 恒为 `/data`）→ 所有空间互相覆盖、互相读入

**经实测证伪。** `VectorStore.save(path)` 里的 `path` 是**索引目录**而不是文件：

| 调用点 | 传入 `path` | `dirname(path)` |
|---|---|---|
| 图谱索引 [space.py#L545](../../alm/space.py#L545) | `<data>/<stem>.index/faiss` | `<data>/<stem>.index` ← **每空间独立** |
| 文档索引 [space.py#L637](../../alm/space.py#L637) | `<data>/<stem>.docs.index/faiss` | `<data>/<stem>.docs.index` ← **每空间独立** |

即 ALM 侧早就靠「每空间独占 `.index/` 子目录」把这条堵住了（[space.py#L491-L496](../../alm/space.py#L491-L496)
的注释正是那次修复）。新增 `test_two_spaces_do_not_share_vector_cache` 锁定该不变式。
**结论：不需要改命名，该项从优化清单中撤销。**

#### 4.19.2 真正的三条问题与改法

| # | 原实现 | 问题 | 改法 |
|---|---|---|---|
| 1 | `FAISS.save_local(path)` | docstore（**全部正文**）被 pickle 进 `index.pkl`，而正文在 YAML / docs.yaml 已有一份；`save` 又把 `_contents` 写进 npz → 同一空间**盘上三份正文** | **索引一律不落盘**，`load` 时用向量在内存重建（`FAISS.from_embeddings`，O(N) 内存拷贝） |
| 2 | `save` 全量重写索引 + 整个向量缓存 | 一次 Add 通常只新增个位数向量，却重写整个索引（BLOCK I/O 14 GB 的机制） | **追加式分片**：`<index>/vectors/{seq:04d}.npz`，只写**本次变更** |
| 3 | `np.stack(...)` 未指定 dtype | 向量以 **float64** 落盘，白占一倍磁盘 | 全链路 `float32`（与 faiss 内部精度一致） |

#### 4.19.3 分片是"日志"而不是"快照"

行格式 `ids / vectors / deleted / contents`，按文件名**升序回放**即可得到权威状态：

- **删除** → 写墓碑（`deleted=1`，向量位用零向量占位，npz 是定长数组不能跳行）
- **更新** → 写新行，同 id **后写覆盖先写**
- **compact** → 分片数 > 16 **且** 总行数 ≥ 2×存活数才合并。**两个条件缺一不可**：
  合并本身是一次全量重写，若分片里大多是存活行，合并比继续追加更贵。
- **`clear_vectors()`** 置 `_cleared`，下次 `save` 先整体清空分片；否则 `load` 会把已清空的向量"复活"。
- **旧格式迁移**：`load` 在分片目录为空时回退读 `<index>/../content_vectors.npz`，下次 `save` 自动转为分片，无需人工干预。

**保持不变**：检索仍是 `IndexFlat` **精确检索（recall 不变）**；`self.store` 仍是 LangChain `FAISS`
实例（`graph_builder` / `space._load_documents` 等外部读取点无需改动）；`_contents` 仍随分片落盘
（保证 `reconcile` 语义与 MCP 侧不受影响）。

#### 4.19.4 验收

- **单测**：`tests/test_vector_store.py` 新增 8 条 —— 跨空间隔离、增量只追加、
  无变更不写、墓碑不复活、更新后写覆盖、落盘 dtype=`float32`、`clear_vectors` 作废分片、
  compact 前后状态一致、旧格式可载入。
- **全量**：`131 passed / 4 failed`。4 条失败全部是
  `tests/test_mcp_server.py` 的 `'FakeVectorStore' object has no attribute 'reconcile'`
  —— **既有失败**（测试替身缺方法），与本次改动无关。
- **待平台验证**：`/data` 每百题增量、单空间索引字节数、BLOCK I/O 绝对量（需一次烟测）。

#### 4.19.5 本地测试环境（新增）

### 4.21 埋点（P0-1）· 日志体积（P0-5）· 边连接拆批（P1-2）（1001）

#### 4.21.1 P0-1 按侧归因 + 缓存命中埋点

**问题**：全部调用点共用同一个 `ChatOpenAI` 实例，账单只能给总数——0926 账单是
"44 次调用/题"，但**算不出写侧占多少、读侧占多少**，于是无法判断该先优化哪一侧。

**改法**（三步）：

| 步 | 内容 | 位置 |
|---|---|---|
| ① | 新增**角色标签**：`with_role(runnable, role)` 把 `role:<name>` 打进 LangChain 运行标签 | [dba_pipeline/llm/roles.py](../../dba_pipeline/llm/roles.py)（中立层，避免 `dba_pipeline → alm` 反向依赖成环） |
| ② | 9 个调用点全部打标；`TokenMeter` 在 `on_llm_end` 的 `kwargs["tags"]` 里读 | [dba.py](../../dba_pipeline/extraction/dba.py)、[inference.py](../../dba_pipeline/llm/inference.py)、[judge.py](../../alm/judge.py) |
| ③ | `summary()` / `report()` 输出**按 role 分桶**的调用数、input、命中率、output、成本 | [alm/tokens.py](../../alm/tokens.py) |

**为什么用 tags 而不是在各调用点手工累加**：tags 是**逐运行**传递的，不依赖全局状态、
并发不串；且新增调用点只要包一层 `with_role` 就被覆盖，不会漏计。
⚠️ 该做法依赖"标签会出现在 `on_llm_end` 的 kwargs 里"这个实现细节——**已实测确认**
（langchain-core 1.4.8 / langchain 1.3.10），并写了端到端断言
`test_tags_reach_meter_on_llm_end` 钉住它。**这个细节一旦随版本变化，归因会静默退化成
全部计入 `unknown`，而 `unknown` 桶看起来"也有数据"，很难被发现**——故必须有测试。

**缓存命中**：`extract_usage` 补三种供应商形态（deepseek `prompt_cache_hit_tokens`、
OpenAI `prompt_tokens_details.cached_tokens`、Responses API `input_tokens_details`），
并**分开计价**（新增 `ALM_PRICE_CACHE_PER_M`）。取不到时按"全部未命中"降级——**宁可高估**
成本。理由是 deepseek 命中价是未命中的 **1/50**，混算等于把缓存策略的收益完全抹平。

**role 词表**（写进 `roles.py` docstring）：`extract` / `link` / `triage`（写侧）、
`purpose` / `status` / `story` / `abstain`（读侧）、`audit` / `answer`（旁路）。

**配套**：[.env.alm](../../.env.alm) 补 `ALM_PRICE_*`（按 deepseek 标准价 ¥2 / ¥0.04 / ¥8，
币种 CNY；夜间折后价是标准价的 1/2），并注明切 gpt-4o-mini 赛道时改成 0.15 / 0.075 / 0.60 USD。

#### 4.21.2 P0-5 留痕截断

新增 `ALM_TRACE_MAX_CHARS`（默认 4000，0=不截断）+ `_clip_for_log()`，作用于三处正文留痕
（`[IO] add 入参` 原文、`[IO] add 落库` 节点、`[IO] search 入参` 的 query 与选项）。

**为什么**：0930 实测 `trace_io=1` 时单文件 **84 MB**、约 60 秒写满一次轮转；平台上确有
把整份文档当 query 送进来的轨道，**单条 `[IO]` 可达数 MB，一条就能顶掉一次轮转**。
截断保留头部（形态判定看开头）并标注原长。

#### 4.21.3 P1-2 边连接拆批

`maintain` 的边步骤改为经 `_link_edges()`：新节点数超过 `EDGE_BATCH_SIZE=24` 时按批调用
并把 `edge_ops` 合并。

**为什么**：`edge_ops` 条数与「本轮新节点 × 候选旧节点」同阶，单次输出线性膨胀——0927
实测一次 `out=32768` 撞顶，JSON 在数组中途断掉、**该批的边整批丢**。

**阈值取 24 的理由**：0930 实测单次 Add 平均 10.8 条消息、约 5.1 组，每组十几个节点 →
24 是"确实异常多"的门槛，**多数调用不会触发拆批**（`<=` 时行为与改造前逐字一致，
含 `new_ids` 为空时仍照常调一次）。拆批的代价是旧节点上下文按批重复发送，故不轻易触发。

> ⚠️ **读数更正**：原计划把 edge-ops 当作撞顶主因，但 0930 日志实测——
> `StoryRank 输出被 max_tokens 截断` **33 次**、`out=32768` 共 **40 次**。
> 即**主因是读侧的 StoryRank（33/40），边连接只占 ≤7 次**。本项仍然值得做（它防的是
> "整批边丢失"这种不可恢复的失败），但**不能指望它解决大部分截断**——那要动 StoryRank 的
> 输出契约或 `max_tokens`，见 §4.20.2 的现场不一致提示。

### 4.22 链路级验证：单测全绿**不等于**链路上生效（1001）

**动因**：§4.21 的三项改动都是**跨模块装配**（`space.add() → save() → _save_index() → vector_store.save()`、
`PROMPT | with_role(llm, …)` 挂 TokenMeter 回调、拆批要穿过真实 `apply_ops`）。
单测验证的是"函数本身对"，验证不了"装起来对"。

**交付物**：[tests/test_alm_pipeline_e2e.py](../../tests/test_alm_pipeline_e2e.py) —— 用真实组件
（`MemorySpace` + `MemoryDBA` + `PurposeDrivenRetriever` + `VectorStore`）跑
**Add → Search → 落盘 → 重载 → Search**。

#### 4.22.1 ⚠️ 它立刻抓到一处真 bug（单测漏掉的）

`_link_edges` 改造时我把 `edge_context = self._build_edge_context(...)` 从 `maintain` 里删掉了，
但 `maintain` 末尾的调试字段仍引用它：

```python
"context": {"node": node_context, "edge": edge_context},   # NameError: edge_context 未定义
```

**后果**：`maintain()` 在**任何**批次上都会 `NameError` → Add 全线 5xx。
而：单测（`test_dba_edge_batch.py`）只测 `_link_edges` 本身，全绿；
`test_dba_temporal.py` 是纯离线不跑链路；`test_mcp_server.py` 用的是假替身。
**没有任何一条测试会执行到 `maintain` 的收尾**——所以它一路漏到了链路验证。

**修法**：`_link_edges` 改为返回 ``(edge_ops, contexts)``（拆批后"唯一的那份上下文"不存在了），
`maintain` 回填 `contexts[0]` 并新增 `edge_batches` 计数（否则读的人会把第一批的 `new_nodes`
误当成本轮全部）。单测同步补上对 `contexts` 的断言。

> **教训（值得写进流程）**：改一个函数的**返回签名**时，"改调用点"≠"改所有引用点"——
> 还要找**同一作用域内其它对旧变量的引用**。本次漏的正是后者。

#### 4.22.2 七条断言（覆盖 §4.21 三项改动）

| # | 断言 | 验证的改动 |
|---|---|---|
| 1 | Add→Search→save→**新实例**重载→Search，结果**逐条一致** | 向量分片落盘 + 索引重建 |
| 2 | 落盘目录里是 `vectors/*.npz`，且**不再有** `index.faiss` | 索引不落盘 |
| 3 | 重载时**不产生任何 LLM 调用** | 分片持久化买到的收益 |
| 4 | 真实链路走完后，meter 里 `extract`/`link`/`purpose`/`story` 四桶**齐全**，且 `unknown` **为空** | role 埋点 |
| 5 | 新节点 51 个 → 边链调用 **3** 次（51/24 上取整） | 边连接拆批 |
| 6 | 新节点恰为 24 个 → 边链调用 **1** 次 | 阈值以下行为不变 |
| 7 | `trace_io=1` 时 `[IO] add 入参` 含"留痕截断"且单条 < 2000 字；默认关闭时不产生该行 | 留痕截断 + 默认关 |

**夹具的两个坑（已写进测试注释）**：

- 假模型的**向量**不能用"文本长度"那种玩具实现——`graph_dedup_threshold=0.92` 会把长度
  相近的节点合并、图建不起来；也不能用纯文本哈希——那是正交向量，`purpose_filter_threshold`
  会把候选全滤掉，检索恒为空、断言退化成"空 == 空"。最终用**词袋哈希**（共享词 → 高余弦），
  并让每个节点带 7 个独有词把节点间余弦压到 ~0.36、与查询保持 ~0.60。
- 测试里显式把 `abstain_cosine` / `abstain_verify_hi` 置 0，与生产 `.env.alm` 一致
  （否则"夹具余弦偏低"会被误读成"链路坏了"）。

**夹具模型按 system prompt 特征词分派**（`节点抽取器` / `边连接器` / …），不用
`FakeListChatModel`：后者按调用顺序返回，链路里多一次/少一次调用就会张冠李戴。

### 4.23 优化量实测：存储省 55%、写入量降 3 个数量级；**token 本轮省 0**

**工具**：[alm_storage_audit.py](../../alm/tools/alm_storage_audit.py) —— 同一空间形状下比 OLD/NEW 两种落盘格式的字节数。
空间形状取自 0930 生产日志的空间 `u_3e***ef23`：图谱 **2,878** 条 + 文档区 **2,430** 块 + 维度 1024。
（合成语料只影响正文部分；向量部分按格式严格计算。）

#### 4.23.1 存储：静止体积

| | OLD（save_local + 全量 npz） | NEW（追加式分片） | 省 |
|---|---|---|---|
| graph 2,878 条 | 37.18 MB<br>（faiss 11.79 + pkl 0.61 + npz 24.79） | 13.00 MB | **65.0%** |
| docs 2,430 块 | 52.12 MB<br>（faiss 9.95 + pkl 4.66 + npz 37.50） | 27.55 MB | **47.1%** |
| **单空间合计** | **89.30 MB** | **40.55 MB** | **54.6%** |

**与生产观测互验**：1001 §二记的现场单空间 `.index` 是 **33~131 MB**——本次实测的 OLD
**89.30 MB** 正落在区间内，说明合成形状**代表性成立**，不是随手造的数。

三处收益的来源可以逐项对上：

1. **索引不再落盘**：省掉 `index.faiss`（4 KB/向量，本来与 npz 里的向量重复存了一份）；
2. **float32**：npz 从 8 KB/向量砍到 4 KB/向量（`content_vectors.npz` 24.79→12.9 MB 量级）；
3. **不再 pickle docstore**：省掉 `index.pkl` 里那**第三份正文**（文档区尤其明显，4.66 MB）。

> 按向量条数算：**OLD 12 KB/向量 → NEW 4 KB/向量**（不含正文），即向量部分省 **2/3**；
> 文档区因为正文占比高，实测只省 47%。

#### 4.23.2 存储：**写入量**（这才是 14 GB BLOCK I/O 的正主）

单次 `save`（只新增 10 条向量）实际写入的字节：

| | OLD（整库重写） | NEW（增量） | 倍数 |
|---|---|---|---|
| graph | 37.36 MB | **0.046 MB** | **806×** |
| docs | 52.32 MB | **0.046 MB** | **1129×** |

**写入量降约 3 个数量级。** 机制很简单：OLD 每次 `add()` 后都重写整个索引与整个向量缓存，
而一次 Add 通常只新增个位数向量；NEW 只写这一段增量。

⚠️ **不能直接把 14 GB 按 800× 折算**：那 14 GB 还包含 YAML 写入与载入时的索引读取，
且多数空间远比 `u_3e***ef23` 小（§7.6.1：单空间最大 688 节点、中位 ~117）。
外部对账口径是 `14 GB / 4,378 次 Add ≈ 3.2 MB/次`，与"小空间整库重写"的量级吻合。
**绝对降幅须在平台上复核**，本节只钉住"单次写入字节"这个可复现的机制数。

#### 4.23.3 token：**本轮已落地的三项，省 0**

| 改动 | token 影响 |
|---|---|
| P0-1 埋点 | **0**——纯观测。但它是量出下面两项收益的前提（没有 role 分侧就算不出写读比） |
| P0-5 留痕截断 | **0**——只影响日志字节，不改变任何 LLM 调用 |
| P1-2 边连接拆批 | **触发时 input 略增**（旧节点上下文按批重发）；换到的是"避免一次 `out=32768` 的
输出浪费 + 该批边不再整批丢"。按 §4.20.2 的实测，`out=32768` 共 40 次、其中 33 次是
StoryRank，**边连接最多占 7 次** → 该收益约 `7 × 32768 tok × ¥8/M ≈ ¥1.8/轮`，很小 |

**结论：本轮没有 token 优化。** 真正的量在**尚未落地**的 P0-2/P0-3，量级如下
（基数取自 §4.20.2 的实测：maintain 组 **22,504**、非跳过组各走节点+边 2 次）：

| 项 | 现状 | 改后（估） | 依据 |
|---|---|---|---|
| 写侧 LLM 调用 | ≈35,100 次（= (22,504−4,954) × 2） | **≈8,000 次** | Σmessages 47,191 / 4,378 Add = **10.8 条/Add**；批放宽到 20 条 + 6000 字后多数 Add 只需 **1 组**（现 5.1 组） |
| 读侧 LLM 调用 | ≈2,704 次（story 1,585 + purpose 1,119） | 不变（除非做路线 V） | §4.20.2 |
| **合计** | **≈37,800 次** | **≈10,700 次** | **省 ≈72%**，对应 1001 §三的「44 → 6~8 次/题」 |

> 即：**存储已经落地并实测到 55%；token 还是 0，要等 P0-2/P0-3**。

> 43,312 → 10,156 次（含 triage），**省 77%**。与"44 → 6~8 次/题"的目标一致。

### 4.25 两个决策点的实验裁决（1001）

本轮遇到两个"要不要改"的决策点。**都做了实验，结论都是"不改"**——而且两条都推翻了原假设。

#### 4.25.1 P0-3 放大批：**质量腰斩，不放开**

§4.24.3 证明放大批能把调用从 43,312 降到 10,156（−77%），但那只测了调用数。
用 [alm_batch_quality_exp.py](../../alm/tools/alm_batch_quality_exp.py) 做质量实验：**生产日志里的真实对话**，
同一批语料只改切批方式，喂给真实 `MemoryDBA`（真 LLM），每个参数集用全新空图。

样本 30 次 Add / 395 条消息 / 131,072 字（13.2 条、4,369 字/Add，与总体 10.8/4,583 同量级）。

| 指标 | 6/1500（现行） | 20/6000 | 变化 |
|---|---|---|---|
| 组数 | 159 | 42 | −74% |
| triage 跳过 | 32 | **1** | 放大批后**长度闸失效**，triage 基本不再参与 |
| 节点 | 758 | 505 | −33% |
| 边 | 3,170 | 999 | −68% |
| **每千字节点数** | **5.38** | **3.61** | **−32.9%** |
| 节点平均字数 | 113.5 | 103.8 | −8.6% |
| **边/节点比** | **4.18** | **1.98** | **−52.7%** |
| 调用 | 339 | 85 | −74.9% |
| 成本 | ¥1.55 | ¥0.66 | −57% |

**判据（事前写死：任一项掉超 20% 即不放开）→ 不放开**：每千字节点数掉 33%、边/节点比掉 53%。

**机制说清了"为什么"**（这条比结论重要）：

- 每**组**产出其实变多了（6/1500 约 6 节点/组 → 20/6000 约 12 节点/组），但组的数量掉了 74%，
  文本量没变 → **净的每千字产出掉三成**，即"输入一长就少切、切粗"被实测坐实；
- 边更惨：**每次边调用产出的边数几乎没变**（约 25 → 24 条），但调用数掉了 74%
  → 边/节点比腰斩。这不是模型变笨，而是**单次输出容量成了瓶颈**：一批要连十几个新节点
  到彼此与旧节点上，模型给不出那么多条边。

> **两项改动的方向是相反的**：P1-2（边连接拆批）是在**修**这个瓶颈，而 P0-3（放大批）
> 是在**加剧**它。结论：**P0-3 不放开，保持 6/1500**；`.env.alm` 里的待验证块已注明。

#### 4.25.2 P1-1 前缀稳定化：**36% 已接近结构上限，原假设不成立**

计划 §P1-1 的判断是"命中率仅 36% → 前缀被污染或调用过于分散"，目标是 ≥80%。
用 [alm_cache_probe.py](../../alm/tools/alm_cache_probe.py) 实测（生产真实对话、真 LLM、按链分别量）。

**先纠自己两次错**（都记在这，因为方法错了结论就会反）：

1. **第一版连调两次同一个输入** —— 那两次 prompt 逐字节相同，缓存把**整条 prompt**都命中，
   "前缀"于是变成"整条 prompt 按 64-token 块取整后的长度"。症状：无论路径多大，算出的
   动态部分都卡在 ~240 tok（显然不可能）。
2. **第二版用不同的动态输入，但 story 链只在尾部差 1~2 个节点** —— 分叉点太靠后，
   缓存照样覆盖几乎整条路径。必须让**分叉点尽量靠前**。

修正后的实测：

| 链 | 静态前缀（跨调用公共部分） | 动态 | 单次 input | **命中率上限** |
|---|---|---|---|---|
| 节点抽取链 | **512 tok** | 842 | 1,354 | **37.8%** |
| 边连接链 | 1,536 tok | 1,955 | 3,491 | **44.0%** |

**与生产观测的 36% 同量级** → **36% 不是"缓存没吃到"，而是接近结构上限。**

**真因找到了**：`MemoryDBA._node_chain(*extras)` 把 temporal / choice 规则**插在 `## 输出`
之前**（`system.replace("\n## 输出", extras + "\n## 输出")`）。于是 4 个变体
（base / temporal / choice / choice+temporal）**只在插入点之前共享前缀**——
实测跨变体调用的命中只有 **512 tok**，远小于系统总量。变体切换一次，缓存就断一次。

**结论 → 不改**：

- 计划里的"≥80%"在当前结构下**达不到**：动态部分就是对话/链路本身，没法变成静态；
- 唯一可动的杠杆是**把变体增量挪到 system 末尾**（让基础系统成为公共前缀），
  但这会改变"规则 vs 输出格式"的相对位置，**属于会动质量的结构改动，须 A/B**；
- 于是 P1-1 从"优化项"降级为"**记录在案、暂不动**"。

> 两条裁决合起来还说明一件事：**本轮真正省下 token 的地方一个都没落地**——
> P0-3 被质量否掉、P1-1 被结构否掉。剩下的 P0-2（合并 triage 进抽取）是唯一还没被判过的，
> 而它同样改 prompt schema，需要同样的实验方式先裁决。

#### 4.25.3 P0-2 合并 triage 进抽取：**净亏，否决**

计划 §P0-2 的设想是"triage 的判定并入抽取的输出，调用数 ÷2"，并把 **44 → 22 次/题** 归功于它。
但账单里**输入 token 占 49%**，只看调用数会把方向看反——所以先量**按 role 分侧的真实 token 账**。

用 `python -m alm.tools.alm_batch_quality_exp --limit 12 --params 6:1500`（12 次真实 Add / 57,126 字）：

| role | 调用 | input | output | **in/次** | 成本 | **单次成本** |
|---|---|---|---|---|---|---|
| extract | 49 | 85,751 | 8,077 | 1,750 | ¥0.152 | ¥0.0031 |
| link | 49 | 145,648 | 16,010 | 2,972 | ¥0.282 | ¥0.0058 |
| triage | 33 | **7,780** | 83 | **236** | **¥0.013** | **¥0.00039** |

**triage 的单次成本只有抽取的 1/8、连边的 1/15** —— 它本来就是最便宜的那次调用。

P0-2 的账（每 12 次 Add）：

| | 变化 |
|---|---|
| **省**：砍掉全部 triage | 33 次 × ¥0.00039 = **−¥0.013** |
| **多花**：原被 triage 判 SKIP 的组要改跑抽取 | 约 8 组 × ¥0.0031 = **+¥0.025** |
| **净** | **+¥0.012，约 +2.7%** |

（30 次 Add 那轮的口径更硬：85 次 triage 里 **32 组**被判 SKIP，
 省 85×¥0.00039=¥0.033、多花 32×¥0.0031=¥0.099 → **净 +¥0.066，约 +5.6%**。）

**结论 → 否决。** 一句话：**拿最便宜的调用（triage）去换最贵的调用（抽取），方向反了。**

> #### ⚠️ 战略含义：P0-2 + P0-3 这条路线整体不成立
>
> 1001 计划 §一 的核心承诺是「改调用结构：**44 → 6~8 次/题**，全量成本 ¥150~250」，
> 而它由两块构成：P0-2（÷2）与 P0-3（÷3~5）。**现在两块都被实验否掉了**：
> P0-3 让图变稀（边/节点比 −53%）、P0-2 让成本升 3~6%。
>
> 也就是说：**"减少调用次数"这个方向在本系统的结构里是死的**——
> 现在的 5.1 组/Add × 2 次（抽取+连边）不是冗余，而是设计本身。
> 成本优化要换赛道：**不是少调，而是让每次调用更便宜**。

#### 4.25.4 换赛道后剩下的真杠杆：变体归并（P1-1′）

由 §4.25.2 的实测直接推出来的——**节点抽取链的缓存上限被"变体插入点"压到 37.8%**，
而它本该是 ~80%（前缀 1,088 / 单次 input 1,354）。

修法：`_node_chain(*extras)` 目前把 temporal / choice 规则 **插在 `## 输出` 之前**
（`system.replace("\n## 输出", extras + "\n## 输出")`），把 base 系统从中间切开。
若改为**追加到 system 末尾**，4 个变体就能共享整段基础系统作为公共前缀。

按分侧成本加权估算（extract 34% / link 63% / triage 3%）：

| | 加权命中率 | 输入成本系数 |
|---|---|---|
| 现状 | ≈40%（实测 36%） | ×0.602 |
| 变体归并后（节点上限 38%→80%、边 44%→~50%） | ≈59% | **×0.425** |

→ **输入成本可再降约 29%**（deepseek 命中价是未命中的 1/50，故这条对有缓存折扣的赛道特别值）。

**但这会改变"规则 vs 输出格式"的相对位置，属于动质量的结构改动**，必须按同一套流程裁决：
先跑 `alm.tools.alm_cache_probe` 量上限提升，再跑 `alm.tools.alm_batch_quality_exp` 量质量是否退化。
**在两项都通过之前不动默认。**

#### 4.25.5 P1-1′ 变体归并：**质量过关，但收益未被证实 → 也不放开**

已实现为开关 `MemoryDBA(variant_tail=True)`（默认 **False**，现行行为逐字不变）。

**第一道门（缓存上限）—— 通过，而且很漂亮**：

| 链 | 变体插中间（现行） | 变体挪末尾 | 变化 |
|---|---|---|---|
| 节点抽取链 | 512 tok / **37.8%** | **1,152 tok / 85.1%** | **+47.3 pt** |
| 边连接链 | 1,536 tok / 44.0% | 1,664 tok / 47.2% | +3.2 pt |

**第二道门（质量）—— 也通过**：20 次真实 Add（275 条消息 / 91,705 字），只改 `variant_tail`。

| 指标 | 6/1500 | 6/1500+尾 | 变化 |
|---|---|---|---|
| 组数 / 跳过 | 107 / 18 | 107 / 19 | — |
| 节点 | 522 | 511 | −2.1% |
| 边 | 1,665 | 1,819 | +9.2% |
| **每千字节点数** | 5.32 | 5.21 | **−2.1%**（阈值 20%） |
| **边/节点比** | 3.19 | **3.56** | **+11.6%** |
| **成本** | **¥0.95** | **¥0.97** | **+2.1%** |

**但第三件事把它否了：成本没降，反而 +2%。**

从分侧成本反解命中率（`cost = miss×2 + hit×0.04 + out×8`，单位 ¥/M）：

- 现行 extract：in=151,521 / out=18,837 / ¥0.314 → **命中率 ≈47.1%**
- 变体归并 extract：in=150,445 / out=18,387 / ¥0.307 → **命中率 ≈47.8%**

**几乎一样。** 而这直接推翻了我 §4.25.4 的模型——

> **我错在哪**：探针测的是"与**上一次调用**共有的前缀"，于是把 512 当成了"可缓存上限"。
> 但 DeepSeek 的前缀缓存会**同时保留所有变体**——第一次用过之后，每个变体的整段 system
> 都已入缓存，后续调用命中的是"自己那个变体的全长"。
> **插入点只影响每个变体首次出现的那一次**；4 个变体在一轮里各冷启动一次，占比可忽略。
>
> 这也解释了为什么实测 47% **高于**我算的 37.8% "上限"——那个上限本身是错的。

**结论 → 不放开。** 不是因为它伤质量（质量反而略好），而是**收益未证实**：
它改了 prompt 结构（把规则挪到输出格式之后），却拿不出可量化的省钱证据，
按"无效改动不占默认位"的口径应当停在开关上。

#### 4.25.6 token 侧三次裁决汇总：**计划里的三个杠杆全部被实验否掉**

| 项 | 预期 | 实测 | 裁决 |
|---|---|---|---|
| P0-3 放大批 | 调用 −77% | 每千字节点数 −33%、边/节点比 −53% | ❌ 质量腰斩 |
| P0-2 合并 triage | 调用 −30% | 成本 **+3~6%**（拿最便宜的换最贵的） | ❌ 净亏 |
| P1-1′ 变体归并 | 输入成本 −29% | 命中率 47.1% → 47.8%，成本 **+2%** | ❌ 收益未证实 |

**三次预期落空，但三次都不是白跑**——它们共同指向一个结论：

> **本系统的成本结构里没有"白捡"的余量。**
> 5.1 组/Add × 2 次（抽取+连边）是设计本身，不是冗余；
> 每次调用的 prompt 也已是最优布局（静态在前、动态在后、变体各自缓存）；
> 连"变体怎么放"这种细节都不影响实际命中率。
>
> 因此 1001 §一「改调用结构 → 全量 ¥150~250」这条主线**不成立**。
> 要继续压成本，只能从**语义**上动：换更便宜的模型（§五迁移）、
> 真正减少喂入量（路线 V / 精确路由，但那是拿召回换）、或缩短输出。

### 4.26 P1-2 输出审计：**上界 14%，其中最大一块是"常量字段"**（1001）

前三项都在动 input / 调用数，这一项动的是**输出**（账单占 49%）。先量上界——
用 [alm_output_audit.py](../../alm/tools/alm_output_audit.py) 把写入链每次调用的**原始输出文本**截下来做字段级审计
（真 LLM + 生产真实对话，20 次 Add / 275 条消息）。

#### 4.26.1 字段占比：载荷就是载荷

| role | 输出 | 主要字段占比 |
|---|---|---|
| extract | 18,018 tok | `content` **89.7%**（真正的载荷）、`node_type` 5.0%、`action` 5.0%、`reason` 0.2% |
| link | 44,408 tok | `rel_type` 32.6%、`action` **25.7%**、`from` 15.9%、`to` 15.8%、`reason` **10.3%** |
| triage | 139 tok | 只有 `NEEDED`/`SKIP`，无可省 |

**extract 侧基本没有可省**——89.7% 是节点正文本身。**link 侧才是重点。**

#### 4.26.2 两个发现，一个比一个大

**① `reason` 是死字段（静态检查确认）**：`_update_node` / `_delete_edge` 里都是
`reason = op.get("reason", "")` 读出后**从未使用**。占 link 输出 **10.3%**。

**② `action` 是常量字段 —— 这个更大**：枚举值分布实测

```
[extract] action=create  504 次 (99.8%)   action=update  1 次
[link]    action=create 1832 次 (100.0%)
```

**边的 `action` 100% 都是 `create`**，却占了 link 输出的 **25.7%**——
一个零信息量的字段，比 `reason` 还贵一倍多。

（顺带看到 `rel_type` 的实际分布：SCENARIO 1382 / CAUSAL 334 / SEQUENCE 87 / 其余 29，
 与 §4.20 的"边型 scenario 65.6%、causal 21.9%"对得上。）

**③ 格式开销**：extract **0.0%**（模型本来输出紧凑 JSON）；link **2.4%**（缩进/换行）——
因为 `EDGE_LINKING_FEWSHOT_EXAMPLE` 是 pretty-print 的，模型照抄了格式。

#### 4.26.3 收益上界

| 项 | extract | link | 合计 | 占总输出 |
|---|---|---|---|---|
| 删 `reason` | 0.2% | 10.3% | 约 4.6k tok | 7.4% |
| `action` 默认 `create`（非常量时才输出） | 5.0% | 25.7% | 约 12.3k tok | **19.7%** |
| 紧凑 JSON | 0.0% | 2.4% | 约 1.0k tok | 1.6% |
| **合计** | | | **约 18.0k tok** | **28.8%** |

**输出占账单 49% → 28.8% × 49% = 成本可省约 14%。**

这是四个候选里**上界最大**的一个，而且三项都不改语义：
- 删 `reason`／`action` 默认化：**只是把没人读或恒定不变的字段从 schema 里拿掉**；
- 紧凑 JSON：改的是 few-shot 示例的排版，解析结果完全一致。

#### 4.26.4 待做的质量验证（不能跳）

三项里有两项**会改变模型必须写出的内容**，故必须过质量门：

- **删 `reason` 会去掉"为连边给理由"这一步**——它可能是隐式的 chain-of-thought，
  删掉后边质量可能下降（这是本项最大风险，**不是**成本）；
- `action` 默认化基本无风险（解析侧加默认值即可）；
- 紧凑示例基本无风险。

判据同 §4.25：`边/节点比` 与 `每千字节点数` 均不得掉超 20%。
**在通过之前不动默认。**

### 4.27 P1-2 第一步落地：机制确凿有效，端到端被方差淹没（1001）

按"分两步"执行：**先做零风险的两项**（`action` 默认化 + 紧凑 few-shot），
`reason`（7.4%，带 CoT 风险）留作第二步。

#### 4.27.1 改动

| # | 位置 | 改动 |
|---|---|---|
| 1 | [graph_builder.py](../../dba_pipeline/extraction/graph_builder.py) `_apply_node_op` / `_apply_edge_op` | `action = op.get("action") or "create"`（原先缺 `action` 会 `raise ValueError`） |
| 2 | [dba.py](../../dba_pipeline/extraction/dba.py) 节点/边输出示例 | 删掉 create 的 `action`，加一句"省略即 create" |
| 3 | [dba.py](../../dba_pipeline/extraction/dba.py) 三处边 few-shot | 删 `action":"create"` + **由 pretty-print 改为单行紧凑** |
| 4 | `dba.py` 边连边统计 / `maintenance_scheduler.py` | 连带的 `op.get("action") != "create"` 也改为省略即 create |

> **第 4 条是这次改动最值得记的一处**：前三条改完后功能正常，但
> `dba.py` 里算"跨批连边分布"的那段仍直接比 `op.get("action") != "create"`，
> 于是**统计静默归零**——功能没坏，但"跨批连边有没有发生"这个判决依据断了。
> 教训：**改一个字段的语义（这里是从"必填"变"可省略"）时，要全仓搜它的所有读取点，
> 尤其是只用于统计/告警的那些**——它们不会报错，只会安静地变成 0。

#### 4.27.2 机制层：确凿有效

用 [alm_output_audit.py](../../alm/tools/alm_output_audit.py) 复测（20 次 Add，同一批语料）：

| 指标 | 改动前 | 改动后 | 变化 |
|---|---|---|---|
| `action` 在输出里出现次数 | 边 1832 次 / 节点 505 次 | **0 次** | 完全消失 |
| 格式开销（换行/缩进） | link 2.4%、extract 0.0% | **两者均 0.0%** | 归零 |
| **link 每 op 输出** | **24.2 tok** | **19.1 tok** | **−20.8%** |
| **extract 每节点输出** | **36.1 tok** | **32.6 tok** | **−9.7%** |
| 输出合计 | 62,565 tok | 52,000 tok | −16.9% |

**"每 op 输出"这一列是三次独立测量一致的数字**（24.24/23.9 → 19.09/19.06），
它把"op 数波动"约掉了，是本项唯一稳健的口径。

#### 4.27.3 端到端：被方差淹没

| 口径 | 指标 | 改动前 | 改动后 | 变化 |
|---|---|---|---|---|
| **30 次 Add** | 节点 / 边 | 758 / 3,170 | 789 / 3,011 | +4.1% / −5.0% |
| | 每千字节点数 | 5.38 | 5.60 | **+4.1%** |
| | 边/节点比 | 4.18 | 3.82 | −8.6% |
| | **成本** | **¥1.55** | **¥1.50** | **−3.2%** |
| **20 次 Add** | 节点 / 边 | 522 / 1,665 | 524 / 2,204 | +0.4% / +32% |
| | **成本** | ¥0.95 | ¥0.98 | **+3.2%** |

**两个抽样一个 −3.2%、一个 +3.2%** —— 而按"每 op −21%"推算应有 −8~10%。
说明**单次抽样的方差（±10~13%）大于本项的真实效应**，本地口径分辨不出来。

（20 次那个 +32% 的边数是噪声：30 次抽样回落到 −5.0%。这也是为什么
 单靠 20 次 Add 做判据不够——**样本量本身会决定结论**。）

#### 4.27.4 裁决：**保留第一步，不做第二步**

**保留**第一=步，理由：
- 机制正确（`action` 确实不再输出、格式开销确实归零）；
- 质量不退化（每千字节点数 +4.1%、边/节点比 −8.6%，均远在 20% 阈值内）；
- **每 op 输出确定降 21%**——这是"单位工作量的成本"下降，不会随抽样来回摆；
- 回退它没有任何好处。

**不做第二步**（删 `reason`，占输出 7.4% → 成本约 3.5%），理由：
- 它的收益**比第一步还小**，而第一步的真实效应已经小于本地方差；
- 它带**真实的质量风险**（`reason` 可能是隐式 chain-of-thought，删掉后边质量可能下降）；
- 用"收益测不出、风险确存在"的改动去占默认位，不符合本轮口径。

> #### 四次裁决的汇总（更新版）
>
> | 项 | 预期 | 实测 | 裁决 |
> |---|---|---|---|
> | P0-3 放大批 | 调用 −77% | 每千字节点数 −33%、边/节点比 −53% | ❌ 质量腰斩 |
> | P0-2 合并 triage | 调用 −30% | 成本 **+3~6%** | ❌ 净亏 |
> | P1-1′ 变体归并 | 输入成本 −29% | 命中率 47.1%→47.8% | ❌ 收益未证实 |
> | **P1-2 输出瘦身** | **成本 −14%** | **每 op 输出 −21%，端到端 ±3%** | **🟡 保留第一步（机制性改善），第二步不做** |
>
> 结论仍成立：**本系统的成本结构里没有"白捡"的余量**。
> P1-2 是唯一留下的一项，而它留下不是因为省钱，是因为**同样一份产出少写 21% 的字**——
> 这在换到按输出计费的赛道（如 gpt-4o-mini）时价值会更明显。

### 4.28 成本到底花在哪：**不是"大 Add"，是"组数 × 固定开销"**（1001）

问题：开销大是不是因为少数 Add 的文本特别大、建图用量也大？
用日志直接量（`alm.tools.alm_batch_audit --distribution` + 现场 `LLM #N: in=` 行），**全程只用 token，不碰价钱**。

#### 4.28.1 Add 体量分布：长尾存在，但是"中等强度"，而且被平台截断了

4,378 次 Add ／ 47,191 条消息 ／ 20,065,653 字 ／ 22,504 个维护组。

| 分位 | 字/Add | 组/Add | 条/Add | max_msg |
|---|---|---|---|---|
| p50 | 2,198 | 4.0 | 10.0 | 1,341 |
| p75 | 7,950 | 7.0 | 20.0 | 2,506 |
| p90 | 11,461 | 11.0 | 20.0 | 3,238 |
| p99 | 16,388 | 13.0 | 20.0 | 8,000 |
| **max** | **32,000** | 24.0 | **20.0** | **8,000** |

**注意那三个整数顶**：条/Add 到 p75 就顶在 **20**、字/Add **32,000**、max_msg **8,000**。
这是**平台侧的截断**——大 Add 跑不飞，尾部是有界的。

集中度（按字/Add 排序后头部占比）：

| 头部 | Add 数 | 字占比 | **组占比** | 均字/Add |
|---|---|---|---|---|
| 前 1% | 43 | 4.9% | **3.3%** | 23,008 |
| 前 5% | 218 | 16.3% | **12.4%** | 15,033 |
| 前 10% | 437 | 29.2% | **23.0%** | 13,428 |
| 前 20% | 875 | 52.6% | **42.2%** | 12,064 |

均匀时前 10% 应占 10%，实际 23%——**2.3 倍**。前 1% 只占 3.3%。
**所以不是"少数几个大 Add 吃掉大半成本"**，是一个从 2,198 字（中位）铺到 11,461 字（p90）的**连续长尾**。

#### 4.28.2 现场实测：in/次 与我本地模拟吻合

从日志里抓 **48,374 条** `LLM #N: in= out=`：

| | 值 |
|---|---|
| in/次 中位 | **1,895** |
| in/次 均值 | **2,171** |
| in/次 p90 | 3,777 |
| in/次 max | **19,022** |
| out/次 中位 | 244 |

我本地用**空图 + 生产真实对话**模拟出的 extract 1,750 / link 2,972（加权约 2,360）
与现场均值 2,171 **同量级** → 本地实验是可信的缩影。

**并且能看到"随图增长"**：

```
前 400 次 in 中位 1,424  →  后 400 次 in 中位 1,982（+39%）
按 1/4 分段：1,726 → 1,901 → 1,928 → 1,954
```

**增长真实存在但会收敛**——同一空间反复 Add，带回的上下文变大，涨到一定规模就平台期。

#### 4.28.3 关键分解：**对话本身只占 1/6**

每次调用的输入 = 固定提示词 + 图上下文 + 对话本身。用 §4.25.2 实测的静态前缀与 §4.27 的 in/次：

| 调用 | in/次 | **固定前缀** | 占比 | 变量 | 占比 |
|---|---|---|---|---|---|
| extract | 1,750 | 1,088 | **62%** | 662 | 38% |
| link | 2,972 | 1,536 | **52%** | 1,436 | 48% |

每组对话约 892 字 ≈ 388 tok。折算到**整个写入链的输入 token**：

| 构成 | 每组的量 | 占比 |
|---|---|---|
| **固定提示词（每次重发的规则+示例）** | 2,624 | **53%** |
| 图上下文（current_nodes / new_nodes / edges） | 1,322 | **27%** |
| **对话本身** | 776 | **16%** |
| triage | 224 | 4.5% |

> **对话文本本身只占约 16%。** 也就是说：**"某些 Add 文本特别大"不是成本的主因**——
> 主因是**每个组都要重发一遍 2,624 tok 的规则与示例**，而组数是按文本量线性增长的。

#### 4.28.4 结论：两层，方向相反

**① 文本量确实放大成本，但放大倍数是 2 倍左右。**
22,504 组 × 4,946 tok ≈ 111M 输入 tok（与账单 116.8M 同量级，差额是检索侧）。
其中 **59M（53%）是固定提示词**——它不是被文本量撑起来的，是被**组数**撑起来的。

**② 所以真正敏感的是「组数」，不是「总字数」。**
同样 20 万字：切成 5 组 vs 100 组，固定开销差 **20 倍**。
而组数 = `字数 ÷ 1500` 与 `消息数 ÷ 6` 的较大者；本轮 892 字/组、10.8 条/Add，
**两个约束都在起作用**。

**③ "随图增长"是真的，但幅度有限**（+39% 后收敛），且**这部分无法靠改参数省掉**——
它是记忆本体的体量。

#### 4.28.5 这给出一个之前没试过的方向

§4.25.1 只对照了 `6/1500` 与 `20/6000`（**3 倍跳**），结论是质量腰斩。
但按 §4.28.3，固定开销占 53%，**省固定开销的收益是实打实的**；
而 3 倍跳可能越过了最优点。

**中间档（如 `8/2000` 或 `10/2500`，1.3~1.7 倍）没测过**：
按 3 倍跳的质量代价（每千字节点数 −33%）外推，1.5 倍跳可能只掉 10% 左右，
而固定开销能省 25~30% × 53% ≈ **13~16% 的总输入** ——**可能就是净正**。

> 这是本轮唯一一个"预期为正且尚未被证伪"的候选，且它是在**已经知道风险长什么样**
> 的前提下提出的（有 §4.25.1 的判据与实验脚手架，增量成本只有一次抽样）。

### 4.30 写侧成本（gpt-4o-mini 口径）：**换模型不省钱；72% 花在没有题目的空间上**（1001）

按用户口径只算**大头：抽取建图**，并把命中率按实测区间取中（40%）。
gpt-4o-mini 官方价：输入 $0.150/M、缓存 $0.075/M、输出 $0.600/M。

#### 4.30.1 写侧总账（**前提：无缓存命中**）

> ⚠️ **口径来自用户实测：gpt-4o-mini 上"未见缓存命中"**，故**全部输入按 $0.15/M 实价计**，
> 不再打折。这一点对本节结论影响很大——见 §4.30.6。

本轮（4,378 次 Add / 22,504 个维护组，日志共 123,086,944 LLM tok）：

| 项 | 量 | 计算 | 钱 | 占比 |
|---|---|---|---|---|
| 输入 | 95,663,355 tok | × $0.15/M | **$14.35** | 59.8% |
| 输出 | 16,107,296 tok | × $0.60/M | **$9.66** | 40.2% |
| **写侧合计** | | | **$24.01 ≈ ¥170** | 100% |

**对比 deepseek 实测的 ¥150 → gpt-4o-mini 贵约 13%。**

原因在价目结构：两者在**未命中输入**（¥1~2/M ≈ $0.14~0.28 vs $0.15）与
**输出**（¥4~8/M ≈ $0.56~1.13 vs $0.60）上**几乎等价**；
deepseek 唯一的优势是**缓存折扣 1/50 vs 1/2**——而这一项在无缓存命中的前提下**完全失效**。

> 结论：**换 gpt-4o-mini 不但不省，还会贵约 13%。**
> （可以有别的理由迁移，但那不是成本理由。）

#### 4.30.6 无缓存使「固定提示词」从免费变成 $7.6 —— **P0-3 重新变得有意义**

这是"无缓存"这个前提下最重要的连带后果。写侧输入按构成拆：

| 构成 | 占比 | tok | 钱 | 占写侧总账 |
|---|---|---|---|---|
| **固定提示词**（每次调用重发的规则+示例） | 53% | 50.7M | **$7.61** | **31.7%** |
| 变量（对话 + 图上下文） | 47% | 45.0M | $6.74 | 28.1% |
| 输出 | — | 16.1M | $9.66 | 40.2% |

在 **deepseek（命中价 1/50）**下，这 50.7M 固定提示词只要 ¥1~2，几乎可以忽略；
但在 **gpt-4o-mini 无缓存**下它值 **$7.61，是整笔账的 1/3**。

**于是 P0-3（放大批）的经济性反转了：**

| | 组数 | 固定提示词 | 省 |
|---|---|---|---|
| 现行 6/1500 | 22,504 | 50.7M tok | — |
| 20/6000 | 6,250（−72%） | 14.1M tok | **36.6M × $0.15 = $5.49** |

→ **P0-3 在 gpt-4o-mini 无缓存下可省约 $5.5~6.2，即写侧总账的 23~26%**。
（在 deepseek 下这个数是 ±3%，因为省掉的那部分本来就在命中区、几乎不花钱——
 这也解释了 §4.27.3 里我端到端只测出 ±3% 的原因。）

**但它的质量代价没有变**（§4.25.1 实测：每千字节点数 −33%、边/节点比 −53%）。
所以它从"白捡"变成了一个**真实的权衡**：

```
换到 gpt-4o-mini 赛道后：
  放大批  → 省 23~26%，代价是图密度掉三到五成
  不放大批 → 维持质量，但固定提示词按实价付 $7.61
```

**注意这不改变"路由"的优先级**：路由能省 72%（无题空间），比放大批的 23~26% 大得多，
且不损失任何质量。

#### 4.30.2 **每组成本恒定 $0.00107** —— 这是路由决策的单价

按空间拆开（46 个空间），**每组的成本完全一致**：

#### 4.30.3 **最重要的发现：72% 的建图开销花在没有题目的空间上**

- **有 QA 的空间只有 3 个**（`u_aa***675f` 570 题、`u_23***2e71` 360、`u_4b***2246` 188，合计 1,118）
- 它们共 6,233 组 → 写侧 **$6.65（27.7%）**
- **另外 43 个空间 QA 全为 0**，共 16,271 组 → 写侧 **$17.36（72.3%）**

**不管这 43 个空间是"语料预热"还是"题目尚未下发"，结论一样：
如果它们本就不需要建图，那 72% 的开销是纯浪费——这比换模型、比放大批、
比输出瘦身加起来都大一个量级。**

#### 4.30.4 另一个结构发现：**QA 数 == `noise` 形态的 Add 数**

三个有题空间的语料形态：

```
u_aa***675f  noise×570, conversation×47   → QA 570
u_23***2e71  noise×360, conversation×27   → QA 360
u_4b***2246  noise×188, conversation×55   → QA 188
```

**570 / 360 / 188 与 QA 数逐一精确相等** —— 平台在**每道题**上都额外发了一次
被判为 `noise` 的 Add。也就是说这三个空间里，**约 1/5 的建图开销来自"每题的噪声注入"**，
而这批 `noise` 语料是否值得建图，本身就是个可判的问题。

#### 4.30.5 这张表就是决策表

```
建图   = $0.00094 × 组数        （恒定单价，已实测）
不建图 = $0
```

所以写侧路由的收益就是**该空间组数 × $0.00094**，没有别的变量。
决策只剩一个问题：**该空间建图后的质量提升，值不值这些钱。**

而那个质量提升（分子）仍然缺——它需要跑一次纯向量臂。

### 4.31 纯向量臂开关落地：**路由的实现 + 分子测量手段**（1001）

按 Plan §一 总目标实现两个**行为级**开关（默认全关，现行行为逐字不变）：

| 开关 | 取值 | 行为 |
|---|---|---|
| `ALM_WRITE_MODE` | `graph`（默认） | 按形态路由，会话型走 DBA 建图 |
| | `documents` | **强制整空间只存文档**：不抽节点、不建边、不进图，**/add 零 LLM 调用** |
| `ALM_READ_MODE` | `graph`（默认） | 目的推断 → 图扩展 → StoryRank |
| | `vector` | **纯向量直查**（图节点区 + 文档区合并按分排序），**/search 零 LLM 调用** |

改动点：`config.write_mode/read_mode` + `space.add()` 形态覆盖 + `space._pure_vector_search()`
+ `[IO] add/search` 留痕加 `模式=` + 启动横幅加「运行模式」行。

#### 4.31.1 三个刻意的设计选择

**① 非法值直接抛错，不静默退回默认。**
写错一个字母（`document` 少个 s）会导致"以为开了纯向量臂、其实还是全链路"——
那次对照实验就白跑，而且**从账单里看不出来**（两边都有开销，只是差一个量级）。
故 `_env_choice` 校验取值并抛 `ValueError` 让容器起不来。

**② 读侧 `vector` 把三层一起关掉。**
目的推断、图扩展、StoryRank 合计只占 5.3% 的 LLM 调用，但它们正是"图到底帮没帮上忙"
的全部来源。只关其中一层就分不清增益来自哪层，所以整条路径一起短路。

**③ 纯向量路径不写 `created_at`。**
保持与叙事路径**默认**形态一致（`story_created_at` 本来就默认关），
避免对照组多带一个变量。

#### 4.31.2 验收：判据只有一个——LLM 调用数为零

因为整套路由的账建立在"不建图 = 零 LLM 开销"上，只要哪条路径偷偷调了模型，
那个前提就是假的，收益全部作废——**而它不会报错，只会让账单对不上**。
故测试直接钉死调用数（`ScriptedChatModel._calls`）：

| 测试 | 断言 |
|---|---|
| `test_write_mode_documents_uses_zero_llm_calls` | `/add` 后 `_calls == []`，且 `docs` 非空（排除"什么都没做"）、图节点数为 0 |
| `test_write_mode_graph_is_the_default` | 默认仍是 `graph`，仍建图 |
| `test_read_mode_vector_uses_zero_llm_calls` | `/search` 新增调用数为 0，且返回非空 |
| `test_documents_only_space_end_to_end` | 纯向量臂全链路 `_calls == []` |
| `test_invalid_mode_is_rejected_not_silently_defaulted` | 非法值抛 `ValueError` |

**回归：181 passed / 4 failed**（4 条为既有的 `test_mcp_server` 替身缺 `reconcile`，非本轮引入）。

#### 4.31.3 平台对照实验的做法（拿到分子）

```
# 纯向量臂
ALM_WRITE_MODE=documents
ALM_READ_MODE=vector
# → 重跑同一批题（写入零 LLM，成本 ≈ 只有 embedding）
```

对照臂就是已有的全链路成绩：**locomo5 36.1% / locomo1 33.1% / scriptMem-angry 36.2%，
合计 35.2%（393/1118）**。

两臂相减，得到**图链路的净增益**，并按空间/题目切分——那才是路由阈值的依据。

**成本上这一次实验几乎是免费的**：纯向量臂的写入零 LLM 调用，读侧零 LLM 调用。

> 一个必须先排除的可能性：若纯向量臂的分数**接近或高于** 35.2%，
> 说明图链路在这三个 benchmark 上没有净增益——那时结论不是"路由"，而是"**默认走向量**"。
> 这两种结局要用同一个实验区分。

### 4.32 写侧路由的判据从哪来：**官方契约里没有分类字段**（1001）

路由的实现（§4.31）已经就位，但**判据**还没解决：怎么知道"这段语料属于哪一类、
值不值得建图"。查了官方公开材料 + 我们自己的现场日志。

#### 4.32.1 官方契约：Add 只有 4 个字段，**没有**数据集/分类字段

从 [agentmemoryleaderboard.ai/api-guide](https://agentmemoryleaderboard.ai/api-guide)
与官方仓库 [AML-memory/agent-memory-leaderboard](https://github.com/AML-memory/agent-memory-leaderboard)
得到的公开信息：

- Add：`request_id / messages[].role/content/timestamp / user_id / session_id`
- 官方 README 明确：文本赛道含 **PersonaMem、LoCoMo-Refined、CLBench、BEAM、LongMemEval、ScriptMem**
  等 10+ 数据集、1,500+ 历史、近 5,000 题
- 但**仓库不含 Add/Search 的驱动逻辑**（属"未公开的编排"）；
  `data/<benchmark>/pipeline.py` 只有 answer 与 judge 两段（已读，无请求构造）

**所以：契约层面不存在"告诉我们是哪个数据集"的字段。**

#### 4.32.2 但 `user_id` 的**格式**里可能带

官方文档的真实请求样例：

```json
"request_id": "eval:run_abc123:locomo_refined:conv-0:chunk-0",
"user_id":    "eval:run_abc123:locomo:conv-0"
```

而我们自己的 `engine.space_dirname` 注释写的也是同一形状：
`eval:run_abc:locomo:conv-0 → eval%3Arun_abc%3Alocomo%3Aconv-0`（当时是 `…-0.yaml` 文件名，见 §4.36 已改为目录名）。

**即 `user_id` = `eval:<run_id>:<dataset>:<conv_id>`，数据集名在第三段。**

#### 4.32.3 ⚠️ 但现场实测**对不上**

`_masked_id()` 是 `user_id[:4] + "***" + user_id[-4:]`，0930 full 日志里的空间名是：

```
u_aa***675f   u_23***2e71   u_4b***2246   u_3e***ef23
```

**前 4 位是 `u_aa` / `u_23` / `u_4b` / `u_3e`，不像 `eval:` 开头**——
更像 `u_<十六进制>` 的**哈希 id**。若真是 `eval:<run>:<dataset>:<conv>`，
掩码应该长 `eval***nv-0` 这样。

**两边矛盾。** 两种可能：
① 平台对 full 运行做了**哈希/脱敏**（规则里有"保持样本隔离"，脱敏是合理做法）；
② full 与 smoke 用了不同的 id 形态。

**结论：不能靠猜。** 只有看到真实报文才能裁决。

#### 4.32.4 唯一**确定可用**的数据集信道：`qa_feedback`

顺带把 §4.30.4 那个"`noise` 数 == QA 数"的巧合解释清楚了：

**平台把上一题的反馈作为一条 Add 消息送进来**（`space.py:841` 的 `_is_qa_feedback`），
内容里含 `qa_id=locomo1:q0000:step01`——**数据集名就在这**。
这条消息被 `_is_qa_feedback` 过滤掉、剩下的批次为空 → `_classify_batch` 判 `noise` →
丢弃、零 LLM 开销。所以 570/360/188 与 QA 数**逐一相等**。

**它的价值**：`qa_id` 是平台主动给出的、**明写数据集**的信道。
**它的局限**：来得**晚**——语料在问答阶段之前就写完了，而反馈是随每道题来的。

→ 对**Streaming 持续记忆**（官方明确纳入评测）有效：从第一条 `qa_feedback` 学到标签后，
把该空间后续的 Add 切到纯向量。对"先灌完语料再问"的模式无效。

#### 4.32.5 已落地的两处修复

| # | 位置 | 改动 |
|---|---|---|
| 1 | [contract.py](../../alm/contract.py) `parse_add_request` / `parse_search_request` | 契约外的顶层字段收进 `request.extra`，**不再静默丢弃** |
| 2 | [server.py](../../alm/server.py) | 新增 `trace_ids` 开关（`ALM_TRACE_IDS`）：原样留痕 `request_id` / `user_id` / `session_id` + `extra` 内容 |

**为什么第 1 条是必需的**：原来的写法只挑 4 个键，
平台**就算现在或将来送一个 `dataset`，我们也连"它存在"都不知道**——
于是"该不该建图"只能靠猜内容，而内容判据在 §4.24.2 已被证明不可靠。

**为什么第 2 条要独立开关而不是复用 `trace_io`**：`_masked_id` 刻意掩掉**中间段**，
而数据集名**恰好就在中间段**——复用 `trace_io` 看不到要用的东西。
代价是它会写入真实 `user_id`，故默认关、只在冒烟/诊断期开。

**回归：184 passed / 4 failed**（4 条为既有的 `test_mcp_server` 替身缺 `reconcile`）。

#### 4.32.6 一锤定音的下一步

```
# → 跑平台的 **smoke** 模式（非计分、量小）
# → 读日志里的 `[IO] add 标识:` 一行
```

那一行会直接给出：`user_id` 的真实形态、`request_id` 的分段含义、
以及**平台是否送了契约外的字段**。有了它，写侧路由的判据才能定下来。

> 在拿到这一行之前，我可以给出"内容侧候选判据"（轮次结构、说话人交替、
> 单条长度分布等），但 §4.24.2 已经证明**用量纪分布类判据去猜数据集是不可靠的**
> （同一份语料换切法结论就反过来）。所以正确顺序是：**先看字段，再决定要不要用内容。**

### 4.33 不用等 smoke：**完整 user_id 就在磁盘文件名上**（1001）

追问"之前的日志里没有吗"，逐个信道查了一遍。

#### 4.33.1 日志里确实没有（决定性否定）

49.4 万行全文扫描：

| 模式 | 命中 |
|---|---|
| `request_id=` | **0** |
| `session_id=` | **0** |
| `eval:` 前缀 | **1 处**——而且是**语料正文**（`Vocabulary retrieval:` 命中了 `eval:` 子串） |
| URL 编码文件名 `%3A` | 2 处——都是语料里的 `CELEX%3A32019R2088`（法条编号） |
| `*.yaml` 路径 | 40 处——全是 `secret.yaml` / `decrypted_secret.yaml` 等配置名 |

**结论：full 日志里零个未掩码的 user_id，全是 `u_XX***YYYY`。日志这条路走不通。**

#### 4.33.2 但磁盘文件名上有——因为 `space_dirname` 会**整串** URL 编码

`engine.space_dirname(user_id)` 把 user_id 逐字节转义成目录名
（`:` → `%3A`），**完整、未掩码**。本地 `data/` 实测：

```
data/ 下共 99 个空间名
  eval:<run>:<dataset>:<conv>形态   65 个
        eval:local:smoke:conv-0
        eval:loadtest:conv-0000 … conv-0063
  其它                             34 个（我们自己的 LiFEMem / memory_graph 等）
```

**`eval:<run_id>:<dataset>:<conv_id>` 这个格式被 65 个真实条目坐实**——
其中 `eval:local:smoke:conv-0` 是**我们自己跑平台 smoke 时留下的**，
说明平台签发过的 user_id 就是这个形状。

#### 4.33.3 所以：一条 `ls` 就能读出生产那 46 个空间的数据集名

本地没有 `u_` 前缀的空间（那批只存在于 0930 full 的那台服务器上）。
**它们的完整 user_id 就写在 `/data` 的文件名里**：

```bash
docker exec <容器名> sh -c \
  "ls /data | sed 's/%3A/:/g; s/\.index$//; s/\.yaml$//' | sort -u"
```

这一步会直接回答两件事：
1. 生产空间的 user_id 到底是不是 `eval:<run>:<dataset>:<conv>` 形态
   （若不是，说明平台对 full 做了脱敏，那就回到 §4.32.4 的 `qa_feedback` 方案）
2. 三个出题空间（`u_aa***675f` / `u_23***2e71` / `u_4b***2246`）**各自是哪个数据集**

#### 4.33.4 关键推论：**我们本来就有这个键**

不论第 3 段是不是数据集名，**`MemorySpace.user_id` 里存着完整值**——
`_masked_id()` 只是**打印时**掩掉，内存里一直是全的。

也就是说：**写侧路由不需要新增任何字段**，判据可以直接从 `self.user_id` 解析
（`user_id.split(":")`），零成本、零契约风险。唯一未知是第 3 段的语义，
而那是一行 `ls` 的事。

> 顺带记一条运维注意：`/data` 的文件名**暴露完整 user_id**。
> 这对我们是好事（可读），但意味着**对外分享目录列表前要先解码检查**。

### 4.34 生产 user_id 是哈希的 → 但 **96% 的写入发生在拿到标签之后**（1001）

用户在服务器上跑了 `ls`，结果推翻了 §4.32.2 的假设，却也给出了比它更好的答案。

#### 4.34.1 生产 user_id = `u_<sha256>`，**不含任何数据集信息**

```
u_000d82acb03e8518048588f8a737f23f6cd02de693ab14c17528b2a626f8e50c
u_000d82acb03e8518048588f8a737f23f6cd02de693ab14c17528b2a626f8e50c.docs
u_00ba320577b4b22b6ef3d8d7c0949cc72f934f4820d330768d2459be22199ffe
…
```

**64 位十六进制 = sha256。平台把 user_id 哈希后才下发**——这正是"保持样本隔离"
那条规则的自然实现：参赛方拿不到数据集名。（日志里的 `u_00***e2fa` 就是
`u_00c1ed…6793` 这类值的掩码。）

⚠️ **同时纠正 §4.33.2 的一个误读**：本地 `data/` 里那 65 个
`eval:loadtest:*` / `eval:local:smoke:*` **是我们自己跑 smoke/loadtest 时造的 id**，
不是平台的形态。官方文档示例里的 `eval:run_abc123:locomo:conv-0` 是**示意**，
生产实际是哈希值。

**所以：`user_id` 这条路彻底断了。**

#### 4.34.2 真正的发现：写入与答题是**流式交叠**的

既然只能靠 `qa_id`（在 `qa_feedback` 里），问题就变成"标签来得够不够早"。
用日志按时间统计每个空间的 Add 分布：

| 空间 | Add | QA | 首条反馈 | `qa_id`（**明写数据集**） | 反馈**之后**的 Add | 占比 |
|---|---|---|---|---|---|---|
| `u_aa***675f` | 617 | 570 | 12:09:31 | **locomo5:q0000:step01** | 605 | **98%** |
| `u_23***2e71` | 387 | 360 | 10:51:28 | **locomo1:q0000:step01** | 381 | **98%** |
| `u_4b***2246` | 243 | 188 | 15:16:30 | **scriptMem-angry:q0000:step…** | 207 | **85%** |
| **合计** | **1,247** | | | | **1,193** | **96%** |

**96% 的 Add 发生在首条反馈之后**，而且标签**来得极早**（locomo5 只用了 12 次 Add 就等到了）。

**这意味着平台不是"先灌完语料再提问"，而是 `Add(一段) → Search(一题) → Add(反馈) → …`
的流式模式**——正是官方 README 里点名的 **Streaming 持续记忆**能力。

#### 4.34.3 于是路由完全可行：**用 `qa_id` 学标签，再切换**

```
空间级策略（按 user_id 键，内存态）:
  未知              → graph（保守，质量优先）
  已知且值得建图     → graph
  已知且不值得      → documents（此后 /add 零 LLM 调用）
标签来源：qa_feedback 消息里的 qa_id 前缀（locomo1 / locomo5 / scriptMem-angry …）
覆盖：96% 的写入（前 4% 在标签到达前，只能按默认走）
```

**⚠️ 一个必须一起做掉的配套动作**：切换成 `documents` 时，该空间**此前的语料只存在于图里**
（那时走的是 graph 链路，没进文档区）。若只切写侧、读侧仍走纯向量，
那批早期语料就**检不到了**。所以切换时要：
1. 把已有图节点**回灌进文档区**（只用 embedding，零 LLM）；
2. 该空间 `read_mode` 一并切到 `vector`。

#### 4.34.4 顺带纠正 §4.30.3：「72% 花在无题空间」需要打折扣

§4.30.3 说 46 个空间里有 43 个 QA=0，判定为"72% 的开销是纯浪费"。
**在流式模式下这个结论要收回**：写入是**跟着题目一段段推进**的，
那 43 个空间很可能只是**在跑被中止时还没轮到它们的问答阶段**（用户在 12% 处停了测试）。

所以正确的说法是：**那 72% 不是"浪费"，而是"尚未被证实有题"**。
它仍然值得怀疑（43 : 3 的比例不像巧合），但**不能按已证实的浪费来计账**。

> 这也说明 §4.30.3 那个结论当时的证据强度不够——它是从"QA=0"直接推到"纯浪费"的，
> 中间缺了"写入是否会跟着题目推进"这一步，而这一步今天才查。

#### 4.34.5 三个空间的数据集已确定

```
u_aa***675f  → locomo5        570 题  36.1%
u_23***2e71  → locomo1        360 题  33.1%
u_4b***2246  → scriptMem-angry 188 题  36.2%
```

与 §4.18 的赛道分组（570/360/188）**逐一对应**，交叉验证成立。

### 4.35 链路审查（1001）：**一个功能性 bug、两处 O(n²)、一处合规冲突**

按"审查 bug / 漏洞 / 冲突项"逐个文件过了一遍，按严重度列出。

#### 4.35.1 功能性 bug：`_fallback_reason` 与 `action` 口径不一致 → **重复入库**

P1-2（§4.27）把节点 op 的 `action` 从必填改成"省略即 create"，但**读取点不止
`graph_builder`**——`space._fallback_reason` 里还留着 `op.get("action") == "create"`，
它现在**恒为假**：

```
抽取产出 create 但**全被语义去重合并**（created_ids 为空，`created` 为假）
  → 该分支判成 "no_create"（其实是一次正常成功）
  → _divert_raw 把**已经被合并掉**的原文又抄一份进文档区
  → 重复内容 + 一次无效 embedding + 每次一条 WARNING
```

修在 [space.py](../../alm/space.py#L1203-L1216)：先归一化 `_act(op) = op.get("action") or "create"`，
再判 create / update|deprecate|fix_type。**同口径的读取点共 4 处**，另外 3 处
（`acts` 计数器、`maintenance_scheduler` 的 create/边计数）此前恒为 0，只喂日志，一并修。

> 教训：字段从"必填"变"可省略"时，**调用方的判定逻辑**比解析器更容易漏——
> 它在另一个模块里，且失效方式是静默的（多存一份、日志恒 0）。

#### 4.35.2 O(n²) 写放大（一）：文档区每次 Add 重写整份条文

`_save_documents` 原先每次 Add 都 `yaml.dump` **整份** docs，而 `documents` 写下
**全部语料**都走这条路（`doc_chunk_chars=1800`）→ 第 k 次 Add 要重写前 k 次累计的全部
条文。线上口径：一轮 full 4,378 次 Add、终态 ~10 MB → **写放大接近 46 GB**（与已修的
"索引全量重写"同源，见 §4.23）。

改为**快照 + 增量日志**（文档区只增不改，故天然适配）：

| 产物 | 作用 |
|---|---|
| `<space>.docs.yaml` | 条文**快照**，仅在日志超过 4 MB 时重写一次（摊薄 ~1/次/4MB） |
| `<space>.docs.log` | append-only JSONL，**每次 Add 只追加一行**（写量与新增成正比） |

回放时**按 id 去重**（合并是"先写快照、后删日志"，中途崩溃会重叠 → 去重保证幂等），
并**就地截断末尾半行**（写入途中崩溃的残行若留着，下次追加会接在它后面，
变成一条永远解析不了的脏行 → 此后所有条文都读不出来）。

#### 4.35.3 O(n²) 写放大（二）：分片合并**抛 NameError**，且不抗崩溃

上一轮引入的 `_compact_if_needed`（两条判据版）有两个缺陷：

1. **`total` 只在 (16, 64] 区间内定义** → 文件数超过硬上限（64）时，日志行引用未定义
   变量 → **NameError**。因为恰好是"追加型负载攒够 64 个分片"这条唯一会走到 ② 的路径，
   等于**② 这条判据一触发就抛异常**。
2. 顺序是"先 `_wipe_shards` 清空、再重写"——**中途崩溃 = 整个向量库归零**
   （虽能从图谱 `_reindex()` 重建，但那要把整个空间重新 embedding 一遍；
   纯向量臂下那就是整个语料，是真金白银）。

改为**先续号写新分片、全部写完再删旧分片**：回放规则是"文件名升序、后写覆盖先写"，
新快照排在旧分片之后，故任意时刻崩溃都能还原出**正确**状态（墓碑照常生效、存活行被
新快照覆盖），删除只删到一半也无妨。

#### 4.35.4 合规冲突：新增落盘产物必须同步 `alm/cleanup.py`

`cleanup.py` 按**后缀**归组删除评测数据，认不出 `.docs.log` → 它会落进 `ignored`、
**永不删除**。而它装的正是原文（且是新增条文的唯一完整拷贝），一旦留下就是
"图谱按期删了、装原文的日志还留着"——**留存条款要避免的那种情形**。
已把 `DOCS_LOG_SUFFIX` 并入归组（连同 `docker-compose.alm.yml` 的产物注释：
四份 → 五份），并加 `tests/test_alm_cleanup.py` 钉住归组与删除。

#### 4.35.5 已核**无问题**的项

| 项 | 结论 |
|---|---|
| `_clip_for_log` | 只作用于三处 `[IO]` 行，**没碰 `[QA]`**（[QA] 是题号信道，不受 `trace_io` 控制） |
| `_store_documents` | **无容量闸**（不像 `_store_raw_fallback` 有 `fallback_max_nodes`）→ 不丢内容 |
| 图谱索引 vs 文档索引路径 | `.index/faiss` 与 `.docs.index/faiss` 互不覆盖 |
| `save()` 无变更时 | `_vec_log` 空 → 不写分片；`docs` 无新增 → 不写日志 |
| `write_mode=documents` + `read_mode=vector` | 两条短路互不干扰；`/add`、`/search` 均零 LLM 调用 |
| `_divert_raw` 三个调用点 | documents 模式下形态判定先被覆盖 → 会话分支不可达，兜底链路不参与 |
| `trace_ids` 合规边界 | 契约外字段落 `extra` 保留（不再静默丢弃），且**只有开关打开才留痕**（默认关） |
| `engine` LRU 换出 | 换出前 `add()` 已 `save()`，不丢数据；在用空间不换出（租约） |
| mcp 替身 `FakeVectorStore` | 缺 `reconcile` → 4 条既有 FAILED；**是替身没跟上接口**，已补 |

#### 4.35.6 遗留冲突（**未修**，需先决策）：模式开关是**进程级全局**

`write_mode` / `read_mode` 是 `ALMConfig` 上的**全局**字段，而一个 ALM 服务实例
**同时**承载多个 user_id 空间（评测就是一个进程跑全部数据集）。因此：

- 设 `ALM_WRITE_MODE=documents` → **所有数据集**都变成纯向量，做不到
  "让完整链路只跑在它擅长的地方、其余交给纯向量"；

### 4.36 底层重构：**一空间一目录** + 工具归档（1001）

要求："重构整个底层，把所有 ALM 产物归档，放在 alm 文件夹下"。

#### 4.36.1 布局对照

| 产物 | 旧（五份平铺在 data_dir 下） | 新（一个 user_id 一个目录） |
|---|---|---|
| 记忆图谱 | `<data>/<user>.yaml` | `<data>/<user>/graph.yaml` |
| 图谱索引 | `<data>/<user>.index/` | `<data>/<user>/graph.index/` |

文档区一律从 `yaml_path.parent` 派生。

#### 4.36.2 为什么值得改（三件事同时成立）

1. **归组规则消失**：删除一个空间 = 删除它那一个目录。旧布局靠 `.docs` 后缀剥离来归组，
   多一个产物就多一次漏删机会（§4.35.4 刚踩过一次）。
2. **`ls <data>` 可读**：旧布局下 N 个空间就是 5N 个平铺条目，分不出谁和谁是一家。
3. **后缀歧义消失**：空间目录名由 `space_dirname` 转义而来、**不可能含 `.`**，
   于是"这个文件属于哪个空间"从"推断"变成"看路径"，两个 id 空间也不会再撞名。

#### 4.36.3 ⚠️ 不迁移（按决定），但补了一个合规口子

存量数据**不迁移**：`<user>/graph.yaml` 不存在时 `create=False` 判定"无此空间"、
`create=True` 直接建新空间——旧数据从服务视角看就是不存在（可接受，评测数据本就一次性）。

**但旧文件仍躺在盘上，装的是记忆正文**。若清理逻辑只认新布局，这些文件会以
"非空间条目"的身份被**永久跳过**——30 天留存条款就此失守。故 `collect_spaces` 保留对
旧后缀的识别（`_LEGACY_SUFFIXES`），把旧遗留与同名的新目录**并组、按同一留存期清理**。
歧义不存在：新布局目录名不含 `.`，凡以那五个后缀结尾的必然是旧布局产物。

> 顺带记一条判断顺序的坑：`<user>.index/` 是**目录**，若先按"是目录就是空间"认领，
> 它会变成一个名叫 `xxx.index` 的独立空间——删是删得掉，但与它的图谱脱钩、对不上账。
> 故必须先判后缀、再判目录。

## 七、改动复审与分流（0927 战略转向：**保系统健康**，不再追榜）

**背景**：平台记分板显示 B = 多跳推理、**B2 = 因果链**（smoke 与 full 同一子项）；我们在 smoke 里
B2 恒 0，而别的项目在 full 里 B2 = 26.89。同时确认：**smoke 只作"结构与功能健康性确认"，
full 的子项多得多**（smoke 约 8 个 vs full 约 24 个）。据此**改变战略**：
一切以**系统自身健康**为准，此前所有"为分数"的改动需重新审视。

**"健康"的操作定义**（本节判据）：
① 正确性（不产生错误结果）；② **不静默失效**（失败必须可见）；③ 数据不丢、不被污染；
④ 可观测、可复现；⑤ ALM 与 MCP 行为一致；⑥ 契约合规；⑦ 成本 / 延迟可接受。

**处置原则（已确认）**：
- **健康类 → 保留**；
- **纯形态/口径类（只为分数）→ 加开关、默认关**（代码与文档一律保留，便于复现与回滚）；
- **有健康代价或收益不明 → 单列"需重评"**，先测量再定；
- **`eval/` 工具分"长期资产 / 一次性探针"**，探针归档。

> ⚠️ **执行时机**：本节的处置**在本轮 smoke 跑完后再动手**——正在跑的读数不能被打断。
> 且一律**只改默认值与开关，不删代码**。

### 7.6 参数复审：峰值容忍带与目的过滤（0930）

**结论：这两个参数的问题不在"值该调"，而在"从没被接出来 + 当年的标定语料不匹配"。**

| 参数 | 现状 | 关键事实 |
|---|---|---|
| `peak_tolerance` | 库默认 **0.10** | `retriever.py:266` **从未显式传入**（0815——debugPlan 已记录）→ ALM 侧**无入口**；0.10 的标定语料是 0925 实验的 **163 / 322 节点小图**（同质场景少） |
| `purpose_filter_threshold` | **0.30** | 入口已有（config / space / env）；但标定样本是 `probe_threshold_retune.py` 的 **14 组中英对照**，且都是"动机→行为"这类**低同质**对照对 |

**实测证据（0927，600 次线上检索）**：`峰值/候选` 中位 **0.81**（候选≥300 档 **0.79**）——"寻峰"平均只筛掉 19%；该退化**与 embedding 无关**（换 bge-m3 前后均 ≈0.80）。原因：δ 是**绝对**带宽，而真实语料余弦分布很窄（scriptMem 18 次全在 0.5497~0.5884、全距 0.039，δ=0.10 已是全距的 2.5 倍）。

**本轮落地（默认都不改变现行行为）**：
- `dba_pipeline/core/peak_find.py`：新增纯函数 `resolve_peak_tolerance()`——`ratio<=0` 返回绝对带宽（行为逐字不变）；`ratio>0` 返回 `ratio × (peak_mean − min(轮均分))`，**尺度无关**，因而**自动随场景（图规模 / 同质程度）调整**，无需人工分档。
- `dba_pipeline/retrieval/retriever.py`：`__init__` 接受 `peak_tolerance` / `peak_tolerance_ratio` 并**显式传给 `PeakFinder`**（补上历史遗漏）；`_collect_peak_tolerance` 记录带读数。
- `alm/config.py`：`ALM_PEAK_TOLERANCE`（默认 0.10）/ `ALM_PEAK_TOLERANCE_RATIO`（默认 0 = 关）；`alm/space.py` 透传；`alm/server.py` 横幅显式打出（此前**无法核对**生效值）。
- **新增两处观测**（此前完全不可见）：`检索:` 行**追加** `带比 / 带宽 / 带模式` 与 `目的过=out/in`（追加在末尾，不影响既有解析脚本）。**观测先于调值**——见 §7.7。
- `tests/test_peak_find.py`：+3 条（默认不变 / 相对带宽随分布缩放 / spread=0 不清空）。

**未做（需读数或大图）**：两个参数的**数值**不动——旧判据已作废（§7.7），且本地 `data/dba_eval/` 最大只有 **322 节点**，复现不了线上 3000 节点级退化。**需先导出生产图做离线复算。**

**⚠️ 7.6.1 实测修正（0930，生产图离线复算）**：用容器导出的生产图 + **npz 里的生产 bge-m3 向量**
（节点侧零 embedding 成本）跑了两组扫描，**结论与上面的设计相反**：

- **规模纠正**：单空间最大 **688 节点**（中位 ~117；1–49 节点的占 139/210）。日志里的"落库节点 3101"
  是**每轮全部 21 个空间合计**，不是单空间——"3000 节点图"的说法作废。
- **容忍带不是输出量的瓶颈**：δ 从 0.10 收到 **0.03**（5 倍），N 中位**纹丝不动（23）**，
  p90 200→149、max 反而涨到 391。**小图档（≤49 节点）读出恒为 100%**，与带宽完全无关。
- **`ratio × spread` 会反向**：真实图轮均分全距 > 0.2 ⇒ `0.5×spread > 0.10` ⇒ 带宽**变宽**。
  实测 200–499 档 N 中位 170→**224（+32%）**、500+ 档 320→**414（+29%）**。
- **真正的瓶颈是可达集大小**：`_effective_seed_k`（≤40 全量）+ `expand_k=40`，在 ≤700 节点的图上
  一步铺满 ⇒ 大图读出仍有 **~46% 全图**、小图 **100%**。
- ⇒ **改法修正**：`peak_tolerance_ratio` 不作为默认（保留为可选项）；"减少过多输出"应动
  **检索预算（expand_k / 种子策略）** 与 **目的向量侧的发散控制（purpose_filter_threshold /
  purpose_weight_coef）**；若要用带宽，只能用**绝对收紧到 0.02~0.03**，不要用比例式。
- 复现：`python -u -m eval.exp_band_real --round 67ef87ff --tols 0.10 0.05 0.03`
  与 `--ratios 0 0.5`（图 + 向量见 `eval/.cache/alm_data/`，由容器导出）。
- 局限：n=33 案例 / 1 轮（09-25 16:06）；大图样本少（200–499 档 4 例、500+ 档 2 例）；
  目的是 LLM 推断（同一轮内固定、跨轮不可比）；`带比`（带内候选/候选总数）与日志里的
  `峰值/候选` **不是同一个量**，不可直接比。

**⚠️ 7.6.2 B2 现场实测（0930，第二次导出 `alm_data_r3.tgz`）**：拿到 **B2 的 scriptMem 大图**
（`u_d5***f6c9` = Billing 立场演变，**409 节点/1151 边**；`u_9d***dd76` = 锁链门，521 节点；
另加 05:32 轮两个同族空间，共 **4 个案例 / 2 轮独立**）。节点侧仍用 npz 生产向量，零 embedding。

**现行配置的"过多输出"在现场被复现**：`exp=40 / pur=0.30` → 读出 **228~253 点 = 47~49% 全图**
（生产日志该题实测 265/409 = 65%，同量级）。

**唯一有效的旋钮是 `purpose_filter_threshold`（= 用户所说的"目的向量控制发散方向"）**：

| 配置 | 读出 N 中位 | N/全图 | 诱导边/点 | 分量（护栏） |
|---|---|---|---|---|
| **exp=40 / pur=0.30（现行）** | **~226** | **~48%** | 4.4~6.8 | **2** |
| exp=40 / pur=0.32 | ~245 | ~54% | — | — |
| exp=40 / pur=0.38 | **~140（−38%）** | **~28%** | 3.3~4.8 | 3~4 |
| exp=20 / pur=0.30 | ~209（−8%） | ~45% | 4.3~6.8 | 2~5 |
| exp=20 / pur=0.38 | **~102（−55%）** | **~21%** | 3.3~4.8 | 3~5 |

- **`pur 0.30 → 0.38` 使读出腰斩（−38%~−55%，两轮一致）**，而护栏只从"分量 2"退到"3~4"、
  边/点仍 ≥3.3（每点平均还有 3 条以上边）→ **可接受**。
- **对照**：`expand_k` 单独用几乎不改读出（−4~8%）；容忍带（δ 0.10→0.03）同样不改
  （见 §7.6.1）→ **这两个都不是"减少过多输出"的有效旋钮**。
- **结构性矛盾（重要）**：按阈值/分数**逐点**筛会**切碎连通性**（极端配置下分量 2→8、边/点 →2.1）。
  若要"既压输出又保链"，正解是 **先按阈值缩候选，再按弱连通分量整块裁**（整块留/整块丢），
  而不是逐点过滤——这为下一步的"结构化 cap"提供了直接依据。

**建议档位**：低风险 `pur=0.32`（−10%，护栏不变）；有效档 **`pur=0.38`**（−55%，护栏 2→3~4）。

--spaces "u_d5***f6c9,u_9d***dd76" --expand-ks 40 20 --purpose-thrs 0.30 0.32 0.38`。
局限：n=4、2 轮；目的是 LLM 推断（轮内固定、跨轮不可比）；"分量"是粗粒度护栏指标。

### 7.7 更正：0925 报告"StoryRank 采纳率 96%"是**坏指标**（0930）

0925 报告 §四.4 的核心依据是"线上实测 采纳/喂入 = **96%**（极端 378/379）"，据此判定"StoryRank 没在做筛选"，并把后续方向定为"转修 StoryRank 的采纳率"。

**该依据不成立**：`采纳` 是后端按**二元组覆盖率 ≥ 0.5** 算的。0930 用**真实节点 + 真实正文**复算某空间：**529 个节点全部通过**（最低覆盖率 0.62）→ 该指标在**句式重复**的数据集上**饱和**，恒等于喂入点（10/10 次比值 0.98~1.00）。**"96%"是度量伪影**，不能用来判断 StoryRank 是否在取舍。

影响：① 日志侧已停用 `采纳`（改打 `正文=`，见 7.2 与审查文档 §11.4）；② §四.4 的结论**需在大图上用可信口径重测**；③ §7.6 的两处新观测正是为避免再犯同类错误。
